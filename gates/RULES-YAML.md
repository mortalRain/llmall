# llmall YAML 配置注释精修规范

本文件是**唯一权威规范**。执行前必须完整读一遍；与你的默认习惯冲突时，以本文件为准。

---

## 一、绝对约束（违反即任务失败）

1. **只允许修改注释**（`#` 开头的部分，含整行注释与行尾注释）。
2. **配置本身必须逐字节不变**：不改任何 key、value、缩进、层级、顺序、引号、空行位置。
   - 不新增配置项，不删除配置项，不调整缩进，不改变量占位符（如 `${LLMALL_DB_PW:123}`）。
   - 唯一例外：*行尾注释被删除后*，该行允许去掉多余的行尾空格。
3. **不新增任何原注释里没有的信息**。不要凭想象补充配置含义。
4. 不执行 `git`；不改分配给你之外的文件（可以读任意文件）。
5. 不启动任何服务、不跑 docker、不跑 maven。

## 二、强制校验（必须自己跑，必须通过）

```
pwsh -File gates\yaml-check.ps1 llmall-xxx-service/src/main/resources/application.yaml
```

多个文件一次传完（空格分隔）。路径以**仓库根**为根（命令都在仓库根目录下执行），**用正斜杠**。

- 输出 `结论: 通过` 且退出码 0 才算完成。
- 报 `[FP1 配置内容被改!]` = 你动了配置本身，**必须还原**后重跑。
- 报 `[FP2 配置格式被改 ]` = 缩进/换行被动了，同样必须还原。
- 任务回复里**必须原样粘贴最终的校验输出**。没有校验输出的交付一律视为未完成。

## 三、注释内容规则

### 删除（全部删除）
1. **口语化描述**："手滑"、"白填一遍"、"照着建环境会启动失败"、"别急着改代码"、"踩过"、"坑"。
2. **踩坑过程与实测叙述**："实测发现…"、"改前是…"、"原先是…"、"本次修复…"、"此前写成…"、
   "已实测"、"连跑 4 遍"、"某次排查时…"。**注意**：把踩坑的"过程"删掉，但把"结论"保留成一句预警（见下）。
3. **背景铺垫**："这样做的意义是…"、"这也是值得展开讲的一个点…"、"设计分层说明…"。
4. **装饰性横幅**：`# ====================`、`# ---------- 以下为 xxx ----------` 一律删除。
5. **与本文件无关的跨文件说明**：除非是必须同步修改的强约束，否则删。
6. **代码块 / 表格 / 示例日志**：删除。

### 保留（只保留这三类，且要写短）
1. **配置项作用**：该项控制什么（一句话）。
2. **关键注意事项**：取值范围、单位、生效条件、必须与别处保持一致的口径。
3. **踩坑预警**：不按此配置会导致什么具体后果（**只留结论，不留过程**）。
   - 反例（删）：`# 实测 VM 上 Redis 密码是 123456 而不是 123，当时照着文档写 123 导致启动即连接失败`
   - 正例（留）：`# 【注意】口令为 123456，与库口令 123 不同，写错表现为启动即 Redis 连接失败`

---

## 四、格式规范

1. 统一用 `#` 单行注释；**不使用**多行横幅式注释。
2. 重要提醒加 `【注意】` 前缀，如 `# 【注意】...`。
3. **对齐工整**：
   - 同一层级、相邻配置项的行尾注释，尽量对齐到同一列；
   - 整行注释与所注释的配置项保持相同缩进；
   - 注释与被注释项之间不留空行（除非原本就有分组空行）。
4. 风格：**生产级配置文件风格** —— 简洁、专业、无冗余信息。一行说清，不写第二行。
5. 注释语言与全文一致（中文），术语用配置项本身的名字（如 `spring.redis.sentinel.nodes`）。

## 五、风格基准（动手前先读）

- **优化后（目标风格）**：
  `llmall-gateway\src\main\resources\application.yaml`
  该文件的 Redis 段落是"作用 + 【注意】后果"的标准写法，可作参照。
- **需要避免的反面风格**：
  `nacos-config\shared-redis.yaml`
  该文件注释量 49 行 / 66 行文件，含大量"为什么这样设计"的论证与实测叙述，是本次要压缩的重点对象。
