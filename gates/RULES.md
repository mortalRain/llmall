# llmall 注释精修规范（阿里巴巴Java开发手册）

本文件是**唯一权威规范**。执行前必须完整读一遍；与你的默认习惯冲突时，以本文件为准。

---

## 一、绝对约束（违反即任务失败）

1. **只允许修改注释**：`//` 行注释、`/* */` 块注释、`/** */` JavaDoc。
2. **代码部分必须逐字节不变**：不改逻辑、不改结构、不改缩进、不改变量名/方法名/类名、不重排 import、
   不删代码行、不加代码行、不调整空行位置以外的任何代码字符。
   - 唯一例外：*紧跟代码的行尾注释被删除后*，该行允许去掉行尾多余空格。除此之外行尾空白也保持原样。
3. **不新增任何原注释里没有的信息**。不要凭想象补充设计意图。
4. 不执行 `git` 任何命令；不修改分配给你之外的文件（可以读任意文件）。
5. 不运行 maven / 不编译整个项目（慢且无关）；校验只用下面的 `gates\gate.ps1`。

## 二、强制校验（必须自己跑，必须通过）

### 单个文件
```
pwsh -File gates\check.ps1 llmall-xxx-service/src/main/java/com/xxx/Yyy.java
```

### 多个文件（一次传完）
```
pwsh -File gates\check.ps1 path/a.java path/b.java path/c.java
```

- 路径以**仓库根**为根（命令都在仓库根目录下执行），**用正斜杠**。
- 输出 `结论: 通过` 且退出码 0 才算完成。
- 报 `[FP1 代码语义被改!]` = 你动了代码，**必须还原那处代码**后重跑，直到通过。
- 报 `[FP2 代码格式被改 ]` = 代码的换行/书写形态被动了（例如你把两行合成一行），同样必须还原。
- 输出里会给出每个文件的「注释 N -> M 行，代码 X -> Y 行」，**Y 必须等于 X**。
- 任务回复里**必须原样粘贴最终的校验输出**。没有校验输出的交付一律视为未完成。

## 三、注释内容规则

### 删除（全部删除，不留残句）
1. **所有 HTML 标签**：`<h3>` `<ul>` `<li>` `<b>` `<p>` `<pre>` `<br>` `<ol>` `<code>` 等一律去掉，改为纯文本。
   - `<pre>` 里的示例输出/日志片段直接删掉（属历史证据）。
2. **所有 Markdown 强调标记**：`**粗体**`、`*斜体*`、反引号 `` ` `` 包裹 —— 源码注释不是 Markdown 渲染场景，
   这些标记在 IDE 里只会显示成多余符号。要强调就用 `【注意】` 或"必须/禁止"这样的实词。
3. **口语化表达**：如"手滑传个 0"、"白填一遍"、"排查成本极高"、"别急着改代码"、"踩过"、"坑"。
4. **讲故事式背景与历史叙述**：任何形如
   "改前是…"、"原代码…"、"原实现…"、"初版…"、"以前…"、"实测发现…"、"第一版就是这么写的"、
   "本次修复…"、"原先这里放过…"、"已删除"、`【改前的问题】`、`【改后】`、`【原来错在哪】` 的内容 —— 全部删除。
   这类信息属于 git 的职责。
5. **代码本身能看懂的逻辑**：普通 CRUD、getter/setter、显而易见的赋值、简单参数校验、直白的循环。
6. **重复表述**：同一个意思在类注释、方法注释、行内注释里说了多遍的，只保留信息量最大的那一处。
   接口注释与实现注释重复时，**接口只留契约**（一两行），"为什么"下沉到实现类。
7. **装饰性分隔线**（`// ===== 以下是 xxx =====`）：删除。
8. **相邻注解已经说清楚的约束**：`@Pattern(regexp=..., message=...)`、`@NotBlank`、`@Schema(description=...)`
   已经把校验规则与字段含义写明白了，**不要再补一条同义的字段注释**。
   反例（实测踩过）：在 `@Pattern(regexp = "^1[3-9]\\d{9}$", message = "手机号格式不正确")` 上方写
   `/** 手机号：11 位，1 开头且第二位 3-9 */` —— 纯属把注解翻译成中文，属"代码本身能看懂"。
9. **不要把可配置项的值写进注释**：`llmall.jwt.tokenTTL` 这类能被 yaml / 环境变量覆盖的值，
   一旦写成"（30 分钟）"，配置改了就变成**一条错误的注释**。
   写法：要么用不会漂移的表述（如"短/长"这类相对关系），要么用 `{@code llmall.jwt.tokenTTL}` 指路。
   （不变量则相反：金额单位"分"、状态字典值这类**稳定的领域事实**必须写。）

### 保留（只保留这四类，且要写短）
1. **设计决策**：为什么这样设计而不是另一种做法（非显而易见时才写）。
2. **隐藏坑点**：不看注释、只读代码一定会踩的坑。
3. **边界约束**：取值范围、单位（分/毫秒/分钟）、前置条件、时序要求（必须在事务提交后/必须原子）、幂等键口径。
4. **业务注意事项**：业务规则上的非直觉约定（例如"支付密码与登录密码同一列"这类现状约束）。

### 更正（唯一允许"改写"而非"删除"的情形）
**类注释与代码事实矛盾时必须更正** —— 错误的注释比没有注释更糟，它会主动误导读者。
- 已确认的实例：一批 PO/VO 由 MyBatis-Plus 生成器产出，带着 `@author 同城生活` / `@since 2023-05-05`
  模板签名，而类注释写的是**别的表**的名字 —— 例如 `Cart`（`@TableName("cart")`）的类注释是"订单详情表"，
  同名的错误也出现在 `CartVO` 上。
- 更正的依据**必须来自该文件内可见的信息**：`@TableName` 的值、类名、字段名与字段口径。**不得臆造**。
- 只改这一行事实描述；**不要**顺手补设计意图（那属于"新增信息"，被 §一.3 禁止）。
- 顺带删掉生成器签名 `@author` / `@since` 与空的 `<p></p>`、`<p></p>` 残留。

## 四、格式规范

1. **类注释**：标准 JavaDoc。
   - 首行一句话说明类职责（不要"XX服务实现类"这种废话式重复类名，要说明**它负责什么业务**）。
   - 重要注意点简要补充，总计 2~4 行以内。
2. **方法注释**：只保留契约、副作用、时序、幂等性、异常语义。
   - 方法内仅在**关键逻辑**与**非直觉边界**处用 `//` 单行注释。
   - 普通流程、逐行翻译代码的注释，一律删。
3. **字段注释**：PO/DTO 字段只保留**字典值、单位、口径**（如"单位分"、"1 待审核 2 已发布 3 已屏蔽"）。
   纯字段名重复的注释删掉。
4. **重要提醒**用 `【注意】` 前缀开头。
5. **保留** `{@code ...}`、`{@link ...}` —— 它们是标准 JavaDoc 内联标签，不是 HTML。但**不要新增**。
6. 缩进与代码对齐保持一致；JavaDoc 每行星号对齐。

## 五、风格基准（动手前先读这两个文件）

- **优化后（目标风格，你的产出应与它同级或更简）**：
  `llmall-shop-service\src\main\java\com\llmall\shop\constant\ShopRedisConstants.java`
- **优化前（反面教材，81 行注释 → 28 行）**：
  第一轮改动前的快照，属工作痕迹、**未入库**。需要对照时按提交取回：
  `git log --oneline -- llmall-shop-service/src/main/java/com/llmall/shop/constant/ShopRedisConstants.java`
  找到第一轮之前的那次提交，再 `git show <提交>:<上面的路径>`。

反面教材里被删掉的东西：类注释"为什么集中管理"的叙述、`<p>/<pre>/<b>` 标签、
"改前的问题（实测可复现）"整段实测证据、"原先这里放过一个 Duration…纯粹是死代码，已删除"、
以及把 `【为什么物理 TTL 必须比逻辑过期时间长】` 这种 8 行论证压缩成类注释里的一行【注意】。
