# 工程化闸门（gates/）

本目录是「只改注释、代码零改动」这件事的**可复现证据链**，随仓库一起交付。

它原先放在仓库外的 `D:\dsh\.verify\comment-opt\`（被 `.gitignore` 排除），后果是：
换台机器、换个 clone 目录，闸门全线失效 —— 而"闸门失效"和"闸门报错"在退出码上分不出来。
现在工具集、现行基线、自校验依赖都在仓库内，**clone 下来就能复现**。

> 原始工作区 `D:\dsh\.verify\` **没有搬走**：那是迁移，不是搬家。历史快照（`pre-*`、`backup/`、
> `pre-codeopt/` 等）留在原处，因为它们不是交付物，也不需要被 clone。

## 一、前置要求（实际跑通的环境已写明）

| 项 | 要求 | 本仓库基线实际生成/验证用的版本 |
|---|---|---|
| 操作系统 | Windows（路径分隔符与 `-ExecutionPolicy` 逻辑按 Windows 写；Linux/macOS 未验证） | Windows 10/11 |
| PowerShell | **Windows PowerShell 5.1 或 PowerShell 7+ 均可**。闸门不依赖 `PATH` 上有 `pwsh` —— 谁跑起闸门，子脚本就用同一个宿主跑 | pwsh 7.6.6；另在 Windows PowerShell 5.1 上整套复跑通过（退出码同为 0） |
| JDK | **JDK 11+**（项目本身要求 11；闸门用 `javac` 现场编译两个指纹工具）。解析顺序：`JAVA_HOME` → `PATH` 上的 `java` 反推 | Microsoft OpenJDK 11.0.32.1 |
| Maven | 只有跑 `verify-all.ps1` 的编译段（不加 `-SkipBuild`）才需要。解析顺序：`MAVEN_BIN` → `PATH` 上的 `mvn.cmd`/`mvn` | Apache Maven 3.9.6 |
| 网络 | 默认**离线**编译（`mvn -o`）。机器上没有本地仓库时用 `-Online` | — |

环境变量（都不设也能跑）：

```powershell
$env:JAVA_HOME      = 'D:\develop\jdk11'                              # 不设则从 PATH 上的 java 反推
$env:MAVEN_BIN      = 'D:\develop\apache-maven-3.9.6\bin\mvn.cmd'      # 不设则从 PATH 找
$env:MAVEN_SETTINGS = 'D:\Maven\settings.xml'                          # 不设则用 ~/.m2/settings.xml，仍没有就不传 -s
```

**UTF-8 的两处约定**（都踩过坑，已固化成脚本行为，不需要使用者操心）：

- `gates/*.ps1` 一律保存为 **UTF-8 with BOM**：Windows PowerShell 5.1 在没有 BOM 时按本地代码页（简体中文机器是 936）读脚本，中文注释会变成乱码并直接引发**语法错误**。
- 脚本启动时把 `[Console]::OutputEncoding` 与 `$OutputEncoding` 都设为 UTF-8：中文一旦跨进程传递（父脚本过滤子脚本输出）就会变成乱码，而**乱码不报错**，只会让结论行匹配静默失配。

## 二、一条命令

```powershell
# 在仓库根目录执行；跑完七道闸门 + 13 模块编译
pwsh -File gates\verify-all.ps1

# 只跑分析闸门（跳过编译，快）
pwsh -File gates\verify-all.ps1 -SkipBuild

# 只有 Windows PowerShell 5.1 的机器上照样能跑
powershell -ExecutionPolicy Bypass -File gates\verify-all.ps1 -SkipBuild

# 改了一个文件，只想验它（最常用）
pwsh -File gates\gate.ps1 llmall-shop-service/src/main/java/com/llmall/shop/service/impl/ShopServiceImpl.java
```

命令都在**仓库根目录**下执行，路径参数一律以仓库根为基准、用正斜杠。
`gates/` 的位置就是仓库根的定位依据（`gates/` 的上一级即仓库根），不再有写死的绝对路径。

### 退出码：刻意分成三档

| 退出码 | 含义 | 该怎么办 |
|---|---|---|
| `0` | 全绿 | — |
| `1` | **硬闸门失败** —— 闸门失效，或出现未登记的违规 | **必须修**，不得继续 |
| `2` | 硬闸门全过，台账闸门报出**已登记**的待处理偏差 | 逐条核对《已知偏差台账》，确认每条都有 owner 与触发条件 |

把「闸门失效」和「已登记偏差」压成同一个非零码，会逼出两种坏行为：
要么把真实违规当"已知问题"放过去，要么为了消红去改台账而不是改代码。

## 三、七道闸门各拦什么

| # | 闸门 | 拦什么 | 判据 | 类别 |
|---|---|---|---|---|
| 1 | **Java 指纹** | 代码语义或**书写形态**被改 | FP1（token 流，空白不敏感）= 0 **且** FP2（代码行序列，对缩进/换行敏感）= 0，且无「未被基线覆盖」的文件 | 硬 |
| 2 | **YAML 指纹** | 配置项、缩进、结构被改 | 同上 | 硬 |
| 3 | **Lua / SQL / 脚本指纹** | 非 Java/YAML 文件的代码被改 | 剥注释后**代码行序列的 SHA256** 逐文件一致 | 硬 |
| 4 | **内容质量** | 11 类不该出现在注释里的东西 | HTML 标签 / 粗体标记 / 装饰横幅 / 历史叙述 / 实测叙述 / 口语化 / 待办标记 / 审计标签 / 迁移叙述 / 变更叙述 / 模板残留 = **全 0** | 硬 |
| 5 | **闸门自校验** | 闸门**自己**出错 | 34 个用例全过（剥离规则、内容规则、端到端指纹、Feign 重试的运行时对照） | 硬 |
| 6 | **字典一致性** | DDL 的取值与代码对不上 | ① 同字段同标签取值冲突 = 0；③ 库名指向错误 = 0；④ 同表同列表述不一 = 0；② 为候选清单 | 台账 |
| 7 | **Feign 一致性** | 有写调用的服务漏配禁重试 | 用到写方法的服务必须显式引入 `NoRetryFeignConfig` | 台账 |

> 1–3 证明「没改代码」，4 证明「该删的删干净了」，5 证明「闸门本身可信」，6–7 证明「跨制品口径一致」。

## 七、自校验的外部依赖（来源与版本）

闸门第 5 项（`selftest.ps1`）的场景 F 要**真的发出一次 HTTP 请求**才能证明"禁重试时只发一次"，
所以需要真实的 Feign 客户端。这些依赖已入库到 `gates/lib/`：

| 文件 | 版本 | 来源 | 为什么需要 |
|---|---|---|---|
| `feign-core-11.8.jar` | 11.8 | 项目自身依赖树（spring-cloud-openfeign 3.1.3 传递引入的同版本），取自本机 Maven 本地仓库 | 被测对象就是 Feign 的 `Retryer`，版本必须与项目一致 |
| `spring-context-5.3.27.jar` | 5.3.27 | 同上（Spring Boot 2.7.12 管理的版本） | 生产源码 `NoRetryFeignConfig` 上有 `@Bean`，编译它需要该注解 |
| `spring-core-5.3.27.jar` | 5.3.27 | 同上 | 上者的注解元数据依赖 |

场景 F 的做法是**用 `javac` 把 `llmall-api` 里的 `NoRetryFeignConfig.java` 现场编译**，
再让探针取它里面的那个 `Retryer` —— 而不是在测试里重写一遍 `NEVER_RETRY`。
后者验证的是测试自己的复述，不是产品代码。

**改动前后**：场景 F 原先是去 `%TEMP%\llmall-demo\` 找 `run-obs-demo.ps1` 解压出来的 fat jar，
于是"全新 clone 上跑一次 `verify-all -SkipBuild`"必然红（而红的原因是前置缺失，不是用例失败）。
现在只要 `gates/lib` 与 `llmall-api` 的源码在位，F 用例**无条件可跑**。

`tools/run-obs-demo.ps1` 仍是例外：它走 Spring 上下文，classpath 是整个 `BOOT-INF/lib`（近百 MB），
无法入库，因此它需要先跑过一次构建（`verify-all.ps1` 的 BUILD 段）。它不在 `verify-all` 的闸门链上。

## 八、基线更新流程（**改基线必须附 diff + 理由**）

基线是「某个时刻的**代码**指纹快照」。它**只记录代码，不记录注释** ——
这意味着：**正常的注释改动永远不需要更新基线**。

| 情形 | 是否需要重建 | 必须附的证据 |
|---|---|---|
| 只改注释（含新增/删除注释行） | **不需要** | — |
| 新增或删除文件 | 需要 | 文件清单（新增/删除各几个、是哪些、为什么） |
| **代码确实变更了** | 需要 | **代码 diff + 变更理由 + 评审结论** |

### 红线：不允许用「更新基线」绕过闸门

- 闸门报 `FP1` / `FP2` / `代码被改动` 时，**唯一正确的处置是还原那处代码**；
- 只有「代码变更本身就是本次任务的目标」时，才允许重建基线，且必须在该次提交里附上 diff 与理由 ——
  否则基线就从「证据」退化成「橡皮图章」；
- 同理禁止：删除规则、放宽阈值、把闸门改成永远通过。**闸门只许变强。**

### 重建命令

```powershell
# Java / YAML（全量，覆盖式）
java -cp gates\build\classes CommentFingerprint snapshot . gates\baseline\java.round2.txt
java -cp gates\build\classes YamlFingerprint   snapshot . gates\baseline\yaml.round2.txt
# 非 Java/YAML
pwsh -File gates\gate.ps1 -Snapshot
```

> `-Snapshot` 写文件时用 .NET 显式写 **UTF-8 无 BOM**：`Set-Content -Encoding UTF8` 在
> Windows PowerShell 5.1 会写 BOM，同一份基线在两个宿主下产生不同字节，
> diff 时看不出是真改还是宿主差异。

## 九、闸门自身的覆盖边界（如实写明）

- **`gates/**/*.java` 纳入第 1 道闸门**（`java.round2.txt` 覆盖它们）：闸门工具的代码同样不许悄悄改，
  改了就按第八节流程重建基线并附 diff。
- **`gates/**/*.ps1` 不纳入第 3 道闸门**：`-Snapshot` 显式排除 `gates/` 自身。它是测量仪器，
  不是被测量的项目源码；`-Snapshot` 的结果在排除前后**逐字节一致**（40 个文件），
  即项目侧覆盖范围没有任何变化。
- **`gates/**` 不纳入第 4 道闸门（内容质量）**：这 11 条规则是为**产品源码的中文注释**定的
  （禁止把 `<h3>核心职责</h3>` 这类 HTML 当注释写），而闸门工具自身的 JavaDoc 用 `<p>/<ul>/<li>/<pre>`
  是标准 JavaDoc 写法。排除前后本闸门扫到的**项目文件数一致（323 个）**，项目侧覆盖未被缩小。
  需要单独校验 `gates/` 下某个文件时用 `-Path` 显式指定，`-Path` 模式不受此排除影响。
- **`gates/baseline/*.round2.txt` 的覆盖缺口（已知且未处理）**：`sql/merged/52a`、`60`、`61`、`62`
  四个脚本是新增文件，尚未纳入 `any.round2.txt`；`any.round2.txt` 是"按清单校验"而不是"按目录校验"，
  未列出的文件不会被拦。这是本轮刻意不动基线的结果（只提交现状），补录属于下一轮。
