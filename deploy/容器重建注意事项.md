## 附：容器重建时的两个 MQ 坑（实测踩过，务必先读）

这两个坑的共同特点是：**数据卷还在、命令也没报错，但服务就是起不来**。VM 迁移、改配置、升级镜像都会触发。

### 1. 节点名漂移 → "数据卷还在，vhost/队列却全没了"

RabbitMQ 的节点名是 `rabbit@<hostname>`，而 docker 默认拿**容器 ID** 当 hostname。
一旦容器被 `docker rm` + `docker run` 重建，节点名就变了，mnesia 里旧节点的目录成了孤儿：

- 现象：`rabbitmqctl list_vhosts` 只剩 `/`，队列/交换机全空，但数据卷里明明有数据；
  用户 `llmall` 看起来"还在"，其实是 `RABBITMQ_DEFAULT_USER` 在空 mnesia 上重新创建的，属于假象。
- 修法：`docker run` 时显式加 `--hostname mq`（compose 里写 `hostname: mq`），让节点名固定为 `rabbit@mq`。
  重建后仍会复用同一份节点数据。
- 已经踩了怎么办：重建 vhost 与权限，其余交给应用自己重新声明：
  ```bash
  docker exec mq rabbitmqctl add_vhost /llmall
  docker exec mq rabbitmqctl set_permissions -p /llmall llmall ".*" ".*" ".*"
  ```
  然后重启各服务，`@RabbitListener` 与 `RabbitConfig` 会把队列/交换机重新声明出来。

### 2. 延迟消息插件默认不启用 → trade-service 启动即失败

trade 的"超时未支付自动关单"用的是 `x-delayed-message` 交换机，它需要
`rabbitmq_delayed_message_exchange` 插件。镜像里**预装了但不启用**，而启用状态写在
`/etc/rabbitmq/enabled_plugins`（容器层，不在数据卷里），容器一重建就回到未启用状态：

- 现象：trade-service 启动过程中报
  `QueuesNotAvailableException: Failed to declare queue(s):[trade.delay.order.queue]`
  → `NOT_FOUND - no queue`，随后应用退出（不是"稍后自动恢复"，是直接起不来）。
- 修法：
  ```bash
  docker exec mq rabbitmq-plugins enable rabbitmq_delayed_message_exchange
  # 关键：把启用文件放进数据卷，并用 RABBITMQ_ENABLED_PLUGINS_FILE 指向它，否则下次重建又会丢
  docker exec mq sh -c "cp /etc/rabbitmq/enabled_plugins /var/lib/rabbitmq/enabled_plugins"
  ```
  compose 里对应 `RABBITMQ_ENABLED_PLUGINS_FILE: /var/lib/rabbitmq/enabled_plugins`。

### 3. 相关：MySQL 连接数会被"反复重启的服务"打满

服务进程被杀时，它对 MySQL 的连接不会立刻消失，要等 `wait_timeout`（默认 8 小时）才回收。
反复重启几次就能把 `max_connections`（默认 151）打满，症状是 `Too many connections`，
连 root 都连不进去。项目侧的缓解是把连接池上限压到 5（见 `shared-jdbc.yaml` 与各服务
`application.yaml` 的 `hikari.maximum-pool-size`），10 个服务最坏 50 条，留足余量。
