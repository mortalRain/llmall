# llmall 后端注释规范（Java / Lua / YAML / SQL）

> **适用范围**：全部后端模块（11 服务 + 网关 + 公共层）的 Java 类、Lua 脚本、YAML 配置、SQL 迁移脚本、运维脚本。
> **目标**：消除注释与实现的不一致，把「设计原因、边界约束、误改后果」沉淀到代码旁边，而不是留在某个人脑子里。
> **本质**：这是一次**注释工程化**，不是「多写注释」，也不是「少写注释」——
> 信息量不足要补，复述代码要删，说过时的要改。

---

## 一、五条总原则（每次改动都要对照）

| # | 原则 | 判定标准 |
|---|---|---|
| 1 | **最小侵入** | 只增删改注释，不动代码、不动方法签名、不动结构。任何一次改动都要能被指纹闸门证明「代码逐 token 未变」 |
| 2 | **价值导向** | 只写「设计原因、边界约束、误改后果、历史踩坑点」。**禁止复述代码、禁止代码翻译式注释** |
| 3 | **读者匹配** | Controller 面向前端与运维；Service 面向后端开发；配置与工具面向运维；脚本面向全量开发者 |
| 4 | **纠偏优先** | 与实现不符的、描述历史实现的、过期的、空泛的注释，**优先级高于新增注释** —— 错误的注释比没有注释更糟 |
| 5 | **格式统一** | 八类注释（类/方法/行内/风险警示/配置/Lua/SQL/TODO）用同一套写法；同类信息用同一个标记词 |

### 1.1 关于书写形态的硬性约定

**源码注释一律使用纯文本，禁止 HTML 标签与 Markdown 强调标记。**

```java
// 反例（本项目 2026-10 已全量清理过一轮，不要回潮）
/**
 * <h3>核心职责</h3>
 * <ul><li><b>幂等</b>：用唯一键兜底</li></ul>
 */
```

理由有三条，都是可验证的：

1. **渲染场景不成立**：源码注释在 IDE、`git diff`、代码评审里都不渲染 Markdown，`<h3>`/`**` 只显示成多余符号。
2. **与既有代码不一致**：全仓库 280 个 Java 文件的既有风格是纯文本分段，混入 HTML 会让同一仓库出现两种风格。
3. **有自动闸门拦截**：`lint-comments.ps1` 把 HTML 标签、`**粗体**` 判为违规，写进去会导致验收不通过。

需要分段或强调时，用**中文标记词**代替：

```java
// 正确写法：用【】标记段落，用实词表达强调
/**
 * 优惠券发放与核销的唯一入口。
 *
 * 【核心职责】
 * 1. 秒杀券的库存预热、原子预扣与订单落库
 * 2. 普通券的领取、核销与回滚
 *
 * 【注意】库存口径是「总名额」而不是「剩余量」，误传会让库存永久归零。
 */
```

保留 `{@code ...}` / `{@link ...}` —— 它们是标准 JavaDoc 内联标签，不是 HTML 排版标签（但**不要新增**，只保留原有的）。

## 二、八类注释规范

### 2.1 类注释

**读者**：接手这个类的后端开发。**必写对象**：核心业务类、工具类、配置类、对外暴露的入口类。

模板：

```java
/**
 * {一句话职责：它负责什么业务，不要写「XX服务实现类」这种重复类名的废话}。
 *
 * 【核心职责】
 * 1. {职责一}
 * 2. {职责二}
 *
 * 【设计意图】{为什么这样做，而不是另一种做法；非显而易见时才写}
 *
 * 【边界约束】{取值范围 / 单位 / 前置条件 / 时序要求}
 *
 * 【注意】{最容易被改错的地方 + 改错的后果}
 */
```

硬性要求：

1. **一句话职责必须落到业务上**，不重复类名。
2. **【注意】只写「会被人改错的地方」**，不写泛泛的「注意线程安全」。
3. 类注释与代码事实矛盾时**必须更正**。已知实例：一批 PO/VO 由 MyBatis-Plus 生成器产出，类注释写的是**别的表**的名字（`Cart`（`@TableName("cart")`）写成「订单详情表」，同一错误也在 `CartVO` 上）。
   更正依据**必须来自文件内可见信息**（`@TableName` / 类名 / 字段名），**不得臆造**。

**范例**：`ShopRedisConstants`（目标风格，最简）、`JwtTool`（四段闭环）、`PayOrderServiceImpl.PaymentLiability`（三态说明为什么不能用 boolean）。

### 2.2 方法注释

**读者**：调用方。**必写对象**：公开方法、核心业务方法、复杂逻辑、有副作用或降级分支的方法。

#### 核心业务方法（四要素齐全）

```java
/**
 * {功能说明：做什么、给谁用}。
 *
 * 【设计意图】{为什么这样做；若为修某缺陷，说明缺陷现象}
 *
 * 【入参约束】{含义 + 取值范围 + 是否可空}
 * 【返回】{含义；null 的语义必须写清}
 * 【异常】{XxxException：触发条件}（业务异常必须列出，调用方据此决定是否重试）
 * 【风险】{误改后果 / 调用方必须注意的时序或幂等要求}
 */
```

#### 简单方法（一行）

```java
/** 脱敏格式：138****1234 */
private String maskPhone(String phone) { ... }
```

#### 判断标准

| 方法类型 | 要求 |
|---|---|
| 涉及资金 / 库存 / 鉴权 | 四要素全 + 必须写「误改后果」 |
| 有幂等 / 并发语义 | 必须写清幂等键口径 + 并发裁决点（DB 条件更新 / 唯一键 / Lua / 分布式锁） |
| 有降级或异常兜底 | 必须写清 fail-open 还是 fail-closed，以及为什么 |
| 纯 getter/setter/转换 | 不写，或一行 |

**接口与实现的分工**：接口注释**只留契约**（功能、入参、返回、异常，1~2 行/方法），
「为什么这样做」**下沉到实现类**。跨文件重复的论证只留一处，其余用 `{@link}` 指路。

### 2.3 行内注释

**只在五类位置写**，其余一律不写：

| 位置 | 该写什么 |
|---|---|
| **幂等点** | 幂等键的口径与由来、为什么不能用客户端可伪造的值 |
| **并发分支** | 裁决点在哪（条件更新 / 唯一键 / Lua / 锁）、为什么不能用「先查再写」 |
| **状态流转** | 状态机取值域、非法状态为何不可能出现 |
| **异常降级** | fail-open 还是 fail-closed、降级窗口内会发生什么 |
| **历史缺陷修复点** | **当前的不变量是什么**（不是「以前错在哪」——那属于 git 的职责） |

```java
// 幂等键必须是服务端产生且确定的值，禁止用客户端可传的 traceId 或按次随机值：
// 随机键会让「扣款成功但响应丢失」被误判为未扣，重试即重复扣款。
String deductBizNo = "PAY:" + payOrderId + ":" + deductedAmount;
```

```java
// 用「插入即判重」而非「先查再插」：查询与插入之间无互斥，并发下两个线程都会查到 0 并各扣一次。
try { stockFlowMapper.insert(flow); } catch (DuplicateKeyException e) { return false; }
```

**禁止**：逐行翻译代码（`i++ // i 加一`）、显而易见的分支说明、装饰性分隔线（`// ===== 以下是 xxx =====`）。

### 2.4 风险警示

**四类位置必须加警示**，且必须写「误改后果」，不能只写「注意」：

| 位置 | 警示内容 |
|---|---|
| **鉴权旁路** | 严禁用在鉴权路径上，以及用了会怎样 |
| **资金核心逻辑** | 口径、幂等键、事务边界；误改会导致什么（重复扣款 / 少扣 / 对不上账） |
| **库存口径** | 参数到底是「总名额」还是「剩余量」；传错会怎样 |
| **关联配置项** | 改这个值必须同步改哪个值；不同步会打开哪个时间窗 |

统一用 **【注意】** 开头；**严禁/禁止**类约束用 **【严禁】**，写在方法注释或类注释最上方：

```java
/**
 * 【严禁】把本方法用于任何鉴权路径 —— 那等于取消令牌过期校验。
 */
public TokenPayload parseAllowExpired(String token) { ... }
```

```java
/**
 * 【注意】本值必须大于 access 令牌寿命。若把 tokenTTL 调大（例如 2 小时），
 * 本值必须同步调大，否则会出现「水位已过期而旧 access 未过期」的窗口。
 */
private static final long GLOBAL_LOGOUT_TTL_HOURS = 1;
```

判定标准：

- **会随某个任务完成而消失** → 用 `TODO(责任人, 日期)`
- **是当前实现的固有约束，永久有效** → 用 `【注意】…`，且必须写清误操作后果

### 2.5 配置注释（application.yaml）

**读者**：运维。核心参数必须回答三个问题：**取值依据、调大了会怎样、调小了会怎样**。
只写「超时时间」是没有价值的 —— 下一个人不知道能不能改。

```yaml
feign:
  client:
    config:
      default:
        # 【取值依据】连接 2s：内网同机房 RTT < 1ms，2s 已是三个数量级的余量。
        #            读 5s：下游最慢的写接口 P99 实测远低于 5s，留足长尾余量。
        # 【调大后果】下游 hang 住时调用方等待更久，线程池与连接池被占满的时间成比例变长。
        # 【调小后果】下游一次 GC 停顿就会触发超时，业务失败率上升（写接口超时还可能触发重试）。
        connectTimeout: 2000
        readTimeout: 5000
```

**必须标注「取值依据」的四类配置**：

| 类别 | 必须说明 | 本仓库示例 |
|---|---|---|
| **超时** | 依据 + 调大/调小后果 | `spring.rabbitmq`、`feign.client.config`、`spring.redis.timeout` |
| **线程池** | 并发模型 + 拒绝策略后果 | `cacheRebuildExecutor`（4 线程 + CallerRunsPolicy：队列满时由请求线程执行，会抬高接口 RT） |
| **缓存过期** | 依据 + 与业务容忍度对齐 | `llmall.shop.cache.ttl-minutes`（逻辑过期中值 + 物理额外余量） |
| **令牌/幂等 TTL** | **与关联生命周期对齐的计算过程** | 全量会话失效水位、支付锁 TTL |

**不得把可被覆盖的值写死进注释**：`llmall.jwt.tokenTTL` 能被环境变量覆盖，
写「（30 分钟）」会在配置变更后变成**一条错误的注释**。要写不会漂移的表述，或用 `{@code ...}` 指路。
反过来，**稳定的领域事实必须写**：金额单位「分」、状态字典值、key 前缀语义。

### 2.6 Lua 脚本注释

Lua 传参是**位置参数**，没有任何类型与语义校验，注释是唯一的防错手段。

头部必须包含五段：

```lua
--[[
  {脚本用途一句话}

  【为什么必须用 Lua】{原子性理由：Java 侧多条命令之间存在时间窗}

  【返回值约定】业务分支用返回值表达，不用异常：
    0 = 预扣成功；1 = 库存不足；2 = 该用户已抢购过

  【fail 策略】{读不到库存一律当没库存（fail-closed）/ 读不到按放行（fail-open）}，以及为什么

  KEYS[1] {键名}  {值语义，例如「剩余可抢数」}
  ARGV[1] userId
  ARGV[2] **总名额**（不是剩余量！）
          语义：该券可发放的总数量，由 Java 侧计算 = DB 剩余量 + DB 已发放行数
          单位：张    取值：>= 0 的整数字符串
          【误传后果】传「剩余量」会让脚本少放库存甚至夹到 0，导致库存永久归零
]]
```

三条硬约束：

1. **口径相同才能同名**：不同语义的参数绝不能用 `initStock` 这类含糊名字（本仓库已把 `initStock` 改名为 `totalStock`，让「总名额」这一口径在变量名上自证）。
2. **多副本必须互相引用**：同一规则在不同脚本/语言里有副本时，注释必须写明「与 XXX 是同一套规则的两个副本，改一处必须同步另一处」。
3. **fail 策略必须写明**：否则后人会以为是漏判而「顺手修掉」，直接把防超卖改成超卖。

### 2.7 SQL 迁移脚本注释

**读者**：DBA 与运维。头部**六段缺一不可**：

| 段 | 内容 |
|---|---|
| 一、功能 | 这个变更做什么（一句话） |
| 二、背景 | 为什么需要它（真实故障或缺陷现象） |
| 三、影响面 | 影响哪些表/数据/账号；哪些**不受影响**（同样重要） |
| 四、执行步骤 | 编号步骤，标出哪一步**不可跳过** |
| 五、前置依赖 | 依赖哪些脚本/应用版本；**顺序反了会怎样** |
| 六、回滚方案 | 可执行的还原语句；无法回滚必须写明「不可逆」及理由 |
| 附、风险等级 | 高 / 中 / 低 —— 依据是「改错后能否自动恢复」 |

**幂等守卫统一写法**（本仓库既有约定）：

```sql
SET @c := (SELECT COUNT(*) FROM information_schema.COLUMNS
           WHERE TABLE_SCHEMA = 'llmall-user' AND TABLE_NAME = 'user'
             AND COLUMN_NAME = 'pay_password');
SET @s := IF(@c = 0, 'ALTER TABLE ...', 'SELECT ''已存在，跳过''');
PREPARE st FROM @s; EXECUTE st; DEALLOCATE PREPARE st;
```

**执行顺序**必须与 `sql/merged/README.md` 保持一致；新增脚本要同步更新该 README 的顺序表。

### 2.8 TODO / FIXME

**问题**：`// TODO: 以后优化` 这类注释没有责任人也没有截止时间，实际等于技术债的坟墓 ——
既不会有人做，也没人敢删（怕删掉别人要做的）。

固定格式：

```java
// TODO({责任人}, {yyyy-MM-dd}): {问题描述} —— 触发条件：{什么时候必须做}；不做后果：{会怎样}
// FIXME({责任人}, {yyyy-MM-dd}): {缺陷描述} —— 影响面：{谁受影响}；临时规避：{当前怎么绕}
```

实例：

```java
// TODO(zhangsan, 2026-03-31): 全量会话失效水位用 Redis 承载，多机房部署时会各写各的
//   —— 触发条件：上线第二机房时必须改为共享存储或按机房收敛
//   —— 不做后果：跨机房请求读到本机房水位，导致「改密后另一机房旧令牌仍可用」
```

| 约束 | 说明 |
|---|---|
| 责任人必填 | 写真实能负责的人；不写等于没写 |
| 截止时间必填 | 用绝对日期（`2026-03-31`），不要写「下个迭代」 |
| 必须写触发条件 | 让后人知道「什么情况下必须做」，而不是靠猜 |
| **不允许裸 TODO** | 评审阶段 grep 出 `TODO(` 之外的 `TODO` 一律要求补齐 |
| 无信息量的直接删 | 例如「TODO: 优化」—— 要么补全，要么删掉 |

## 三、分模块优化重点

每个模块都有**必须写清、且最容易被改错**的一组口径。逐条核对，缺哪条补哪条。

### 3.1 公共模块（llmall-common / llmall-api）

| 主题 | 必须写清的内容 |
|---|---|
| **JWT 四段闭环** | 签发 → 校验 → 吊销 → 清理四段的职责边界与调用点；access 与 refresh 的分工；**旁路禁令**（`parseAllowExpired` 之类的放宽方法严禁用于鉴权路径） |
| **幂等键统一规则** | 键的构成（业务前缀 + 业务主键 + 口径区分）、为什么必须服务端产生、集中定义在哪（`IdempotentKeys`），**禁止各处手拼** |
| **埋点规范** | `BizTrace` 的字段口径（业务号/事件类型/耗时），埋点缺失时的降级行为，禁止在埋点里吞异常 |
| **全局异常处理策略** | `CommonException` 系 → 400；`IllegalStateException`/`RuntimeException` → 兜底 500。**为什么不统一成业务异常**：它们承载的是「消息体序列化失败」「未注册的消息类型」「ES 检索失败」这类基础设施错误，统一会把 500 变 400、掩盖真实故障 |
| **Feign 配置** | 禁用自动重试的原因（写操作重试 = 重复扣款风险）；超时取值依据；fallbackFactory 与「下游真不存在」必须可区分 |

### 3.2 用户模块（llmall-user-service）

| 主题 | 必须写清的内容 |
|---|---|
| **口令职责分离** | `password` 列同时承担登录密码与余额支付密码的现状；为什么不能只改一处；未来拆分时的迁移路径 |
| **弱口令分层拦截** | 分层边界（长度/字典/与用户名手机号相似度）各自拦什么；哪一层是**兜底不可省** |
| **改密校验成本排序** | 校验顺序为什么这样排（先廉价后昂贵），顺序反了会带来什么（放大攻击面 / 浪费资源） |
| **会话失效水位** | 水位的作用（一次改密让全部旧 access 失效）；与 `tokenTTL` 的倍数关系；**关联配置改了它必须同步改** |
| **验证码与日志** | 验证码明文写日志必须受开关约束（默认关闭），生产走真实短信通道 |

### 3.3 支付模块（llmall-pay-service）

| 主题 | 必须写清的内容 |
|---|---|
| **三态模型语义** | `PaymentLiability`（未提交 / 待支付 / 已关闭 / 成功，含「未知」态）每一个取值的含义；**为什么不能再用 boolean**（未知 ≠ 未支付） |
| **订单维度幂等** | 幂等键为什么按订单维度而不是按请求；重复支付的裁决点在 DB 条件更新还是唯一键 |
| **对账为什么不自动修正** | 自动修正需要下游「按业务号查流水」的能力，当前不具备；因此对账只报告不修改，人工介入的触发条件是什么 |
| **补偿与回滚** | 扣款成功但后续失败时的回滚链路；`faultInjectAfterDeduct` 这类故障注入开关**必须隔离在生产之外**，并写明误开的后果 |

### 3.4 营销秒杀模块（llmall-promotion-service）

| 主题 | 必须写清的内容 |
|---|---|
| **预热与扣减分离** | 为什么把库存预热与运行时扣减拆成两条路径；两条路径的库存口径必须一致 |
| **库存口径警示** | Java 传给 Lua 的是「总名额」；Lua 内部按 `总名额 - 已发放` 引导。**两侧注释都要写口径**，并注明「改一处必须同步另一处」 |
| **多副本同步** | `seckill.lua` 与 Java 侧 `BOOTSTRAP_SCRIPT` 是同一套夹取规则的两个副本 |
| **领券幂等键** | 领券与秒杀的幂等键为什么要拆开（口径不同、并发窗口不同）；用户维度与券维度的约束分别由谁保证 |
| **失败语义** | 库存不足 / 已抢购 / 系统繁忙 三类返回值与异常的分工 |

### 3.5 网关与 Feign（llmall-gateway / llmall-api）

| 主题 | 必须写清的内容 |
|---|---|
| **鉴权步骤** | 放行白名单 → 令牌解析 → 状态校验（是否被吊销）→ 注入用户头，四步的顺序与各自失败时的响应；**顺序调换会打开什么漏洞** |
| **降级策略** | Redis 不可用时是 fail-open 还是 fail-closed，以及该窗口内「已注销/被踢的令牌仍可用」这一后果必须写明 |
| **内部调用凭证** | 哪个头是可信的内部凭证，哪个头**不能**用来判内部调用（网关注入的用户头拿它判等于没判） |
| **禁用自动重试** | Feign 默认会重试，写操作重试 = 重复扣款；配置放在哪里、为什么放在 api 模块集中管 |
| **链路追踪** | traceId 的产生点与透传规则（哪些头必须原样透传、哪些必须剥离） |

### 3.6 其余业务模块（cart / item / shop / content / search / trade）

按同一套标准核对：**类注释是否落到业务、方法注释是否写了入参约束与异常、行内注释是否只出现在五类位置、风险点是否写了误改后果**。
重点核对三类高频问题：

1. **类注释写错表名/职责**（生成器模板残留）。
2. **注释描述与实现不符**（例如注释说「刷新的是最新价」而实现用的是请求体快照）。
3. **注释声称的能力实际不成立**（例如注释说「未建索引时按 engine 回落」，而实际语义已变）。

### 3.7 配置与脚本

- **YAML**：四类核心参数（超时/线程池/缓存 TTL/令牌 TTL）必须有「取值依据 + 调大调小后果 + 关联配置」。
- **Lua**：每个 ARGV 的语义/单位/取值范围 + fail 策略 + 历史缺陷警示。
- **SQL**：六段式 + 风险等级；执行顺序与 `sql/merged/README.md` 对齐。
- **运维脚本（.ps1/.sh）**：文件头写清用途、前置依赖、幂等性、失败后果；危险操作（删 key、重建索引、改配置）必须有二次确认或 `-Force` 之类的显式开关说明。

## 四、禁止的注释写法

| 反例 | 问题 |
|---|---|
| `// TODO: 以后优化` | 无信息量；要么写清触发条件，要么删掉 |
| `// 这里加了锁保证并发安全`（实际没加锁） | **注释与实现不符**，比没有注释更危险 |
| `// 历史上这里是这样写的…` / `// 改前是…` | 描述已不存在的实现，误导按注释改代码的人 |
| `// 用户不存在与密码错误返回同一句提示`（代码已按类型区分） | 过期注释，必须同步删除或修正 |
| 复制粘贴的注释块（同一段出现在多个不相关方法上） | 批量操作残留，掩盖真实意图 |
| 注释掉的大段死代码 | 用版本控制保留，不要留在源码里 |
| `<h3>` / `**粗体**` / `// ===== 分隔线 =====` | 源码注释不渲染 Markdown，见 §1.1 |
| 把可配置项的值写死（「（30 分钟）」） | 配置改了就变成一条**错误的注释** |

## 五、验证方式（三道闸门，缺一不可）

「只改注释」这句话不能靠人工核对来担保，每次改动都要过闸门。

| 闸门 | 证明什么 | 命令 |
|---|---|---|
| **① 指纹闸门** | 代码逐 token / 逐行未变 | `pwsh -File D:\dsh\.verify\comment-opt\gate.ps1 <相对路径...>` |
| **② 内容质量闸门** | 该删的确实删干净了（HTML/粗体/历史叙述/口语化/横幅） | `pwsh -File D:\dsh\.verify\comment-opt\lint-comments.ps1` |
| **③ 编译闸门** | 改完仍可构建（13 模块） | `pwsh -File D:\dsh\.verify\comment-opt\accept.ps1` |

**指纹闸门的原理**：用状态机扫描源码并剔除注释（正确处理字符串/字符字面量里的注释符号），对每个文件算两个指纹 ——

- **FP1（token 流）**：保留全部代码字符、压缩连续空白后取 SHA-256。对换行与缩进不敏感 → 相同即「代码语义逐 token 未变」。
- **FP2（代码行序列）**：剔除注释后逐行 `trimEnd`、丢弃空行后取 SHA-256。对格式敏感 → 相同即「连换行与书写形态都没动」。

基线文件（2026-10-15 本轮优化前）：

| 文件 | 覆盖 |
|---|---|
| `baseline/java.round2.txt` | 280 个 Java 文件 |
| `baseline/yaml.round2.txt` | 41 个 YAML 文件 |
| `baseline/any.round2.txt` | 38 个 Lua/SQL/PS1/SH/JS/Dockerfile 文件 |

**闸门自身踩过的坑（保留在此，防止后人重蹈）**：

1. **带误报的闸门比没有闸门更危险** —— 初版把「供**本次**请求的日志使用」这类正常中文判成违规，会诱导出错误的「修复」。
2. **必须区分 Markdown 强调与代码通配符**：`/**`（JavaDoc 起始符）、`/items/**`（AntPathMatcher glob）、`138****1234`（手机号掩码）都不是粗体标记。
3. **注释符长度必须按实际长度比较**：剥离器若固定拿 2 个字符去比对，`--[[`（4 字符）会被误当成行注释 `--`、`#`（1 字符）则永远比不中 ——
   结果是「块注释内部的行」与「`#` 注释行」被算成代码行，改注释反而被判成「代码被改动」，闸门从保护变成阻碍。
   这两处已在 `gate.ps1` 修掉，重写工具时务必保留长度比较。
4. **批量替换必须限定在注释行内**：用全文件正则替换 `**粗体**` 时，`echo "…以**从库**身份回归…"` 这类**脚本输出文案**会被一起改掉（属代码行）。
   正确做法是逐行判断「行首是否为该语言的注释符」再替换；闸门会拦下误伤，但不要依赖它兜底。
