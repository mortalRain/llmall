# 核销越权修复与门店员工判权（2026-10-26）

> 一句话：`POST /orders/verify` 以前只校验"登录 + 核销码存在 + 门店一致"，**任何登录用户拿到核销码都能核销**；
> 现在由**交易域强制**校验"调用者是该订单门店的在岗员工"，非员工返回 **403**，门店服务不可用时**按拒绝处理**（fail-closed）。

## 一、问题与影响

| 项 | 修复前 | 修复后 |
|---|---|---|
| 谁能核销 | 任意登录用户（知道/猜到核销码即可） | 仅该订单所属门店的员工（`shop_staff` 有 `(shop_id, user_id)` 行） |
| 权限在哪校验 | 无 | 交易域 `OrderServiceImpl#verifyOrder` → 门店域内部接口 `GET /internal/shops/{shopId}/staff/{userId}` |
| 非员工响应 | 200（订单被核销） | `403 {"code":403,"msg":"仅门店员工可核销","data":null}`，订单状态不变 |
| 门店服务不可用 | — | `403 {"code":403,"msg":"暂时无法核销：门店员工校验不可用，请稍后重试","data":null}`，**不会放行** |

影响面：核销是"券已使用"的终态，直接决定门店结算与用户资产。越权核销可把别人的券核掉、把门店的结算单做错，
且无法通过退款完全恢复（券状态、核销时间、核销事件都已落库/投递）。

## 二、设计（为什么这么落）

### 1）员工关系落库：`llmall-shop.shop_staff`

```sql
CREATE TABLE IF NOT EXISTS `shop_staff` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `shop_id`     BIGINT UNSIGNED NOT NULL,
  `user_id`     BIGINT UNSIGNED NOT NULL,
  `role`        VARCHAR(16)     NOT NULL DEFAULT 'STAFF',
  `create_time` TIMESTAMP       NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_shop_user` (`shop_id`, `user_id`),
  KEY `idx_user` (`user_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

- **多对多**：一个人可以在多家门店任职（演示账号 Jack 就是 1 号与 10 号店的 STAFF），`user` 表上的单值角色字段表达不了。
- **只认 `user_id`**：`user_id` 是跨库逻辑外键（`llmall-user.user.id`）；用户名可改，不能作为权限依据。
- **不加物理外键**：用户域与门店域是两个库、两个服务，物理外键会让用户域删号被门店域锁死。
- **不缓存判权**：每次核销实时查唯一键（一次索引命中）。员工离职/调店必须"改完即生效"，
  缓存会把撤权延迟到 TTL 过期。撤销权限 = `DELETE FROM shop_staff WHERE ...`，无需重启。

脚本：`sql/merged/32-shop-staff.sql`（幂等：`CREATE TABLE IF NOT EXISTS` + `INSERT IGNORE`）。
种子先按 `username = 'Jack'` 查真实 `user_id` 再插，**不写死 1**；查不到 Jack 时插入 0 行（宁缺勿错）。
本次演示库实际落库：`user_id = 1`，`shop_id = 10` 与 `shop_id = 1`，`role = STAFF`。

### 2）门店域：内部判权接口

```http
GET /internal/shops/{shopId}/staff/{userId}
x-service-token: <LLMALL_SERVICE_TOKEN>
→ true / false
```

- 与交易的 `PUT /orders/{id}`（标记已支付）同一套内部鉴权：只认 `llmall.internal.service-token`，
  **配置缺失时同样拒绝**（fail-closed）。`x-internal-token` 不能用来判内部调用——网关会给每个登录用户注入它。
- 网关路由表里没有 `/internal/**`（实测经 8080 访问返回 404），外部到不了；即使将来误加路由，
  该头也只由服务间 Feign 携带，网关对客户端版本只剥离、不注入。
- 返回布尔值而不是抛异常：调用方要区分"不是员工"（业务拒绝）与"门店服务不可用"（基础设施故障，
  同样拒绝但要打 ERROR 归因）。

代码：`llmall-shop-service/.../controller/InternalShopController.java`、
`service/impl/ShopStaffServiceImpl.java`、`domain/po/ShopStaff.java`、`mapper/ShopStaffMapper.java`。

前端展示用接口（只读、需登录）：

```http
GET /shops/my/staff → ["10","1"]
```

它只是"是否展示核销入口"的开关，**不是权限边界**：真正的拦截在交易域。

### 3）交易域：核销前强制判权

`OrderServiceImpl#verifyOrder` 的校验顺序（顺序即安全边界）：

1. 入参（码/门店）非空 → 2. 按码查订单（命中多单直接拒绝）→ 3. **订单门店 == 核销门店**（否则 403）
→ 4. **调用者是该门店员工**（否则 403）→ 5. 订单状态必须是 2 → 6. 条件更新 2→7 + 投递核销事件。

- 判权放在状态判断**之前**：避免无权限者用错误文案探测"这个码是否已付款/已使用"。
- 门店取自**订单**（权威值），不取请求参数（此时已校验一致）。
- 调用者身份取自 `UserContext`（网关注入的 `user-info`，只在 `x-internal-token` 匹配时采信）。

**fail-closed 的三条路径**（缺一不可）：

| 路径 | 结果 |
|---|---|
| `isStaff` 返回 false | 403 `仅门店员工可核销` |
| 门店服务超时/不可用 | 403 `暂时无法核销：门店员工校验不可用，请稍后重试` + ERROR 日志 |
| 降级方法抛出的异常 | 同上（见下方位） |

> **坑（实测）**：`feign.sentinel.enabled=true` 时，`SentinelInvocationHandler` 用反射调用
> `fallbackFactory` 生成的降级对象，把降级方法抛出的异常**包成 `AssertionError`**（`Error` 不是 `Exception`）。
> 只 `catch (Exception)` 会漏掉它，冒到全局兜底变成 `400 请求参数处理异常`——语义上仍是"拒绝"，
> 但文案完全误导。因此 `assertStaffOfOrderShop` 显式 `catch (RuntimeException | AssertionError)`，
> 并有单测 `sentinelWrappedAssertionErrorFailsClosed` 锁定这一行为。

### 4）前端：顾客出示、员工核销

核销是**门店员工**的动作，不是顾客的动作。前端把两端分开：

- **顾客侧（`Orders.vue`）**：订单卡片与详情**突出展示核销码**，文案"到店出示给店员核销"；
  **没有任何"去核销"按钮**。顾客能做的只有出示核销码（以及未支付时取消订单）。
  之前把核销按钮放在顾客订单操作里，等于在产品上暗示"用户能自己核销"，是把越权漏洞产品化。
- **员工侧（`StaffVerify.vue`，路由 `/staff/verify`「核销台」）**：
  - 入口按员工身份展示：`AppLayout` 拉 `GET /shops/my/staff`，非空才在导航里出现"核销台"；
  - 页面自身再校验一次：空列表 → 显示"仅门店员工可使用核销台"，不渲染表单；
  - 表单只有两项：**核销门店**（从任职门店里选）+ **核销码**，提交 `POST /orders/verify`；
  - 成功显示订单号与"核销成功"，失败（403/400）把服务端 `msg` 同时显示在 alert 与消息条里。
  - 接口失败按空集合处理（fail-closed）：查询失败不等于有权限。
- **演示账号**：Jack 同时是 1 号与 10 号店员工，所以同一个账号既能演示"顾客出示核销码"，
  也能在导航看到"核销台"演示员工侧核销。

> 前端所有判断都只是 UX。真正的权限边界仍在交易域：即使手敲 `/staff/verify`、伪造
> `/shops/my/staff` 的返回，非本店员工调 `POST /orders/verify` 依然 403。

## 四、上线与回滚

- **上线顺序**：先跑 `32-shop-staff.sql`，再发布 shop 与 trade 服务。反了也不会 fail-open，
  但所有核销都会被拒绝（`shop_staff` 不存在 → 判权失败）。
- **生产种子**：`32` 的种子段仅演示库需要；生产只执行建表段，按真实员工关系 `INSERT`。
- **回滚**：应用回退到旧版本后再 `DROP TABLE llmall-shop.shop_staff`；只撤某人权限请删行（即时生效，无需重启）。
- **未做/边界**：
  - 没有 RBAC：`role` 字段当前只作扩展（STAFF/MANAGER 同等放行），细粒度权限（如"只有店长能退大额单"）未实现。
  - 没有员工管理界面/接口：员工关系目前只能通过 SQL 维护。
  - 判权不做缓存，核销会多一次跨服务调用（唯一键查询，毫秒级；门店服务故障时核销不可用，这是有意的取舍）。
  - 前端 `GET /shops/my/staff` 只用于展示；伪造它不会带来任何权限。
