## 2. 改了什么

### 2.1 消息表设施：三份复制 → 一份基类（-217 行）

`MessageLogServiceImpl`（194/214/191 行）、`MessageRetryTask`（39/36/33 行）、`IMessageLogService`（30/35/36 行）
在内容域、门店域、交易域各存一份，代码相似度 **66% ~ 81%** —— 已经是"改一处忘两处"的状态。

收敛为 `llmall-common` 的四个文件：

| 文件 | 作用 |
|---|---|
| `MessageLogSupport` | 行契约（12 个字段访问器 + 4 个状态字典常量） |
| `IMessageLogService<M>` | 操作契约（record / dispatchAfterCommit / dispatch / retryPending / compensate / markDone） |
| `AbstractMessageLogService<M, MP>` | 全部投递、退避重试、对账补偿、序列化逻辑 |
| `AbstractMessageRetryTask<M>` | 定时重试任务（`@Scheduled` 与批大小统一） |

各服务只保留"自己的 PO + 自己的消息类型登记"，约 20 行。

**为什么可以共用列名**：三张 `message_log` 的列名、类型、状态字典完全一致
（`02-shared-infra.sql` / `05-shop-message-log.sql` / `06-content-message-log.sql`），
基类因此统一按列名读写。**代价与约束**：任一服务单独改列名会静默查不到数据，已在基类注释中写明。

**顺带修掉的重复**：`retryPending(50)` 里的 `50` 原本硬编码在三处。

### 2.2 JWT 实现：两份漂移中的副本 → 一份共享（-120 行）

`JwtTool`（网关 99 行 / 用户服务 113 行）与 `JwtProperties`（各 21 行）在两个服务各存一份，
`SecurityConfig` 相似度 **92.6%**。

**这不是普通的重复，而是已经发生的漂移**：两份 `JwtTool` 的代码差异只有一处 ——
用户服务版在 `readExpiresAt` 里有 `if (exp == null) return null;`，**网关版没有**。
签发与验签各持一份实现，任一方改动都可能让另一方签发的令牌验不过，表现为"登录成功但所有接口 401"。

收敛为 `llmall-common` 的 `JwtTool` + `JwtProperties`（取含空判断的版本）。
各服务的 `SecurityConfig` 以 `@Bean` 暴露 `JwtTool` —— 因为 `@SpringBootApplication` 只扫描
`com.llmall.<服务>`，common 里的 `@Component` 不会被发现；用 `@Bean` 而非自动装配，
是为了避免"条件装配没命中导致服务启动失败"这类无法在本机验证的风险。

**为什么 `SecurityConfig` 本身没有合并**：它的 `keyPair` Bean 依赖 `KeyStoreKeyFactory`
（`spring-security-rsa`），该依赖在两个服务里都是**传递引入**、pom 未显式声明；
给 `llmall-common` 添加它会引入版本管理风险，收益（约 15 行）不抵风险。

## 3. 审计过但**决定不改**的

| 项 | 相似度 | 为什么不动 |
|---|---|---|
| `ConsumeRecord` PO ×4、`MessageLog` PO ×3 | 62 ~ 65% | **架构正确**：微服务"一服务一库"要求每个服务持有自己库的 PO，合并到 common 会耦合各服务的表结构 |
| `ShopDocChangedEvent` ×2 | 54% | 契约模块 + 消费端镜像类是有意为之（事件契约的跨服务副本） |
| `ContentEventPublisher` / `ShopEventPublisher` / `OrderEventFactory` | 低 | 各自领域的事件与逻辑不同；`OrderEventFactory` 甚至是另一种职责（构造事件而非发布），强行合并是过度设计 |
| `ShopSearchReconcileTask` / `OrderReconcileTask` | 结构平行 | 共享的只有几个常量与一个 `DownstreamState` 枚举，业务逻辑差异大，抽取基类的收益低于复杂度 |
| `PayStatus.equalsValue` / `PayType.equalsValue` | 完全相同 | 抽一个带 default 方法的接口：新增 12 行、减少 12 行，**净收益为零**，不值得引入抽象 |
| `gateway` / `user-service` 的 `SecurityConfig` | 92.6% | 见 §2.2 —— 合并需要给 common 增加传递依赖，风险大于收益 |

## 4. 验证方式

本轮的改动**改变了代码本身**，因此"去注释指纹"不再适用，改用：

1. **全量编译**：每一批改动后都跑 13 模块离线编译，全程 BUILD SUCCESS；
2. **行为等价性**：抽出的逻辑是从原实现**逐语句搬运**，未重写（`record` 的同事务语义、
   `dispatchAfterCommit` 的 afterCommit 注册、退避公式 `5 * 2^retry` 上限 600s、
   `getOne(wrapper, false)` 的"多结果不抛异常"等口径逐条保留）；
   `AbstractMessageLogService` 的 `record`/`dispatch` 等公开方法继承自基类，
   Spring 的 `@Transactional` 与 `@Scheduled` 对继承方法同样生效；
3. **注释质量闸门**：新增代码必须符合同一套注释风格，`lint-comments.ps1` 的 11 条规则全部 0 处；
4. **可回滚**：改动前快照在 `.verify/comment-opt/pre-codeopt/`，可与当前逐文件 diff。

**未做运行时验证**：可靠消息、JWT 签发/验签要跑起来需要 Nacos + MySQL + Redis + RabbitMQ + 启动 10 个服务，
本机未做。上述等价性是**静态保证**，若要在本机确认，最直接的是跑 `scripts/MallE2E.java`（覆盖下单→支付→核销全链路）
与 `scripts/verify-auth.ps1`（覆盖登录→鉴权→注销→无感刷新）。
