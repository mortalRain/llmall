# P-02 容量测试与建议阈值：GET /items/page（2026-10-17）

> **状态：停点 —— 只给容量曲线与建议阈值，正式默认值全程未改，等拍板最终值。**
> 压测时把 `llmall.sentinel.item-page-qps` 用**临时覆盖文件**抬到 10000（文件写在仓库树**之外**，见第三节），
> 压完已用不带覆盖文件的重建把 item-service 恢复到正式默认 **200**，并复测确认（见第五节）。

## 一、结论先说

| 项 | 值 |
|---|---|
| **真实容量（拐点）** | **≈1400~1500 rps**：30 并发已达 1477 rps，50 并发只有 1521 rps（再往上加并发不再换来吞吐） |
| **P99 开始恶化的位置** | **≈1300 rps**：1280 rps 时 P99=11 ms，1477 rps 时 P99=34 ms（**3 倍**），此时吞吐只涨了 15 % |
| **下游 MySQL 出现压力的 QPS** | **本轮未出现**：最高 3042 条 SELECT/s 时 `Threads_running` 峰值只有 **3~7**、行锁等待 **0** |
| **真正的天花板** | **宿主 CPU**（被测容器与 JMeter 同机抢 16 个物理核）：t10 63 % → t30 81 % → t50 84 %，再往上先撞内存 90 % 熔断 |
| **建议阈值（= 容量 × 70~80 %）** | **1000 QPS（70 %，保守）**，或 **1120~1200 QPS（80 %，激进）** —— 见第四节 |
| 现正式默认值 | **200 QPS** = 容量的 **13 %**，明显偏保守（它是"安全阀"，不是按容量调的） |

**一句话**：把限流拿掉之后，这个接口在本机同构环境里的容量约 **1500 rps**，而 `MySQL` 完全不是瓶颈；
所以"商品列表容量 = 限流阈值"这个台账判断**成立但被低估了 7 倍** —— 现在有了可对标的数字。

### 同一档位的应用侧与 DB 侧读数（每档压测开始/结束取指标增量）

| 并发 | 每请求 SQL（`Com_select` ÷ 请求数） | 连接池上限 | 在用连接峰值 | 排队线程峰值 | 平均等连接 | 平均占用连接 | MySQL `Threads_running` 峰值 | 行锁等待增量 |
|---|---|---|---|---|---|---|---|---|
| 10 | **2.00** | 5 | 5 | 0 | 0 ms | 2 ms | 3 | 0 |
| 30 | **2.00** | 5 | 5 | 19 | 10 ms | 3 ms | 3 | 0 |
| 50 | **2.00** | 5 | 5 | 39 | 22 ms | 3 ms | 3 | 0 |
| 70 | 2.01 | 5 | 5 | 56 | 18 ms | 3 ms | 3 | 0 |
| 100 | 2.01 | 5 | 5 | 89 | 29 ms | 3 ms | 3 | 0 |

三条硬读数：
1. **每请求 SQL 恒为 2.0 条**，与并发无关 —— 与台账里测到的口径一致（`/items/page` 无 N+1）；
2. **MySQL 侧毫无压力**：3000 条 SELECT/s 时只有 3 个线程在跑、行锁等待 0。**容量拐点不是 DB 造成的**；
3. **item-service 的连接池（上限 5）从 10 并发起就被占满**（在用恒为 5），排队线程随并发线性增长（19→39→89）。
   它抬高了延迟，但不是本轮吞吐天花板（按 Hikari 指标：平均每次占用 2.55 ms、5 条连接理论上限 ≈1960 ops/s，
   实测 1521 rps 已接近该上限；真正先撞墙的是宿主 CPU 与内存）。

## 三、怎么测的（可复现）

### 1. 临时调高阈值（不改任何正式配置）

覆盖文件写在**仓库树之外**（`$env:TEMP`）。理由：仓库内的 `.yml` 会被 `YamlFingerprint` 判成"新增未纳入基线的配置文件"，
而一个只用于本次压测的临时文件**不该进基线** —— 基线是项目代码的证据，不是压测脚本的证据。

```powershell
$override = Join-Path $env:TEMP 'p02-override-item-qps.yml'
@'
services:
  llmall-item-service:
    environment:
      JAVA_OPTS: "-Xms64m -Xmx192m -XX:MaxMetaspaceSize=128m -XX:+UseSerialGC -XX:TieredStopAtLevel=1 -Dspring.jmx.enabled=false -Dfile.encoding=UTF-8 -Dserver.shutdown=graceful -Dspring.lifecycle.timeout-per-shutdown-phase=30s -Dllmall.sentinel.item-page-qps=10000"
'@ | Set-Content -Encoding UTF8 $override

# 用 base + 覆盖文件重建 item-service（不写进 deploy/docker-compose-apps.yml、也不写 Nacos）
cd deploy
docker compose -f docker-compose-apps.yml -f $override --profile full up -d --no-deps --force-recreate llmall-item-service
# 启动日志确认生效：
docker logs llmall-item-service | Select-String '最小规则集'
# → [Sentinel] 最小规则集已加载: flow=1 条（itemPage QPS=10000.0）, degrade=1 条（...）
```

> 为什么用覆盖文件而不是改 Nacos：阈值在 `SentinelRuleConfig#loadMinimalRules` 里 `@PostConstruct` 静态注册，
> 改 Nacos 也要重启才生效，口径上还不如直接给启动参数；而且改 Nacos 属于"动别人的环境"。

### 2. 只压这个接口的计划

`logs/task2/items-page-only.jmx` 是从 `benchmark/read-c01-feed.jmx` 里摘出来的（去掉 setUp 登录与 `/follows/feed` 线程组，
理由：`/items/page` 走网关只读白名单、不需要令牌；content-service 本轮已为腾内存停掉，留着那条采样器只会把错误率染红）。

```powershell
$env:JAVA_HOME='<JDK11>'
foreach ($t in 10,30,50,70,100) {
  pwsh -File benchmark\bench-guard.ps1 -Jmx logs\task2\items-page-only.jmx -Tag "p02-items-t$t" `
       -Threads $t -Duration 60 -Ramp 10 -CooldownSeconds 15 -SkipLogin `
       -JmeterHome <jmeter-home> -JavaHome <JDK11> -OutDir logs\task2
}
```

一键脚本：`pwsh -File logs\task2\p02-capacity.ps1`（把上面循环 + 每档的 Hikari / MySQL 指标增量一起采）。

## 四、建议阈值（**待你拍板，我没有动正式值**）

判据：**建议阈值 = 实测容量 × 70~80 %**

| 取法 | 计算 | 建议值 | 说明 |
|---|---|---|---|
| 保守（70 %，我推荐） | 1400 × 70 % ≈ 980 | **1000 QPS** | 把 triples 的 P99 恶化留在阈值之外；留出"其它接口共享同一连接池/CPU"的余量 |
| 激进（80 %） | 1500 × 80 % = 1200 | **1200 QPS** | 已到 P99=34~61 ms 的区间，突发时更容易排队 |
| 现状 | 200 | 200 QPS | 容量的 13 %，安全但不经济 |

**为什么推荐 1000 而不是 1200**：本轮是"单接口接近独占整机"的口径（其中 5 个服务被停掉腾内存），
真实线上是全站共享，所以宁可取 70 % 那一档；而且 1000 已经是现状的 **5 倍**，一次调到位的风险大于收益。

### 上线前需要一并确认的三件事（不是建议，是前提）

1. **阈值的单位是"每实例 QPS"**：现在 item-service 单实例，1000 即整站 1000；将来多实例时总容量 = 实例数 × 阈值。
2. **同一台 MySQL / 同一个连接池是共享资源**：`/items/page` 拿掉限流后能吃掉整池 5 条连接，
   其它接口（含订单读）会跟着排队 —— 这也是"连接池上限 5"值得单独决策的原因（与 P-01 是同一个根因）。
3. **本机测不出更高容量**：70/100 并发两档被内存熔断掐断，若要把建议值抬到 1200 以上，
   需要先在更强机器或远程压测环境复测，不能在 16 GB 宿主机上继续加码（红线）。

## 六、停点：等你拍板的问题

1. **最终阈值定多少**？我推荐 **1000**（容量 70 %），备选 1200（80 %）或 500（更保守的第一档）。
2. **是否要我按定下来的值做一次"阈值生效"复测**？（50 并发压 60 秒，看放行 QPS 是否贴住新阈值、错误率里
   只有限流拒绝、没有业务失败）
3. **阈值要不要写进 Nacos 而不是继续用代码里的 `@Value` 默认值**？现在规则是启动时静态注册的，
   改值必须重启；若希望运行期可调，需要接 `sentinel-datasource-nacos`（那是新依赖 + 新配置面，需单独评估）。
4. **要不要同时把 P-01 的连接池上限一起决策**？这两条是同一个根因（池 5），分开调会出现
   "阈值抬了但池没抬，排队把 P99 又顶回去"的情况。

## 七、抬池验证后的复测（2026-10-17 第二轮，pool 5 → 20）

把 item-service 的池上限临时抬到 **20**（做法与踩坑见 P-01 文档第五·补节：外部启动参数改不动 Nacos 下发的键，
只能临时让它不引 `shared-jdbc.yaml`），限流仍临时抬到 10000，重跑同一套并发阶梯。**这一轮五档全部跑满 60 秒**
（上一轮 70/100 两档被内存熔断掐断）。

| 并发 | pool 5：吞吐 / Avg / P99 | **pool 20：吞吐 / Avg / P99** | 变化 |
|---|---|---|---|
| 10 | 1280.1 rps / 7.1 / 11 ms | **1223.2 rps / 7.5 / 11 ms** | 持平 |
| 30 | 1477.5 / 18.6 / 34 ms | **1550.1 / 17.6 / 36 ms** | 吞吐 +5 % |
| 50 | 1521.4 / 30.1 / 61 ms | **1521.4 / 30.0 / 65 ms** | 持平 |
| 70 | （熔断，无有效数据） | **1430.1 / 44.9 / 90 ms** | 越过拐点：吞吐下降、P99 上台阶 |
| 100 | （熔断，无有效数据） | **1400.4 / 65.5 / 145 ms** | 继续下降 |

连接池侧读数（pool 20）：

| 并发 | 在用连接峰值 | **排队线程峰值** | 平均等连接 | 平均用连接 | 每请求 SQL | MySQL `Threads_running` |
|---|---|---|---|---|---|---|
| 10 | 8 | **0** | 0 ms | 2 ms | 2.00 | 5 |
| 30 | 16 | **0** | 0 ms | 7 ms | 2.00 | 5 |
| 50 | 20 | 18 | 2 ms | 10 ms | 2.00 | 5 |
| 70 | 20 | 32 | 13 ms | 12 ms | 2.00 | 5 |
| 100 | 20 | 64 | 30 ms | 13 ms | 2.00 | 5 |

### 结论：**读路径抬池几乎无收益（+2 %），item 的天花板不是连接池**

- 30 并发档是唯一"池不再排队"（pending = 0）又有完整吞吐的档：**(pool 20) 1550 rps vs (pool 5) 1477 rps，只多 5 %**；
- 50 并发档两池的吞吐**完全一样**（1521.4 rps），P99 还略差（65 vs 61 ms）；
- 所以 item 的容量天花板 ≈ **1500~1550 rps**，卡在**宿主 CPU（81~87 %）与 MySQL 侧的 QPS**，
  不是应用侧的连接池 —— 这跟 P-01（写路径抬池 −47 %）是**相反**的结论；
- 顺带补上了上一轮缺的两档：**70 / 100 并发都在拐点右侧**（吞吐反而降到 1430 / 1400 rps，P99 升到 90 / 145 ms），
  说明"加并发换吞吐"在 50 并发之后已经失效。

### 据此修正的阈值建议（不变，但理由更硬了）

| 项 | 值 |
|---|---|
| 真实容量（pool 20 与 pool 5 同量级） | **≈1500~1550 rps** |
| P99 恶化起点 | **≈1300 rps**（再往上每加一档并发，P99 上台阶而吞吐不涨） |
| **建议阈值（容量 × 70~80 %）** | **1050~1200 QPS**；我仍推荐 **1000**（保守一档，也是现状 200 的 5 倍） |
| 抬池对阈值的影响 | **没有**：容量没变，所以阈值不必因抬池而上调 |

> **给 P-01 的联动**：抬池在写路径有收益、在读路径没有 —— 说明"全站统一抬池"不是个好主意，
> 该按接口类型分档（见 P-01 文档第六节的建议）。

## 八、阈值已落地：1000 QPS（2026-10-17 定稿）

按拍板把 `SentinelRuleConfig` 的默认值从 **200 改成 1000**（`@Value("${llmall.sentinel.item-page-qps:1000}")`），
字段注释写清取值依据（容量 1500~1550 rps × 70 %）。**该键 Nacos 里没有**，所以代码默认值即生效值，不需要 Nacos 配合。

### 落地验证（50 并发 × 60 秒，`logs/task2/items-page-only.jmx`）

| 项 | 值 |
|---|---|
| 启动日志 | `[Sentinel] 最小规则集已加载: flow=1 条（itemPage QPS=1000.0）` |
| 尝试吞吐 | 143,069 请求 / 60 秒 ≈ **2387 rps** |
| 放行 | 52,561 次 → 全窗平均 **876 rps**；**稳态（爬坡后）平均 940/s、峰值 1046/s**（秒边界允许略超阈值）；爬坡 3 秒内即到达 ≈1000/s |
| 被拒 | 90,508 次，全部 HTTP 400 |
| 被拒原因是否单一 | **是**：item-service 日志里 `业务拒绝 -> BizIllegalException，原因：商品列表访问过于频繁，请稍后再试` 命中 **90,508** 行，与 400 次数完全相等，没有任何其它错误类型 |
| 熔断 | 未触发（峰值 CPU 87 %、内存 76.5 %） |

> 结论：放行贴住 1000、拒绝全部来自限流 —— 阈值按预期工作。
> 稳态均值 940 略低于 1000 是几秒毛刺（宿主 CPU 87 %）拉下来的，不是限流多拒；单秒峰值为 1046，与 Sentinel 的秒级计数口径一致。

### 与抬池的关系（不变）

抬池对 item 容量只有 +2~5 %，所以**阈值不随池大小调整**；`item` 的连接池仍保持全局默认 5（本轮只抬了 pay）。
