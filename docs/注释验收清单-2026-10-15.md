## 四、分模块优化重点（对照需求逐条）

### 4.1 公共模块（llmall-common / llmall-api）

| 主题 | 是否写清 | 落点 |
|---|---|---|
| JWT 四段闭环（签发/校验/吊销/清理）与各自调用点 | ✅ | `JwtTool` 类注释；access 与 refresh 的分工与寿命关系 |
| **旁路禁令** | ✅ | `parseAllowExpired` 的【严禁】提到方法注释最上方，写明「用于鉴权路径等于取消令牌过期校验」 |
| 幂等键统一规则 | ✅ | `IdempotentKeys`：【键的构成】= 业务前缀+业务主键+口径区分；【为什么必须集中定义】= 手拼会导致的三类失效 |
| 埋点规范 | ✅ | `BizTrace`：【字段口径】【调用顺序】【降级行为】【边界约束】（禁止为让埋点跑完而吞异常） |
| 全局异常策略 | ✅ | `CommonExceptionAdvice`：【映射策略】+ **为什么不统一成业务异常**（会把 500 变 400、掩盖基础设施故障）+ 兜底【严禁】 |
| Feign 禁用自动重试 | ✅ | `NoRetryFeignConfig`：写操作重试 = 重复扣款/重复下单；为什么放 llmall-api 集中管；为什么用 `defaultConfiguration` |

### 4.2 用户模块（llmall-user-service）

| 主题 | 是否写清 | 落点 |
|---|---|---|
| 口令职责分离 | ✅ | `password`（登录口令）与 `pay_password`（支付口令）**两列各自的读写点**（login / changeLoginPassword / 自动注册 ↔ deductMoney / changePayPassword）、为什么两者强度要求相反不能合并、**跨列读写的误改后果**、`60-user-pay-password.sql` 两步迁移路径（ADD COLUMN 与 UPDATE 都不能跳过） |
| 弱口令分层拦截边界 | ✅ | 真实的三层收口（响应标记提示 / 登录硬拦截 / 支付入口拦截）、第 2 层是**兜底不可省**（唯一不依赖前端配合也不依赖资金动作）、并**显式写出边界**「判据只有是否等于初始口令，服务端不查字典、不比相似度」 |
| 改密校验成本排序 | ✅ | 频控 → 锁定 → 验证码 → bcrypt 比对，为什么先廉价后昂贵；顺序反了会让未过前两关的请求也触发 CPU 密集比对，放大撞库面 |
| 会话失效水位 | ✅ | 作用、**倍数关系与计算过程**（access 最大寿命 × 2 = 1 小时，2 倍用于吸收时钟偏差）、关联 `IdempotentKeys` 常量须成对改、不同步会出现「水位已过期而旧 access 未过期」的窗口 |
| 验证码与日志 | ✅ | **如实写明该行当前没有开关约束**（依据代码事实）、仅本地可接受、生产必须走真实短信通道、误开后果（任意手机号验证码进入日志采集链路） |
| Controller 契约（面向前端/运维） | ✅ | 类注释统一权限口径（仅 login / sms / code 三个接口匿名可访问），逐接口补【权限】【入参约束】【返回】【错误码】（400/401/403 各自触发条件）【影响面】 |
| PO 字典口径 | ✅ | `User` 状态字典与 `UserStatus`（0 冻结 / 1 正常）及 DDL 列注释逐值对齐，并写明写入枚举外取值的静默失效后果 |

### 10.1 闸门自身的缺陷（本轮修掉 3 处 —— 最值得记录的一段）
