# 能力缺口清单（2026-10-15）

> **为什么单独有这一份**：本轮注释工程化把若干处「注释声称存在、代码里没有」的表述改成了事实描述 ——
> 这是对的（注释必须与实现一致）。但**只改注释等于把缺口藏起来**：
> 那些被删掉的承诺里，有些是产品可能真的想要的能力。所以把它们显式登记，交给排期，
> 而不是让它们消失在一句被删掉的注释里。
>
> **来源**：`docs/注释验收清单-2026-10-15.md` 第六节的纠偏记录 + 各模块的核对结论。

## 一、真正的能力缺口（建议排期）

| # | 被声称的能力 | 代码实际 | 影响面 | 建议 |
|---|---|---|---|---|
| 1 | **「粉丝过多时改由读 Feed 时拉取合并」**（`BlogServiceImpl` / `FollowServiceImpl` / `IFollowService` 三处注释都这么写） | `pushToFollowers` 超过阈值**直接 return**（不写收件箱）；读路径 `queryFeed` **只查 feed_inbox（纯推模式）**，没有任何拉取合并分支 | 大 V 的粉丝**看不到该笔记**，且全程无提示、无告警 —— 只有对比"关注列表"才能发现 | 二选一：① 补拉模式兜底（取关注作者集合，对超阈值作者按时间查近 N 条 `status=1` 的笔记，与收件箱结果归并去重后分页）；② 若不补，则把阈值行为改成"仅推给活跃粉丝 + 打 WARN/指标"，**不要静默丢弃** |
| 2 | **热词 ZSet 是「滚动窗口」，旧热词不会永远压住新热词**（`SearchRedisConstants.HOT_WORD_TTL`） | 写入路径的 Lua 每次都 `pexpire` 续期 → **只要有搜索流量 key 就不过期**，score 恒为"自 key 建立以来的历史累计"；截断只砍成员数、不减分数 | ① 热搜榜长期被老词占据，新热词上不来；② `syncHotWordsToDb` 用绝对值覆盖写 `search_count`，把"7 天累计分"整份记成"今天"的量 → **按天报表口径必然偏大** | 若要真正的滚动窗口：改为按天分桶 key + `ZUNIONSTORE` 聚合近 7 天，或写入时对旧 score 衰减；落库改为"当日增量" |
| 3 | **「未建索引时检索按 `llmall.search.engine` 回落（auto → MySQL）」**（`ShopSearchIndexInitializer`） | 回落只在 `esGateway.search()` **抛异常**时触发；而 ES 对"索引不存在"很可能是 `200 + 0 条`（不抛错） | 新环境首次部署（或索引被误删后重建）：索引建出来了但**没有数据** → 检索**正常返回空列表、不回落 MySQL、不告警**，表现为"搜索页什么都搜不到"而 `engineStatus` 只提示 `esDocs:0` | ① `created == true` 时启动期自动触发一次 `reindexFromReadModel()`；或 ② 检索侧加"索引为空但读模型非空"的降级判定（须加 60s 缓存避免每次检索多一次往返）。**已实机验证（2026-10-17 压测，见 `benchmark/README.md` 与 `docs/已知偏差台账-2026-10-15.md` 第七节）**：§「索引被删（不存在）」→ ES 抛 `index_not_found_exception`，`engine=auto` **正常回落 MySQL**（`/search` 返回 `total=2`，日志有 `ES 检索失败，回落 MySQL 读模型`）—— 台账原猜测的这一半不成立；§「**索引存在但为空（0 条）**」→ ES 返回 `200 + 0 命中`，检索**静默返回空列表、不回落、不打 WARN**（`total=0, list=[]`），只有 `GET /search/engine` 显示 `esDocs:0, consistent:false` —— **缺口确认，且触发条件比原文更精确：不是"索引不存在"，而是"索引存在但为空"**。**已修复（2026-10-17）**：`SearchServiceImpl#doSearch` 对"命中 0 条"再判一次"索引为空且读模型非空"，是则回落 MySQL 并打 WARN；复测空索引下 `/search` 由 `total=0` 变为 `total=2`，负例（关键词无命中）仍为 0，空索引 50 并发 60 秒错误率 0% |
| 4 | **「评论有举报与屏蔽状态」**（`30-content.sql` 的 `blog_comments.status` 声明 `0 正常 / 1 被举报 / 2 禁止查看`，PO `BlogComments.status` 的注释同样这么写） | 写入点 `BlogServiceImpl#comment` **固定 `.setStatus(BlogComments.STATUS_NORMAL)`**；全仓库**没有任何代码写 1 或 2**（无举报接口、无审核任务、无后台改状态的入口）；读路径 `pageComments` **只查 `status = 0`**（自提交 `4f53ed6` 起就是这样），所以"被屏蔽的评论仍会展示"这条风险不成立 —— 缺口只在写入侧 | ① 举报/审核功能实际不存在，"被举报""禁止查看"两个状态永远不会出现；② 更危险的是**读路径不看 status**：一旦有人手工（或将来某条链路）把某条评论改成 2，它仍会正常出现在评论列表里 —— "屏蔽"这个动作在展示侧根本没有落点 | ① 保留 DDL 注释（能力是产品要的）+ 把缺口登记进台账（**已登记 C-04**）；② 显示侧过滤**已确认存在**（`status = 0`，比"排除 2"更严），2026-10-17 已把它固化成单测 `BlogCommentsDisplayFilterTest` 并改用命名常量；③ 举报/审核链路单独立项（**仍未实现，C-04 保持打开**） |

## 二、已在本轮修掉、但值得知道其存在过的「失真的能力声明」

这些是**注释与实现不符**，本轮已把注释改成事实（不涉及代码能力缺失），列在此处是为了说明
「失真声明」比「缺口」更常见 —— 它们会让人按错误的心智模型改代码。

| 位置 | 曾声称 | 实际 | 本轮处理 |
|---|---|---|---|
| `CartMapper.upsertItem` | 「购物车展示的是最新价」 | 落库的是**加购请求体的快照**；展示用最新价是另一个字段 `newPrice`，由 `CartServiceImpl` 回源填 | 已更正注释 |
| `EsShopSearchGateway.healthy()` | 「用于状态接口与回落判断」 | 全仓库**没有任何调用方** | 已更正为"当前无调用方" |
| `HotWordSyncTask` | 热词落库「供报表与离线分析」 | 唯一读者是搜索建议 `suggest` 的前缀匹配 | 已更正 |
| `SearchController` 运维开关 | 「大量读写 Redis 并扫描商品表」 | 实际是 Feign 逐页拉**门店**数据 → 重写读模型 → 重灌 ES，**全程不碰 Redis** | 已更正 |
| `ShopServiceImpl.rebuildGeoIndex` | 差集删除「必须，否则旧成员永远清不掉」 | 最终成员集合由末尾 `RENAME` **整体替换**决定，差集作用在即将被替换的旧 key 上 | 已更正，并补上"该前提在 RENAME 之后的异常路径里不成立"这一真实风险 |
| `StockFlow.status` | 「1 有效 2 已回滚」 | 扣减与回补都写 1；回补是新增一条正数流水，**没有任何写 2 的路径** | 已更正 PO 注释；DDL 待同步（见字典漂移清单） |

## 三、与其它清单的关系

| 清单 | 管什么 | 文件 |
|---|---|---|
| 注释验收清单 | 注释工程化是否到位（八类规范、纠偏、闸门） | `docs/注释验收清单-2026-10-15.md` |
| **字典与口径漂移清单** | DDL 声明的取值与代码不一致 | `docs/字典与口径漂移清单-2026-10-15.md` |
| **能力缺口清单（本文件）** | 注释（或产品口径）声称存在、代码没有的能力 | 本文件 |

三份清单的分工是：**验收清单证明"做完了什么"，后两份登记"发现了什么还没做"** ——
后者不会随着注释改完而消失，所以必须独立存在、带着触发条件。
