# Feed翻页：两路内容用同一把“尺子”

旧版v2把收件箱的接收顺序与大V笔记的发布时间混在一起，再用不同游标前进。实际数据测试发现：同一时刻发的笔记可能重现；同一篇先推送又补拉的笔记可能隔页再出现；头部内容已删或被屏蔽时，明明后面还有正常内容，页面却停了。超过200个关注作者和单作者密集发布也会造成遗漏/误结束。

现在两路都按“笔记发布时间＋笔记ID”排序和翻页。先从数据库筛掉不可见内容，再合并去重；后端明确告诉前端hasMore，前端不再只看“这一页有没有凑满10条”。

## 协议与处理过程

1. 首页不传游标。后续页成对回传上一页nextCt/nextCi，SQL用严格小于二元组查询，时间相同再按笔记ID倒序。半个游标、非正数ci、仅li/ai分页返回400。
2. 收件箱JOIN blog获取笔记发布时间，在LIMIT前排除已删除笔记和他人未发布内容。大V侧通过当前用户的关注关系选取全部关注的大V，再按相同游标选择已发布笔记。
3. 每路最多size+1条，按blogId去重、按共同二元组归并。只处理前size个候选；是否存在额外候选决定hasMore。默认10、最多50，因此每路最多51候选，详情最多50条。
4. 详情用一次批量查询取回，并再次检查可见性，以防候选查询后笔记被删/屏蔽。即使被跳过，游标仍推进到已处理候选。这样items为空但hasMore=true时，仍能继续加载后面的内容。
5. 前端优先读取hasMore，并确认有完整的ct/ci游标；没有这个新字段的旧后端仍兼容原长度判据。列表key改用blogId，因为补拉内容的feedId本来就是null。

旧/feed及/feed/ids没有改，实际页面使用/follows/feed/v2。旧接口只返回列表的分页限制仍保留，不把本轮结论扩展到它们。

## 兼容与取舍

- nextLi、nextAuthorId、pullTruncated等字段保留，li/ai参数也保留；v2统一使用ct/ci推进，作者窗口不再轮换，nextAuthorId固定null、pullTruncated固定false。旧li/ai-only客户端会收到400。发布时前后端配套升级并刷新已有Feed页面，不能拿旧游标跨版本续翻。
- 不再用“每作者最多20条”的内存截断控制多样性。新版是明确的时间线，密集发布作者可以占满一页，后面内容仍可继续翻。若要作者配额或推荐排序，应另行定义分页语义，不在本轮添加推荐业务。
- 单页候选/SQL条数有界，不代表扫描成本恒定。非空页通常3条SQL（收件箱、补拉、详情），空候选2条；关注作者数不再决定查询批次数，但相关粉丝聚合、JOIN及排序成本仍随数据增长。
- 既有收件箱索引(user_id,id)不能直接满足按blog发布时间排序。私有夹具EXPLAIN显示Using temporary/Using filesort；小表blog也可能ALL扫描。本轮没有强加索引hint、新索引或历史回填，没有证明大规模Feed性能提升。后续优化应依据真实规模和查询计划。
- 不是跨页快照。新发布且高于游标的内容刷新后看到；关注关系、粉丝阈值、状态变化或延迟推送仍可能改变集合。删除后不会重现已消费候选，但不承诺持续变动时绝不遗漏任何历史内容。

## 验证

实际MySQL+真实Mapper的6项原实现断言均失败，修复后6项通过：同秒且收件箱乱序、推拉重复跨页、删除/隐藏头部、201个关注作者、单作者70条、翻页期间新增头部。粉丝夹具用1001条真实关系满足既有大V阈值，没有调低业务阈值。最终遍历使用hasMore，而不是见短页就停止。

默认服务单测另外验证：匿名不查库、非法游标、合并去重、候选后并发删除导致空页但仍可前进、详情可见性二次校验、50条上限、刚好满页但已结束。前端单测覆盖显式hasMore及旧后端兼容。

日志、EXPLAIN、私有schema与原始结果见 `D:/codex/llmall-feed-cursor-20261029/`。测试仅操作新建llmall_feed_test_随机后缀私有库；未动业务库、未启动其他容器、未做HTTP/浏览器实测、未部署。重跑显式选择FeedCursorIntegrationTest，设置LLMALL_TEST_DB_PASSWORD及新的LLMALL_FEED_TEST_OUTPUT目录。真实组件测试默认integration排除，判断结果需同时看JUnit退出状态与results.json completed。
