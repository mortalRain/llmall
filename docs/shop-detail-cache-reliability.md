# 门店详情缓存的可靠性边界

本轮保留逻辑过期、随机 TTL、空值缓存和 Redis 互斥锁，补齐故障降级、重建线程池饱和和旧读取回填问题。没有引入新中间件、持久化版本表或支付业务。

## 组件职责与读路径

- `ShopServiceImpl` 提供数据库读取和 DTO 转换，保留门店业务职责。
- `ShopDetailCache` 管理 Redis、逻辑过期、重建调度和写入权限。
- `ShopCacheFallback` 只合并正在进行的数据库降级读取，完成后立即移除，不保存结果。

有效热缓存每次请求只执行一次 Redis GET，不增加版本查询。缓存逻辑过期时先返回旧值，持锁者在后台重建。锁服务异常或线程池拒绝时继续返回已有旧值；拒绝策略由 CallerRunsPolicy 改为 AbortPolicy，避免请求线程承担数据库重建。排队任务执行前检查令牌，过期任务不再查询数据库。

缓存读取失败，或冷缓存等待竞争者超时后，采用有限回源。同一实例内，同一门店的重叠请求合并为一次正在进行的读取；默认最多 4 个不同门店读取者，其余请求返回 HTTP 503。同 key 等待者最多等待 500ms，超时不取消持有者。数据库异常保持原异常，不误判成 Redis 故障后二次查库。

这限制的是并发读取数，不是 QPS。主读取者的 SQL 耗时仍依赖数据库/驱动超时；500ms 仅限制合并等待者。各实例独立限额，多实例的总回源上限需乘实例数量。正常冷缓存持锁重建不占此降级配额。

配置：`llmall.shop.cache.fallback-max-concurrency` 默认 4，允许 1–64；`llmall.shop.cache.fallback-wait-millis` 默认 500，允许 1–5000。原有 TTL、锁和轮询配置名称保持不变。

## 令牌如何阻止旧值回填

1. 读取者用 SET NX 和租约获取随机锁 token。
2. 从数据库读取后，用 Lua 同时检查锁仍属于自己并写缓存。正值和空值都必须经过检查。
3. 数据库提交后的失效用另一段 Lua 原子删除锁与缓存，撤销旧读取者的发布资格。
4. 释放锁仍采用 compare-and-delete，旧读取者不能删掉新持有者的锁。

因此，失效前开始、失效后完成的旧读取不能重新污染缓存；锁到期后的旧任务也不能覆盖新缓存。旧的在途 HTTP 请求本身仍可能得到它已经读出的旧数据，这不是线性一致的读协议。

热度更新的详情失效，以及手动失效/下线清理入口，都使用 `TxAfterCommit`：有事务则提交后执行，回滚不执行；无事务立即执行。下线清理入口只清理派生数据，不负责修改门店数据库营业状态。

## 验证证据（2026-10-29）

默认回归包含缓存组件、服务委托、Spring 构造注入、两个 Executor 候选的限定注入、线程池实际饱和、降级并发、异常/中断释放、事务提交/回滚等检查。真实组件测试为 `ShopCacheRedisIntegrationTest`，标记为 `integration`，不进入默认测试。

真实验证使用独占标记的临时 Redis（48MiB 容器限制、16MiB 数据上限、本机随机端口）和随机命名的私有 MySQL schema。验证了热缓存 100 请求恰好 100 次 GET/0 次额外 SQL、正负缓存 TTL、提交失效与双持有者交错、锁到期、迟到空值、回滚、过期排队任务、拒绝释放令牌和真实 Redis 停止后的数据库回源。测试结束已关闭临时 Redis，未清空或停止业务 Redis。

MySQL 使用简化的 `id/name` 夹具表和真实事务；失效回调通过实际服务的提交后钩子触发。它证明协议时序，不等于完整 ShopMapper、网关、鉴权和 HTTP 链路的端到端压测。单次 Redis 停止读取约 509ms，测试客户端命令超时为 500ms，仅用于故障验证，不能作为生产 P99 或 SLA。

## 必须保留的限制

- Redis 与 MySQL 不处于同一事务。提交后进程崩溃、Redis 失效失败仍可能保留旧值，直到物理 TTL 到期、逻辑到期重建或再次成功失效；本轮没有引入可靠失效队列或 outbox。
- Lua 涉及锁与缓存两个无共同 hash tag 的 key，当前适用单机/Sentinel；不声明支持 Redis Cluster 跨槽执行。
- 令牌只约束新代码写入。升级时应排空旧版本重建任务，再启用新协议；旧版本无条件 SET 无法被新 Lua 阻止。
- 已有详情旧值可帮助容忍 Redis 抢锁故障，但读取 Redis 本身仍受客户端连接/命令超时影响。
- 缓存内容需有逻辑过期时间，且非空 DTO 的 id 与请求匹配。损坏内容采用原值比较删除，不打印原始数据。
- 故障日志按实例限频，避免持续故障刷屏；本轮未增加指标平台。后续 HTTP 验证应观测成功率、503、数据库实际查询次数、AVG/P99、并发和资源占用。

本轮没有部署业务服务，没有修改业务数据库结构，没有重新证明历史 6700 RPS，也不应把组件检查写成全站性能提升。最终简历专项在整体优化收口后，根据可复现证据统一筛选。
