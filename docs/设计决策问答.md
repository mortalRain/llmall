## 一、电梯陈述

### 1.1 一分钟版（要点，不背稿）

- **是什么**：同城生活电商平台，**10 个服务、一服务一库**（1 网关 + 9 业务服务），
  闭环是「逛门店 → 买套餐 → 下单支付 → 到店核销 → 写评价 → 门店热度/榜单」（README:3、README:43-58）。
- **技术栈一句话**：Spring Boot 2.7 + Spring Cloud Alibaba（Nacos / OpenFeign / Gateway / Sentinel）+ RabbitMQ + Redis + MySQL 8 + Docker（README:4）。
- **我做的三件事**：
  1. **鉴权收口到网关并防伪造**：入口无条件剥离 `user-info`，下游凭内部凭证才采信身份（`common/UserInfoInterceptor:39-47`）；
  2. **跨域最终一致**：本地消息表 + 三层幂等 + 定时对账，而不是把远程调用塞进全局事务（`trade/OrderServiceImpl:333-357`、`trade/OrderReconcileTask:19-27`）；
  3. **评价 → 热度 → 榜单准实时闭环**：事件驱动重算热度分并写 ZSet 榜单，检索侧按新热度排序（`shop/ReviewCreatedListener:61-73`）。
- **拿得出的数字**：端到端冒烟 **37 项通过 / 0 失败**（实跑，logs/task5/MallE2E-pool20.log）；
  写路径 50 并发 × 60 秒：**1,403 次下单 → 1,371 次支付成功，余额减少 35,097,600 分 = 25,600 × 1371.0**，
  与成功次数**精确相等**（无重复扣款，bench:168-177）。

### 1.2 三分钟版（在 1 分钟版基础上按这个骨架展开）

1. **架构与边界**：按**领域**拆、一服务一库、**只有它能写自己的表**；跨域展示只用三种手段
   ——Feign 聚合 / 冗余字段（下单快照）/ 事件构建本地视图表（`docs/架构设计.md:25-35、65-75`）。
2. **一条链路的纵深**（挑鉴权讲）：剥离伪造头 → 白名单按"路径 + HTTP 方法"双维度判 → 验签 →
   类型隔离（refresh 不得当 access）→ 黑名单（jti）→ 会话失效水位（userId）→ 注入 `user-info` + `x-internal-token`
   （`gateway/AuthGlobalFilter:159-232`）。**顺序即安全边界**，5 个 401 原因码是对外契约（`gateway/AuthGlobalFilter:471-483`）。
3. **一个取舍**：JWT 无状态 → 只对"需要失效的部分"引入状态：access 用**黑名单**（TTL = 剩余寿命，不膨胀）、
   refresh 用**白名单**（可轮换、可"登出所有设备"）（docs/internal/M2-进展与验收.md:36-42）。
4. **一个工程化亮点**：把"只改注释、代码零改动"变成**机器判据** —— 八道闸门 + 三态退出码 + 39 行台账
   （gates/README.md:71-84、台账:159）。**实跑全绿、退出码 0**（附录 C）。
5. **一个踩坑故事**：网关黑名单判定用了 refresh 脚本 + 哨兵 key，导致**每个 access token 都被判已吊销**，
   白名单路径全测不出问题，**MallE2E 走到第一个带鉴权写请求就崩**（`scripts/MallE2E.java:85`，详见 5.1）。
6. **诚实的收尾**：压测是**单机同测口径**，QPS 绝对值不能对标生产；FE 有三处登记不排期（OPT-B/C/D）；
   评论举报/审核链路仍缺（台账:185-194、60）。

### 本节我自己必须能脱稿讲出来的 3 个问题
1. 一句话说清"10 个服务 + 一服务一库"的闭环是哪六段，以及为什么按领域拆而不是按功能拆。
2. 三件事（鉴权收口 / 最终一致 / 热度闭环）各用一句话说清**做了什么、证据在哪**。
3. 主动说出你的**三个边界**（QPS 是单机同测口径、Seata 实测 +259% 故默认关、举报审核链路缺），并说明为什么先登记不硬做。

## 二、架构与流程

### Q2.1 为什么要做微服务？你凭什么说这不是"分布式单体"？

**问题**：一个小项目为什么要拆微服务？拆完是不是更难维护了？

**答案要点**
- **拆的依据是三条判据**，不是"表多就拆"：① 业务能力内聚（一个服务 = 一个完整业务能力）；
  ② **数据所有权独占**（一服务一库，只有它能写自己的表）；③ 可独立部署演进（`docs/架构设计.md:25-29`）。
- **反例我也能举**（这是最常被追问的一类反例）：把点赞 / 评论 / 签到各拆一个服务 → 每条链路跨 5 个服务，耦合反而上升；
  多服务共享一个库互相查表 → 逻辑上还是单体（`docs/架构设计.md:31-35`）。
- **判断是不是分布式单体的两个硬问题**：改一个功能要不要同时发 4 个服务？跨域数据是不是靠直连别人的库拿的？
  本项目的口径是**任何服务不得直接访问别人的库**（`docs/架构设计.md:65-75`）。
- **代价我认**：分布式事务面变大、联调与运维成本上升（README:285 就写着这条代价）。

**溯源**：`docs/架构设计.md:25-35、65-75`；README:285；服务清单 README:43-58。

**边界／别说过头**：不要说"这是生产级微服务"。它是**演示/学习环境**：单机 Docker、每服务
`mem_limit 256m` / `-Xmx192m`（bench:28）、**没有**链路追踪（README:407 列为未做）、没有灰度与优雅发布。

### Q2.2 为什么是 10 个服务？这个粒度你怎么定的？

**问题**：为什么是 10 个，不是 5 个也不是 20 个？

**答案要点**
- 数字口径先说清：**10 个可部署服务 = 1 网关 + 9 业务域**，另有两个**共享库（非服务）**
  `llmall-common`、`llmall-api`（README:43-58、`docs/架构设计.md:79-89`）。
- 粒度判据：**一个服务 = 一个业务能力 + 独占一个库 + 能独立演进**，落在 8 个域上
  （用户 / 门店 / 商品 / 交易 / 支付 / 营销 / 内容 / 搜索），网关不持库、只做路由与鉴权（`docs/架构设计.md:41-55`）。
- **不拆的东西也要能解释**：站内信 `notice-service` **未实现，明确不列入**（`docs/架构设计.md:55`）——
  这是我主动划掉的，不是漏了。

**溯源**：README:3、91-107；`docs/架构设计.md:41-55、79-89`。

**边界／别说过头**：**统一说 10 个服务（1 网关 + 9 业务）**，网关是入口，不是业务域，也不持库。
仓库里曾有一处旧口径写 11（早期把未实现的站内信、或"网关单独算一份"计了进去），现已按 README
服务表统一：`docs/架构设计.md:41` 的小节标题、`deploy/Dockerfile` 与 `nacos-config/shared-jdbc.yaml`
的注释都已改齐。被追问时直接说"以 README 的服务表为准，其余文档引用它"——**只有一份权威口径**，
比背数字更有说服力；若翻到早期提交仍见 11，说明当时口径未统一，现在已收敛。

### Q2.3 一服务一库的取舍是什么？跨服务的列表怎么查？

**问题**：一服务一库拆得爽，可列表页要跨 3 个域的数据，你怎么查？允许跨库 JOIN 吗？

**答案要点**
- **不允许跨库 JOIN**。跨域展示只用三种手段（`docs/架构设计.md:65-75`）：
  1. **Feign 聚合**：内容域校验门店存在性走 `shopClient.queryShopById`，**不直连 shop 库**
     （`content/BlogServiceImpl:69-73`）；
  2. **冗余字段（下单快照）**：`order_detail` 冗余商品名/价格/图片 —— 这是**正确做法**不是脏数据，
     订单要的就是"下单那一刻的快照"；
  3. **事件构建本地视图表**：`feed_inbox`、`shop_search_doc` 都是"消费事件构建的本地读模型"。
- **取舍一句话**：牺牲"一次 JOIN 就拿到全字段"的便利，换来"每个域能独立演进、独立扩缩容、故障不横向传染"；
  代价是**一致性从"数据库保证"变成"应用保证"**（要做幂等、重试、对账，见 Q2.5）。
- 一个具体证据：搜索域**不查 shop 库**，而是维护 `shop_search_doc` 读模型，靠 `shop.hot.changed` 事件同步
  （`shop/ShopServiceImpl:611-615` 把事件登记进本地消息表同事务提交）。

**溯源**：`docs/架构设计.md:65-75`；`content/BlogServiceImpl:69-73`；`shop/ShopServiceImpl:611-615`。

**边界／别说过头**：跨域一致性靠"应用层保证"，所以**必然存在短暂不一致窗口**；本项目里明确存在的是
①大 V 粉丝 Feed 缺条目（台账 C-01）②空索引不回落（已修，见 4.5）③热词窗口口径偏大（台账 C-02）。

### Q2.4 核心链路一：统一鉴权与身份透传

**问题**：你们服务之间怎么认人？我在请求里自己加一个 `user-info: 1` 会怎样？

**答案要点（四步骨架，顺序即安全边界）**
1. **无条件剥离伪造头**：`user-info` / `x-internal-token` / `x-service-token` 三个头在**所有 return 分支之前**删除，
   且**绝不**在下游"信头不认凭证"（`gateway/AuthGlobalFilter:177-187`）。
   原因：白名单路径（`/items/**` 这类）是**直接放行**的，若不剥离，谁都能自带 `user-info: 1` 冒充任意用户
   —— 这是一次**完整认证绕过**。
2. **白名单按"路径 + HTTP 方法"双维度判**：只有 GET/HEAD/OPTIONS 才走 `excludePaths`；
   写方法只认显式登记的 `unsafeExcludePaths`（`gateway/AuthGlobalFilter:536-554`）。
   否则 `/items/**` 一条会把 `DELETE /items/1`、`PUT /items/stock/restore`（无限加库存）一起放行。
   白名单未配置时**恒不放行**（fail-closed）：配置缺失的后果是"要求登录"，不是"接口裸奔"（`:539-542`）。
3. **验签 + 类型隔离**：`TokenExpiredException`（过期，可刷新）与 `UnauthorizedException`（非法，刷新无用）
   走**两个分支**，混在一起前端会做错交互（`:194-214`）；`type` 必须是 `access`，否则长效 refresh 可当 access 用，
   短 TTL 的安全收益归零（`:212-214`）。
4. **两层失效机制**：黑名单按 `jti` 回答"这个令牌被注销了吗"；会话失效水位按 `userId` 回答
   "改密之后签发的才算数吗"。缺任一条都会留窗口（`gateway/AuthGlobalFilter:62-64`）。
5. **注入下游**：只写 `user-info` + `x-internal-token`，**绝不**写 `x-service-token`
   （那是"服务间调用"的凭证，注入等于把内部接口开放给所有登录用户，`:443-445`）。

**下游怎么认**：`common/UserInfoInterceptor:39-47` —— 头存在**不等于**可信，**必须**同时持有
`x-internal-token` 且与配置全等才采信，否则按未登录 + WARN（把"疑似绕过网关直连"变成可检测信号）。
服务默认监听 `0.0.0.0`，**网关并不是唯一入口**，所以这条 fail-closed 不可省。

**溯源**：`gateway/AuthGlobalFilter:61-78、159-232、448-462、471-483、536-554`；
`common/UserInfoInterceptor:15-19、39-53`；README:68-74。

**边界／别说过头**：**下游服务不验签**，信任边界是"经过网关"。
内网若不可信，需要内网签名或 mTLS —— 现在是**假设内网可信**，这句话要主动说。

### Q2.5 核心链路二：跨域最终一致性

**问题**：下单扣了库存，但支付/发积分失败怎么办？MQ 丢消息怎么办？

**答案要点（三道防线，各兜不同场景）**
1. **业务与消息同事务落库**：支付回调里先**条件更新** `order.status 1→2`（`affected rows=0` 即幂等，重复回调直接返回），
   再在**同一本地事务**里 `messageLogService.record(...)`，注册提交后投递（`trade/OrderServiceImpl:333-357`）。
   语义是"**业务成功 ⇒ 消息一定存在**"。
2. **定时重试兜"没发出去"**：退避基数 × 2^n、上限 10 分钟，`fixedDelay` 默认 15s
   （`common/AbstractMessageLogService:39-45`、`common/AbstractMessageRetryTask:28-43`）。
   **踩过的坑写进注释了**：漏 `@EnableScheduling` 不会报错，`@Scheduled` 静默不执行、`status=3` 的行躺着没人管
   （`common/AbstractMessageRetryTask:11-12`）。
3. **对账兜"发出去了但下游没处理成功"**：定时**问下游**"你处理了没有"——用户域答"积分流水在不在"、
   门店域答"消费记录在不在"，任一为"未处理"就补偿重发（下游消费幂等，重发安全）。
   窗口只对**最近 24 小时**，批 100 条（`trade/OrderReconcileTask:19-35、57-66`）。
4. **对账的三态是重点**：`CONSUMED / NOT_CONSUMED / UNKNOWN`。**"查询失败"与"查到了、结果是没有"业务含义相反**，
   所以未知**既不算已处理**（否则一致性缺口被伪装成正常）**也不触发补偿**（避免补偿风暴），
   只留到下轮；连续 3 轮未知升级为 ERROR 提醒人工（`trade/OrderReconcileTask:24-26、43-53`）。
5. **消费幂等锚在唯一键上，不锚在 Redis**：`consume_record` 的 `uk_consume(biz_type, biz_id, consumer)`，
   占位与业务**同事务** → 抛异常则占位随回滚消失，不需要"失败删占位"（`shop/ReviewCreatedListener:21-26、49-59`）。
   幂等键**只有数据库唯一键**才是终局，Redis 会丢（`common/IdempotentKeys:25-33`）。

**溯源**：`trade/OrderServiceImpl:333-357`；`common/AbstractMessageRetryTask:11-43`；
`common/AbstractMessageLogService:39-45`；`trade/OrderReconcileTask:19-47、57-66`；
`shop/ReviewCreatedListener:18-74`；`common/IdempotentKeys:3-35`。

**边界／别说过头**：这是**最终一致**，不是强一致 —— 窗口内会读到旧值（例如积分晚到几秒）。
另外 `markOrderPaySuccess` 里消息发送失败只记 error 不抛（"支付本身不受影响"），
所以**窗口的上界由重试 + 对账决定，不是 0 秒**（`pay/PayOrderServiceImpl:317-322`）。

### Q2.6 核心链路三：评价 → 热度 → 榜单闭环

**问题**：用户发一条评价，多久能在首页榜单上看到？中间经过几跳？

**答案要点（六跳，每跳都能说出落点）**
1. **内容域收评价**：先 **Feign 校验门店存在**（不直连 shop 库）→ 落 `blog` → **写扩散推粉丝收件箱** →
   `publishBlog` 里 `publishReviewCreated`（`record()` 写消息表 + `dispatchAfterCommit()` 注册提交后投递）
   （`content/BlogServiceImpl:63-106`）。
   注意注释里那条坑：**不能**把这次调用套回 `TxAfterCommit`，否则 `record()` 被推到提交后执行、脱离业务事务
   （`content/BlogServiceImpl:91-94`）。
2. **门店域消费**：`consume_record` 唯一键挡重投 → 一条 SQL 原子累加评分/评价数（`shop/ReviewCreatedListener:61-68`）。
3. **那条 SQL 有个致命顺序**：`score = ROUND((score*comments + 新分*10)/(comments+1))` **必须写在
   `comments = comments + 1` 之前** —— MySQL 单表 UPDATE 里**后面的赋值会看到前面刚赋的新值**，
   顺序反了分母多 1，平均分被**系统性算低**（`shop/ShopMapper:13-21`）。
4. **重算热度**：`base = 评分/10×4 + log10(评价数+1)×3 + log10(销量+1)×3`，`decay = 1/(1+Δ天/7)`；
   **衰减锚点取"最近一次评价时间"而不是重算时间**，否则每次重算都把衰减重置成 1，衰减形同虚设
   （`shop/ShopServiceImpl:572-598`）。
5. **写榜单 + 发事件**：写 DB → 写 ZSet（总榜 + 按类型榜，带 TTL 滑动续期）→ 失效详情缓存 →
   把"整行门店快照"事件登记进本地消息表（同事务），指向搜索域（`shop/ShopServiceImpl:601-615`）。
6. **读榜单与检索**：榜单**必须按 ZSet 的 id 顺序还原**（DB 的 `IN` 查询不保证顺序），
   并且要**剪枝**（ZSet 没有单成员 TTL，打烊/删除的门店会永久占名次）（`shop/ShopServiceImpl:461-512`）；
   检索侧 `ORDER BY hot_score DESC, comments DESC` 承接最后一跳（`search/SearchServiceImpl:211-213`）。

**实测**：E2E 里"评价 → 门店热度重算(事件驱动)"这一项就是这条链路，热度 **35.4053 → 36.6351**，
评价数 **3044 → 3045**（实跑，logs/task5/MallE2E-pool20.log）。

**溯源**：`content/BlogServiceImpl:63-106`；`shop/ReviewCreatedListener:18-74`；`shop/ShopMapper:10-22`；
`shop/ShopServiceImpl:461-512、587-634`；`search/SearchServiceImpl:202-218`。

**边界／别说过头**：闭环里**嵌着一个功能缺口**——第二步"写扩散推粉丝收件箱"在粉丝数超阈值时
**直接跳过推送**（`content/FollowServiceImpl:172-180`），所以"发布后粉丝能看到"这句话**只对粉丝数 ≤ 阈值的作者成立**。
不要把它说成"推拉结合"。

## 三、技术选型与取舍

> 每问都要能说出：**选了什么 / 为什么 / 代价是什么 / 备选方案为什么不行**。只说前两条的答案会被一问就塌。

### Q3.1 为什么是 Spring Boot 2.7 + Spring Cloud Alibaba，不是 Boot 3？

**问题**：现在都 Boot 3 了，你为什么用 2.7？

**答案要点**
- **版本矩阵是一个整体**，不是随手选：JDK 11 + Spring Boot 2.7.12 + Spring Cloud Alibaba 2021.0.4.0 +
  MyBatis-Plus 3.5.3.2（`docs/架构设计.md:132-138`）；`javax.*` 时代（拦截器用的是 `javax.servlet.*`，
  `common/UserInfoInterceptor:9-10`），上 Boot 3 要整仓迁 `jakarta.*` + 抬 JDK 17，**与"先把业务闭环和治理做实"的目标冲突**。
- **SCA 2021.0.4.0 与 Boot 2.7 是对齐的官方组合**，Nacos/Gateway/Sentinel/OpenFeign 四个组件的版本都不用自己掰。
- **我自己踩过版本红线，所以这条不是拍脑袋**：Lombok 1.18.30（`llmall/pom.xml:45`）打不开 JDK 22+ 的内部 javac API，
  在 **JDK 25 上编译必然失败**，而**只跑分析闸门时它还是绿的** —— 于是"闸门通过"会掩盖"构建不了"，
  我在闸门入口加了 JDK 11~17 的准入闸门（`gates/gate-env.ps1:94-108`，实跑见 5.5）。

**溯源**：`docs/架构设计.md:132-138`；`common/UserInfoInterceptor:9-10`；`llmall/pom.xml:45`；
`gates/gate-env.ps1:94-108`；`gates/README.md:21`。

**边界／别说过头**：不要说"2.7 更好"。正确说法是**"我的环境与依赖链是 2.7 对齐的，升 3 是一次独立迁移任务，
收益是长支持期，成本是全仓 jakarta 迁移 + 全部依赖重验"**——这是取舍，不是优劣。

### Q3.2 为什么用 Nacos 而不是 Eureka？

**问题**：服务发现用 Eureka + Config 不也行吗？你为什么选 Nacos？

**答案要点**
- **一个组件干两件事**：服务发现 + 配置中心。`bootstrap.yaml` 里同一个 `server-addr` 下同时配 `discovery`
  与 `config`，`shared-*.yaml` 是"跨服务的同一份口径，在 Nacos 上发布即对所有服务生效"
  （`llmall-pay-service/src/main/resources/bootstrap.yaml:8-31`）。Eureka 只有注册，配置得再引入一套 Config + Bus。
- **配置分层是真实收益**：启动参数 → 服务私有 `application.yaml` → Nacos `shared-*.yaml` → 默认值；
  换环境只改一份 `application-local.yaml`，不动 Nacos（`nacos-config/README.md:30-30`）。
- **我还用 Nacos 做过"非配置类的东西"**：网关路由放在 Nacos 的 `gateway-routes.json`，
  用 `ConfigService.getConfigAndSignListener` 监听变更、全量重建本机路由表
  （`llmall-gateway/.../DynamicRouteLoader.java:22-30、53-65`）。
  **为什么不用 Spring Cloud Gateway 的 routes 属性源**：那份配置根节点是 JSON 数组，**无法展开成属性源键值对**；
  且中文注释在默认字符集下会被 Nacos 按 UTF-8 解析失败（`DynamicRouteLoader.java:26-30`）。
- **一个只有踩过才知道的点**：**Nacos 下发的键，外部参数一律盖不过去**。
  我为了改 Hikari 池上限试过 5 种覆盖方式（服务自己的 yaml / `-D` / 命令行 / `override-none` /
  `override-system-properties=false`），**五轮全部仍为 5.0**；最后只有"**服务专属 dataId**"这一层能盖住
  shared-configs（`docs/P-01-申请支付单耗时定位-2026-10-17.md:179-196、291-300`）。

**溯源**：`llmall-pay-service/src/main/resources/bootstrap.yaml:8-31`；`nacos-config/README.md:30-30`；
`DynamicRouteLoader.java:22-30、53-65`；`docs/P-01-...md:179-196、291-300`。

**边界／别说过头**：Eureka 也不是"不行"，是**多引一套组件的运维成本**；如果你要说"Nacos 更好"，
请落在"**发现 + 配置 + 动态路由监听在一个组件里**"这个具体事实上，而不是泛泛说"Nacos 更流行"。

### Q3.3 为什么单镜像多服务（单镜像多 jar）？

**问题**：为什么不是一服务一镜像？这不是反模式吗？

**答案要点**
- **明确的成本账**：一服务一镜像 = **11 次 Maven 构建 + 11 层依赖下载**，本地/小服务器上极其耗时；
  打成"一个镜像内含全部 jar"，**容器只换启动命令**即可，构建一次复用 N 次（`deploy/Dockerfile:4-7`）。
- **怎么做到的**：`FROM maven:3.9-eclipse-temurin-11 AS build` 多阶段构建 → 运行阶段把 10 个 jar
  `COPY` 进 `/app/`（`deploy/Dockerfile:20-70`）→ `CMD` 默认起网关，其他服务在 compose 里**覆盖 `command`**
  （`deploy/Dockerfile:76-77`）。
- **两个真实优化点**（可以讲到构建细节，是实际构建过的证据）：
  ① 先只 COPY 所有 `pom.xml` 再 `dependency:go-offline`，利用层缓存（`:28-49`）；
  ② 加 `--mount=type=cache,target=/root/.m2`，因为"源码一变 `COPY . .` 之后所有层失效"，光靠层缓存挡不住全量重下（`:43-49`）。
- **什么时候该拆**：注释里自己写着 —— **"生产上若各服务独立发布节奏不同，再拆成一服务一镜像"**（`deploy/Dockerfile:7`）。

**溯源**：`deploy/Dockerfile:4-7、20-49、57-77`；README:293。

**边界／别说过头**：单镜像 = **所有服务共享同一个发布单元**，任一服务改了就要整镜像重建、整批重启，
这是**演示环境的取舍**，不是生产方案。被问"生产怎么办"就答"按发布节奏拆一服务一镜像 + 独立 CI"。

### Q3.4 为什么用 Redis 做锁，不用数据库锁？

**问题**：分布式锁为什么不用 `SELECT ... FOR UPDATE`？Redis 锁挂了怎么办？

**答案要点**
- **先分清两件事**：Redis 锁是**优化**，DB 条件更新是**裁决**。
  锁只做"同一支付单串行化"，**重复扣款的最终裁决点是下游余额流水表的唯一索引**
  —— 注释原话："锁失效不会造成资损，但会放大下游的并发冲突"（`common/IdempotentKeys:157-168`）。
- **为什么不排队等锁**：表里**没有"支付中"的中间态**，两个并发请求都会通过待支付检查；
  后来的请求必须**立即失败**而不是排队（`pay/PayOrderServiceImpl:226-234`）。实现是 `setIfAbsent` + 30s TTL
  （`pay/PayOrderServiceImpl:68-75、244-251`）。
- **为什么不用 DB 锁**：余额支付链路是 `@Transactional`，**事务内还要发一次 Feign 扣款**。
  用 `FOR UPDATE` 意味着**行锁被持有到远程调用返回**，锁持有时间 = 网络往返，这是把 DB 连接与行锁一起浪费掉
  —— 这正是我登记下来的 **OPT-D**（台账:193），也是抬池后 `POST /pay-orders/{id}` 的 **Avg 反而升到 953ms**
  而 P99 下降的原因（`docs/P-01-...md:204-209`）。
- **释放锁必须比对值再删**：`if get(KEY)==ARGV[1] then del`，直接 DEL 会误删"锁超时后别人刚拿到的那把"
  （`pay/PayOrderServiceImpl:77-80、615-622`）。

**溯源**：`pay/PayOrderServiceImpl:67-80、222-251、615-622`；`common/IdempotentKeys:155-169`；
`docs/P-01-...md:200-209`；台账 OPT-D（台账:193）。

**边界／别说过头**：这不是 Redisson 的看门狗方案 —— **锁 TTL 到期不续期**，
注释里写清了"锁 TTL 内没跑完，并发请求即可拿锁并通过状态检查"，靠 DB 条件更新兜（`pay/PayOrderServiceImpl:233-235`）。
被问"锁过期怎么办"走 7.3，别在这儿硬撑。

### Q3.5 为什么 Sentinel 阈值用代码注册，不放 Nacos？

**问题**：Sentinel 规则不都放 Nacos 做持久化吗？你写在代码里不落后吗？

**答案要点**
- **理由一：规则少且与具体资源强绑定**。只有 `itemPage` 一个资源（`ItemController#queryItemByPage` 上唯一一处
  `@SentinelResource`），"**改了要发版**"反而让口径更清楚（`common/SentinelRuleConfig:17-26`）。
- **理由二：一旦接 `sentinel-datasource-nacos`，`loadRules` 会被数据源覆盖**，本类退化成"兜底默认值"，
  且**会出现两处同时改**的风险 —— 注释里明确写了"注意不要两处同时改"（`common/SentinelRuleConfig:24-26`）。
- **阈值不是拍脑袋，是压测算出来的**：`1000 = 压测容量（≈1500~1550 rps）× 约 70%`；
  抬连接池对该接口容量**几乎没有影响（+2~5%）**，所以阈值不随池大小调整（`common/SentinelRuleConfig:45-53`）。
  落地验证：启动日志 `[Sentinel] 最小规则集已加载: flow=1 条（itemPage QPS=1000.0）`，
  50 并发 60 秒放行峰值 1046/s，被拒 90,508 次**全部 400 且日志原因单一**
  （`docs/P-02-商品列表容量与建议阈值-2026-10-17.md:204-218`）。
- **顺带一条"设计内"现象**：压测里 `GET /items/page` 错误率 93%~96%，不是故障 ——
  **是限流在拒绝**，说明"**该接口容量上限 = 限流阈值**，扩容前先调规则而不是先加机器"
  （bench:56-61、229-231）。

**溯源**：`common/SentinelRuleConfig:17-26、33-55、57-82`；`docs/P-02-...md:188-218`；bench:56-61。

**边界／别说过头**：**控制台推送的规则重启即丢**（README:409 把"规则持久化到 Nacos"列为未做）。
被问"生产怎么管"就答：**接 `sentinel-datasource-nacos` 并接受"代码默认值退化为兜底"**，
同时把"两处同改"写成发布检查项。

### Q3.6 为什么 Hikari 池压到 5？

**问题**：连接池给 5 条也太小了吧？

**答案要点**
- **算法是连接总数上限，不是单服务性能**：默认 10 时 `11 服务 × 10 = 110`，已接近 MySQL 默认
  `max_connections=151`；而且**服务被杀后连接要等 `wait_timeout`（默认 8 小时）才回收**，
  反复重启就能打满连接数（表现是 `Too many connections`，连 root 都被拒）。压到 5 后最坏情况 110 → 55
  （`nacos-config/shared-jdbc.yaml:8-11`）。
- **配套三件套都写了取值依据**：`connection-timeout: 5000`（池满 5s 快速失败，默认 30s 会让 Tomcat 线程陪着挂住）、
  `idle-timeout: 60000`、`max-lifetime: 600000`（**必须远小于 wait_timeout**，否则超龄连接被服务端单方面关闭，
  取到即 `Communications link failure`）（`nacos-config/shared-jdbc.yaml:13-22`）。
- **代价我压出来了，而且量化了**：池 5 让 pay-service 的 DB 并发钉死在 5 —— 一次 DB 操作 =
  **517ms 排队 + 65ms 执行**，排队占 89%；吞吐天花板 `5 ÷ 0.065s ≈ 77 次/秒`，实测 76.3 次/秒**贴着天花板**
  （`docs/P-01-...md:23-48`）。
- **抬到 20 的结果**（如实说）：`POST /pay-orders` Avg **1083 → 573ms（−47%）**、P99 **2374 → 950ms（−60%）**、
  整链路吞吐 **74.8 → 85.6 req/s（+14%）**，但**排队没有归零**（`pending` 43~46 → **30**），
  且单次占用从 65ms 涨到 221ms（DB 侧摩擦上来了）（`docs/P-01-...md:198-231`）。
  最终用**服务专属 dataId** `llmall-pay-service.yaml` 只给 pay 抬到 20，其余 8 个服务仍 5，
  连接总账 `8×5+20 = 60 ≤ 100`（`docs/P-01-...md:274-311`）。

**溯源**：`nacos-config/shared-jdbc.yaml:7-22`；`docs/P-01-...md:23-48、172-249、274-311`；台账 OPT-B（台账:191）。

**边界／别说过头**：**"5 是错的"这个结论只对写路径成立**。读路径（item）抬池**几乎没有收益（+2~5%）**，
容量天花板是宿主 CPU 与 MySQL QPS，不是应用侧池（`docs/P-02-...md:179-198`）。
正确说法是"**按接口类型分档**"，不是"全站统一抬到 20"（否则 `9×20=180 > max_connections`）。

## 四、关键接口的"为什么这么设计"

### Q4.1 `applyPayOrder`：为什么先校验订单可付再建单？幂等键为什么 fail-closed？三道防线各拦什么？

**问题**：申请支付单这个接口，你怎么保证不重复建单、不给已关闭的订单建单？

**设计意图**
- **顺序**：`checkOrderPayable`（Feign 查交易订单 + 归属 + 状态 + 金额）→ `checkIdempotent`（按交易订单号复用或新建）
  （`pay/PayOrderServiceImpl:118-131`）。注释一句话就是答案：**"越早失败，需要人工对账的差错单越少"**（`:118`）。
- **金额必须比对**：`amount` 来自前端，不比对等于允许把 100 元改成 1 元（`:212-215`）。
- **状态必须等于 1（待付款）**：已支付/已关闭要**明确报错**而不是默默建单，否则会重现
  "订单已超时关闭、钱却付了"的资损路径（`:208-211`）。

**幂等键为什么 fail-closed**
- 下游余额扣减**缺 bizNo 直接拒绝**：`if (StrUtil.isBlank(bizNo)) throw BadRequest`，
  注释写的是"幂等键强制（fail-closed）：缺了它，上游重试/并发双击就会重复扣款，事后也分不清哪一笔对应哪次支付"
  （`user/UserServiceImpl:339-342`）。
- **键的形态只有一个定义点**：扣款键 `PAY:<支付单id>:<金额>`、退款键 `PAYFAIL:<扣款键>`，
  由 `IdempotentKeys` 统一构造，**禁止手拼**（`common/IdempotentKeys:44-76`）。
  **扣款键必须确定**（重试落同一个键，才不会被二次扣款）；**退款键必须与扣款键不同值**（否则会把另一笔扣款退掉）。
- **申请支付单这一层**的幂等靠 `pay_order.biz_order_no` 的**唯一索引**裁决 ——
  "先查后插"在并发申请之间**没有任何互斥**，真正兜底的是唯一键（`pay/PayOrderServiceImpl:653-666`）。

**三道防线各拦什么**（这是最容易被追问的一段，按这个顺序答）

| 防线 | 拦什么 | 失效后果 | 溯源 |
|---|---|---|---|
| ① 支付单维度 Redis 锁（30s，**不排队**） | 同一张支付单的**并发重复提交** | 并发请求各自推进状态、各自承担退款责任 | `pay/PayOrderServiceImpl:226-255` |
| ② DB 条件更新闸门（`status=1` 才放行，affected rows 裁决） | 锁过期/穿透后**仍有人继续往下走** | 各自发起一次跨服务扣款 | `pay/PayOrderServiceImpl:273-277、344-364` |
| ③ 下游余额流水**唯一键** | 前面两道都漏掉时的**重复扣款** | 真资损 | `user/UserServiceImpl:368-384` |

> 原话值得背一句："**三道防线（锁 / 状态条件更新 / 下游唯一键）缺一不可**"（`pay/PayOrderServiceImpl:235`）。

**踩过的坑**
- **锁不能放 finally**：`finally` 在 `@Transactional` **提交之前**执行，锁一放开，另一个请求立刻拿到锁、
  读到**还没提交**的支付单（仍是待支付）→ 通过检查 → 同一支付单出现多个支付尝试。
  所以释放锁与状态归位都必须挂在**事务同步钩子** `afterCompletion`（`pay/PayOrderServiceImpl:448-489`）。
- **提交阶段失败也要补偿**：Spring 传进来的 status 是 `STATUS_UNKNOWN`，判据必须是
  "**不等于 COMMITTED**"而不能只判 `ROLLED_BACK`（`:446-447`）。
- **只有"确定已扣"才退款**：`UNKNOWN` 一律不猜（对已扣的单退款 = 凭空加钱），只落
  `result_code=UNCERTAIN` 留痕交日终对账（`:498-513、414-439`）。三态 `PENDING/DEDUCTED/UNKNOWN`
  装不进一个 boolean，这是设计上的关键决定。

**溯源**：`pay/PayOrderServiceImpl:118-131、181-216、222-235、269-273、344-364、441-482、498-513、643-656`；
`user/UserServiceImpl:324-400`；`common/IdempotentKeys:44-76`。

**边界／别说过头**：这条链路**每请求取 2 次数据库连接**（SELECT 与 INSERT 各借还一次，方法上**没有事务**），
这是已登记但**不排期**的 OPT-B（台账:191）；`applyPayOrder` 目前**故意没有事务**，唯一性靠唯一索引兜底
（`docs/P-01-...md:160`）。

### Q4.2 `GET /follows/feed`：推模式 + 读时 IN 批量合并；为什么用 feedId 而不是 blogId 做游标？

**问题**：Feed 怎么做的？分页为什么用游标不用 offset？游标为什么是 feedId？

**设计意图**
- **写扩散（推）**：发布时把 `(user_id, blog_id, author_id)` 批量插进粉丝收件箱 `feed_inbox`，
  `(user_id, blog_id)` 唯一索引让重复推送天然幂等（`content/FollowServiceImpl:165-195`）。
- **读时批量合并**：一页收件箱 1 条 SQL + 笔记 `selectBatchIds` 1 条 SQL，
  **口径是"每请求恒 2 条 SQL，与页大小无关"**（`content/FollowServiceImpl:218-250`）。
  注释把失效条件也写死了：**"若把 IN 查询改回循环内单条查询，SQL 条数会随页大小线性增长"**（`:211`）。
- **合并后可见性同口径**：只出 `status=1`（作者本人可看自己未过审的），不可见/已删除的条目**跳过而不是占位**
  ——"返回空壳会把'不该给看'变成'看起来没内容'"（`:239-249`）。
- **顺序按收件箱还原**：以收件箱行序为准（`ORDER BY feed_inbox.id DESC`），不依赖笔记表的返回序。

**为什么游标是 feedId 而不是 blogId**
- 游标条件是 `feed_inbox.id < lastId`（`:190-194`、`:220-224`），**分页键必须是分页所依据的那张表的主键**。
  `feedId` 就是收件箱行的自增 id，**单调、稳定、与"每个读者各自的收件箱"一一对应**；
  `blogId` 是**作者的发布顺序**，与读者的收件箱顺序没有单调关系，用它做游标会导致**翻页跳条/重条**。
- 对外视图里 `feedId` 是显式返回的（`FeedItemVO.setFeedId(row.getId())`，`:256-258`），
  所以客户端下一页直接回传它即可：`lastId 传上一页最后一条的 feedId（收件箱记录 id），首页不传`
  （`content/.../FollowController:58-67`）。
- 为什么不用 OFFSET：避免**深分页性能塌陷**与**翻页重复/漏数据**（`:189`）。

**实测**（这是"没有 N+1"的硬证据，不是靠延迟推的）
- 用 MySQL `Com_select` 增量 ÷ 请求数量"每请求 SQL 条数"：
  `/feed` 串行 **1.01**、10 路并发 **1.04**；`/items/page` 恒 **2.02 且与 pageSize=1/10/30 完全无关**（bench:93-102）。
- 延迟：10/50/100 并发 P95/P99 = **6/7、39/48、70/84 ms**，错误率 0%（bench:53-55）。
  并发升高延迟上升是 CPU 饱和，**不是 N+1 放大**（bench:91、101-103）。
- **⚠ 这里有一个必须自己先想清楚的口径差（否则会被当场问倒）**：
  代码里写的是"**每请求 2 条 SQL**（收件箱 1 条 + 笔记 IN 1 条）"（`content/FollowServiceImpl:221-223`），
  但压测测出 **1.0 条** —— 差的这一条不是 bug：`queryFeedItems` 在**收件箱为空时提前 return**
  （`content/FollowServiceImpl:242-244`），只发了收件箱那 1 条；而种子数据里**没有关注关系**
  （`sql/merged/30-content.sql:165-166` 的 `INSERT INTO follow` 是**注释掉的迁移指令**，
  50/51 号 seed 只写 `user_info.followee/fans` 计数），所以压测账号的收件箱是空的。
  **正确说法**："**收件箱非空时是 2 条且与页大小无关；那次压测因为收件箱为空，只覆盖了 1 条的分支**，
  造出关注关系后复跑才是对 N+1 的完整验证" —— 这属于**压测覆盖缺口**，不是代码缺陷。

**踩过的坑**
- **阈值必须以 DB 计数为准**：用 Redis 粉丝数判断会把"计数刚好过期/被清"的大 V 当小号做全量写扩散
  （`content/FollowServiceImpl:169-174`）。
- **事务内不写 Redis**：关注关系的 Redis 写一律放 `TxAfterCommit`，否则事务回滚会留下"DB 没有的粉丝"
  （`:86-91、473`）。

**溯源**：`content/FollowServiceImpl:165-267、481-497`；`content/FollowController:58-75`；bench:49-107。

**双端点口径（这半页必须分清，说混就露馅）**：
- `/follows/feed`（**v1，冻结为纯推兼容**）：只读收件箱，**没有**读时拉取合并，大 V 的笔记在这里**看不到**；保留它是为了让旧口径与旧前端不受影响。
- `/follows/feed/v2`（**完整推拉**）：收件箱 + 大 V 补拉近 20 条 → 按 `(create_time, id)` 归并 → 按 `blog_id` 去重 → 分页（`:270-364`）。**C-01 由它关闭**。
- **推的是什么**：粉丝数 ≤ 1000 的作者发布时由 `pushToFollowers` 写扩散进粉丝收件箱，收件箱里**有行**；
  **拉的是什么**：粉丝数 > 1000 的作者发布时**跳过**写扩散（`:172-180`，WARN 保留作可观测信号），其粉丝读 v2 时按关注作者分批判补拉，**每个作者近 20 条**，条数上界 `3 + ⌈min(关注数,60) ÷ 20⌉`。
- **代价（必背）**：吞吐 **−20%~−25%**、P99 **+8%~+27%**、每请求 SQL 从 **2** 涨到 **4**（1 批）/ **6**（3 批上界）；两端都实测过，且都与页大小无关。

### Q4.3 余额扣减：为什么只校验 `pay_password`？为什么首次支付强制改密？为什么幂等唯一键兜底？

**问题**：用户改了登录密码，余额支付能力应该跟着变吗？支付密码为什么还要单独一列？

**设计意图（三步同一事务）**
`占位流水 → 条件更新余额 → 用真实余额修正流水`（`user/UserServiceImpl:324-400`）：
1. **先插流水占位**：并发下"查一下这笔业务号扣过没有"挡不住第二个请求，**只有流水唯一键能挡住**，
   且第二个请求**一分钱不动就退出**（`:262-264、303-319`，`DuplicateKeyException` 捕获后直接 return）。
2. **条件更新**：`balance >= amount` 作为 SQL 的 WHERE，**按受影响行数判断**，余额不足不会扣成负数（`:321-325`）。
3. **修正账本**：并发下"扣款前余额 − 金额"未必等于最终值，`balance_after` 必须写**真实余额**，
   否则对账时 `SUM(change_amount)` 与余额对不上（`:327-332`）。

**为什么只校验 `pay_password`**
- **两列禁止互相读写**（`user/UserServiceImpl:57-67`）：`password`（登录口令）只在 `login` 校验；
  `pay_password`（支付口令）只经 `selectPayPassword` 取出，在 `deductMoney` 与 `changePayPassword` 校验。
- **为什么必须分两列**：两种口令的强度要求**相反** —— 登录口令必须**不可预期**（自动注册用随机值，
  否则"用户名由手机号推导 + 口令固定"= 知道手机号即可接管账号）；支付口令必须**用户可预期**
  （否则自动注册的账号无法完成余额支付）。**合为一列时两个要求直接冲突**（`:55-58`）。
- **误读后果**：支付校验若误读 `password`，**用户改登录口令即等于改掉支付口令**（`:59-60`）。
  SQL 侧也钉死了：`@Select("select pay_password from user where id = ...")`，注释写明"禁止改读 password"
  （`llmall-user-service/.../UserMapper.java:17-20`）。

**为什么首次支付强制改密**
- 判据是"**当前口令是否等于初始口令**"，不是"是否改过"：改成其它值后即永久放行，
  即使后来改回初始值也无所谓（那是用户自主选择，不再是"从未设置过"）（`user/UserServiceImpl:354-364`）。
- **必须放在密码校验之后**：先证明"你知道当前口令"，否则等于给攻击者一个**免费的状态探测接口**
  （"哪个账号没设过支付口令"）（`:292-294`）。
- 初始口令常量 `INITIAL_PASSWORD = "123456"` 有**两个用途（写入 + 比对）必须同源**，
  否则只改其一会静默出现"明明没改过口令却不再被要求改密"（`:74-89`）。

**为什么幂等唯一键兜底**
- 扣款/退款都落 `balance_flow`，唯一键 `uk_biz(biz_type, biz_no)` 去重 ——
  **这是"重试、快路径与事务收尾重复补偿都只会真正动一次钱"的最终依据**（`pay/PayOrderServiceImpl:53-58`）。
- 退款复用同一条资金路径（不新造只有支付域会走的加钱通道），按 `PAYFAIL:<扣款键>` 去重，
  **快路径与事务收尾各补偿一次也只退一次钱**（`pay/PayOrderServiceImpl:583-609`）。

**踩过的坑（三个，每个都能独立讲）**
1. **"先查一遍这笔业务号扣过没有"挡不住并发**：两个请求都会查到"没扣过"，然后各扣一次；
   **只有流水唯一键能挡**，且第二个请求**一分钱不动就退出**（`user/UserServiceImpl:327-329`）。
2. **`balance_after` 不能写"扣款前余额 − 金额"**：并发下它不等于最终值，对账时 `SUM(change_amount)`
   与余额对不上；正确做法是**扣完回查真实余额再修正流水**（`:327-332`）。
3. **冒烟里余额支付恒失败不是脚本写错**：`deductMoney` 在密码校验后还有"初始支付口令强制改密"拦截，
   而改密接口要求**短信验证码**、脚本无法自给 —— 详见 5.2（`user/PayPasswordFormDTO:34`）。

**实测**
- 20 线程并发双击同一支付单：**1×200 + 19×400**，余额**只减 25,600**（bench:179-185）；
- 50 并发 60 秒：余额减少 35,097,600 ÷ 25,600 = **1371.0**，与支付成功次数 1,371 **精确相等**，
  `balance_flow` 新增 1,371 条一一对应（bench:168-177）。

**溯源**：`user/UserServiceImpl:57-67、74-89、259-335`；`llmall-user-service/.../UserMapper.java:17-20`；
`pay/PayOrderServiceImpl:53-58、583-609`；bench:166-188。

**边界／别说过头**：**退款入账接口是参数化 userId 的**，靠"有登录上下文时只允许操作自己"来限制越权面
（`user/UserServiceImpl:402-426`）。这是**内部接口**，被问"外部能不能调"要答"网关 + 归属校验两层挡，
但更彻底的做法是内部接口只走服务间凭证（`x-service-token`），目前只做到了剥离不采信"。

### Q4.4 鉴权黑名单：为什么独立脚本只判 `exists`？为什么保留 fail-open 降级？

**问题**：黑名单你怎么查的？Redis 挂了是不是全都登不进？

**设计意图**
- **黑名单只回答一个问题**："这个 jti 是否被吊销"。独立脚本只有一行逻辑：
  `if redis.call('exists', KEYS[1]) == 1 then return 0 end return 1`（`gateway/AuthGlobalFilter:144-146`）。
- **为什么不复用 refresh 那条脚本**（`AUTH_CHECK_SCRIPT`）：那条脚本第二段是
  `local v = get(KEYS[2]); if not v then return 0 end`，判定的是"**refresh key 是否存在**"。
  主流程手里只有 access token，而白名单 key 是 `auth:refresh:{refreshJti}`，**access 的 jti 与 refresh 的 jti 是两个不同值**
  （签发时各自 `newJti()`）→ `auth:refresh:{accessJti}` **永远不存在** → 脚本恒定返回 0 →
  调用方把 0 判成"命中黑名单" → **每个 access token 都被判已吊销**（`gateway/AuthGlobalFilter:133-142`）。
- **一次 Redis 往返同时做两件事**（刷新流程需要"黑名单 + 白名单 + userId 一致性"三者同时成立）：
  拆成多条命令会在命令之间留时间窗（查完白名单到返回时令牌可能刚被 logout），放进单条 Lua 才是**同一原子快照**
  （`:99-104`）。返回值语义 `1 / 0 / -1`，`-1` 表示"refresh 存在但 userId 不匹配（疑似令牌拼接）"要额外打 WARN（`:105-107、319-325`）。

**为什么保留 fail-open**
- **可用性取舍**：Redis 异常时按放行处理，收益是**整站不会因 Redis 抖动全线 401**（连未登录的浏览请求都进不来）；
  代价是故障窗口内**已注销 / 被踢下线的令牌仍能通过**，即"提前失效"的能力在窗口内暂时失效
  （令牌本身仍在自身有效期内，**不是新增长期风险**）（`gateway/AuthGlobalFilter:387-391、433-437`）。
- **两类"拿不到结论"的口径相反，不得混为一谈**：Redis 异常 = **fail-open**；
  脚本无返回值（异常输入，不是 Redis 故障）= **fail-closed 按 0 拒绝**（`:387-392、407-414`）。
- **缺口如实写在注释里**：本类**只打 ERROR 日志、没有降级指标、没有告警规则**，
  "降级正在发生"只能靠检索日志发现，并**禁止改成静默返回或降级为 WARN**（`:69-71、273-275`）。

**踩过的坑（就是 5.1 那个 bug 的"余波"）**
- 修复方案不是"把哨兵 key 换成真实 refresh key"——**实测这条走不通**：一次真实登录里
  access jti=`7cd9929b…` / refresh jti=`12fc848e…`，`EXISTS auth:refresh:{accessJti}` = **0**、
  `EXISTS auth:refresh:{refreshJti}` = **1**，用 access jti 跑那条脚本仍返回 0（=401）（`gateway/AuthGlobalFilter:138-139`）。
  **所以只能新增独立脚本。**

**溯源**：`gateway/AuthGlobalFilter:99-141、319-325、387-415、417-438`；`gateway/AuthGlobalFilter:136-146`。

**边界／别说过头**：**会话失效水位**也有两条刻意的取舍，**不得当成缺陷"修掉"**：
① 旧版本令牌**没有 `iat`** 时跳过校验并放行（否则灰度发布瞬间全站在用令牌集体失效）；
② 水位值不是时间戳时放行并打日志（`gateway/AuthGlobalFilter:241-247`）。
被问"这两个不是漏洞吗"就答：**是取舍，代价写在那儿了（无 iat 的旧令牌改密后仍可用，直到自然过期）**。

### Q4.5 ES 检索：为什么"索引存在但为空"才降级，而不是"索引不存在"就降级？

**问题**：ES 挂了怎么保证搜索可用？索引没数据呢？

**设计意图**
- **原设计的回落只在 ES 抛异常时触发**（`search/SearchServiceImpl:182-188`）。
  问题在于 **ES 对"索引存在但没有文档"的查询返回 `200 + 0 命中`，不抛异常** ——
  于是 `catch` 里的回落分支**形同虚设**：新环境建了索引却忘了灌数时，搜索页**静默返回空列表**，
  既不回落、也不打 WARN（`search/SearchServiceImpl:174-178`）。
- **补的判定必须很窄**：只有"**命中 0 条** **且** 索引里**一条文档都没有**（`esGateway.count() == 0`）
  **且** MySQL 读模型**有数据**"才回落（`:170-172、229-246`）。
- **为什么不能"命中 0 条就回落"**：关键词本来就可能没有门店命中（例如搜一个不存在的词），
  那时 ES 与 MySQL **都应当返回空**；把它当故障判据会让每次正常空结果都去打 MySQL（`:218-224`）。
- **为什么要缓存判定**：一旦高发（索引真丢了），每次检索会多打一次 ES count + 一次 MySQL count 两次往返；
  判定结果缓存 **10 秒**（原注释里有一处写 60 秒，**以常量 `10_000L` 为准**）（`:92-99、229-233`）。
- **反向失效**：任何一次命中非 0 条都会把判定时刻清零 —— 于是"**原来有数据、随后被清空**"这一最常见的变化
  在下一次检索就立刻被识别，不必等缓存到期（`:173-178`）。
- **`engine=es` 语义不变**：该模式**依然不回落**，保证"纯 ES"观测口径不被污染（`:182-186`）。

**踩过的坑（三态对照实测，这是本条的含金量）**

| 索引状态 | `/search/engine` | `/search` 返回 | 结论 |
|---|---|---|---|

### Q5.1 鉴权黑名单 bug：为什么所有带鉴权的请求都 401，而前几轮测试全绿？

**是什么**
- 只要请求**带 access token** 且命中需要鉴权的路径，网关一律返回
  `401 {"code":401,"msg":"登录状态已失效，请重新登录"}`（原因码 `revoked`）（`gateway/AuthGlobalFilter:471-483`）。

**怎么发现（这是故事的关键）**
- **白名单路径（`/items`、`/search`）完全不受影响** → **此前几轮只测白名单时完全看不出问题**；
- **MallE2E 走到第一个带鉴权的写请求（`POST /carts`）就崩在这里**（`scripts/MallE2E.java:85`）。
- 实测：登录成功拿到 token 后 `GET /users/me` **恒 401**；修复后同一请求返回 **200 + 用户资料**。

**怎么定位**
- 黑名单判定复用了 refresh 白名单那条脚本，主流程给 `KEYS[2]` 传了一个**恒不存在的哨兵 key**
  （`auth:\u0000no-such-key`），于是脚本**恒定**走 `if not v then return 0`；
  而调用方把 `code == 0` 判成"命中黑名单" → **每个 access token 都被判已吊销**
  （`gateway/AuthGlobalFilter:136-141`；`gateway/AuthGlobalFilter:133-142`）。
- **关键否证**（这一步救了整个方案）：本来想改成"传真实 refresh key"，
  实测一次真实登录：access jti=`7cd9929b…` / refresh jti=`12fc848e…`，
  `EXISTS auth:refresh:{accessJti}` = **0**、`EXISTS auth:refresh:{refreshJti}` = **1** ——
  **两个 jti 不同源，方案 B 修不掉**，只能用独立脚本（`gateway/AuthGlobalFilter:138-139`）。

**怎么修**
- 新增 `BLACKLIST_CHECK_SCRIPT`（**只判 exists**），`isBlacklisted` 改用它 + `REDIS_BLACKLIST + jti`；
  refresh 的存在性仍由 `tryRefresh` 用原脚本判定（那条路径的 payload **就是 refresh token**，jti 对得上，逻辑正确，未改）
  （`gateway/AuthGlobalFilter:144-146`；`gateway/AuthGlobalFilter:417-438`）。

**怎么验（4 步正/负验证，双向可逆）**
1. 无 token → `401 未登录`；2. 有效 token → **200 + 用户资料**（修复前恒 401）；
3. 手动写入 `auth:blacklist:{jti}` → **401 登录状态已失效**（**吊销仍然有效**，不是把鉴权关掉）；
4. 删掉黑名单 key → **200**（`gateway/AuthGlobalFilter:429-435`）。
端到端：同一份改动在 scratch 副本里先构建并跑完整 MallE2E —— **37 项通过 / 0 失败**（`docs/P-03-Seata-AT对照-2026-10-17.md:146-151`）。

**闸门表现**：第 1 道闸门如期拦下，重建基线后 diff **只有 1 行**
（`AuthGlobalFilter.java fp1 56a7ea70ac3b → ead1520e6f73`）；第 4 道闸门还抓到我写在 Javadoc 里的
Markdown 粗体（`docs/注释验收清单-2026-10-15.md:264-266`）。

**溯源**：`docs/internal/M2-进展与验收.md:35-40`；`gateway/AuthGlobalFilter:133-146、417-438`。

**这个故事怎么讲**（结构模板）：**症状范围异常**（只有带鉴权路径挂）→ **为什么之前全绿**（测试覆盖偏了）→
**根因是"复用了语义不同的脚本 + 哨兵 key"** → **否证一个看似正确的备选方案**（jti 不同源）→
**独立脚本 + 双向可逆验证** → **闸门只允许 1 行 diff，防止顺手改坏别的**。

### Q5.2 支付口令拆分：为什么"加一列"这一步不能只加列？

**是什么**
- 用户表原本只有 `password` 一列，余额支付也用它校验。拆成 `password`（登录）+ `pay_password`（支付）两列
  （`user/UserServiceImpl:57-67`）。

**怎么发现的（有两层）**
- **第一层（设计层）**：两种口令的强度要求相反（登录要不可预期 / 支付要可预期），合在一列必然有一边妥协
  ——这是设计推导，不是线上事故（`user/UserServiceImpl:62-65`）。
- **第二层（落地层，真踩到了）**：补完 60 号脚本（把全库 `pay_password` 统一成 `bcrypt(123456)`）**不足以让冒烟变绿**。
  因为 `deductMoney` 在密码校验通过后还有一道"**初始口令强制改密**"拦截，而 Jack 的支付口令仍是初始值 `123456` →
  **余额支付必被拒**；而改密接口 `POST /users/pay-password` 要求**短信验证码**（`@NotBlank`），**冒烟脚本无法自给** →
  "脚本内先改密再支付"这条路走不通（`user/PayPasswordFormDTO:34`）。

**怎么修的（注意口径，别说过头）**
- **只改演示口径**：E2E 新增常量 `DEMO_PAY_PW = "888888"`，两处支付调用改传它；
  **登录口令保持 `123456` 不动**（`/users/login` 那行与断言逐字未改）——
  改的只是"支付口令"这一个口径（`scripts/MallE2E.java:39`）。
- **被绕开的是什么，注释里写清了**：绕开的只是"演示账号从未改过密"这一个状态，**不是那条拦截本身**，
  生产安全语义不变（`scripts/MallE2E.java:37`）。
- **迁移路径写死在类注释里**：`ADD COLUMN`（明文占位默认值）+ 把占位值改写为 BCrypt 哈希的 `UPDATE`
  **两步都不可跳过**，缺第二步会让存量账号的余额支付因"明文与哈希对不上"而不可用
  （`user/UserServiceImpl:69-71`）。

**怎么验（改完怎么证明没把安全语义改掉）**
- 闸门第 1 道如期拦下：`[FP1 代码被改动!] scripts/MallE2E.java` —— "代码确实变更了"属**重建基线**的情形；
  重建后 diff **只有 1 行**（`MallE2E.java fp1 abc8586… → 389c666…`，注释行 15 → 29，总行 271 → 272），
  其余 289 个 Java 文件逐条未变（`docs/注释验收清单-2026-10-15.md:254-261`）。
- 第 4 道闸门又抓到我写在类注释里的 Markdown 粗体 1 处，已去掉 —— **闸门在正常工作，不是误报**（`docs/注释验收清单-2026-10-15.md:264-266`）。
- 之后整条写路径的账实核对仍精确成立（见 Q4.3 的"实测"两条）。

**溯源**：`user/UserServiceImpl:43-89、347-364`（含 60 号脚本的迁移路径 `:62-64`）；`sql/merged/60-user-pay-password.sql:5-14`；
补列脚本 `sql/merged/60-user-pay-password.sql` 的说明见 `sql/merged/60-user-pay-password.sql:1-7`。

**这题的加分点**：能把"**改代码 / 改数据 / 改演示口径**是三件不同的事"分开说清，
并且**没有**为了冒烟变绿去关掉那条拦截。

### Q5.3 连接池 5 导致的排队：怎么定位到"不是 MySQL 慢、也不是行锁"？

**是什么**：`POST /pay-orders` 在 50 并发下 Avg **1083ms**、P99 **2374ms**，比创建订单（57ms）慢约 20 倍。

**怎么发现**
- 压测只给出"这个接口慢"，但**总耗时回答不了"慢在同步 Feign / 支付单落库 / 单号生成"** ——
  三者处置方式完全不同（改调用方式 / 加索引 / 换生成策略）（`pay/PayOrderServiceImpl:133-152`）。

**怎么定位（分段计时 + 指标取证，可复现）**
1. **只读埋点**：`SegmentTimer` 在 `applyPayOrder` 的 `finally` 里**一条日志打完所有段**
   （一次请求一行，避免日志 IO 本身变成瓶颈；DEBUG 级、先判 `isDebugEnabled()` 再拼串）
   （`pay/PayOrderServiceImpl:118-183`）。
2. **分段结果**（n=1487）：`trade.queryOrderById#1` **4.4ms（0.4%）**、
   `pay.queryByBizOrderNo` **557.2ms（51.8%）**、`pay.save` **512.4ms（47.7%）**、`pay.idWorker.getId` **0ms**
   （`docs/P-01-...md:10-16`）。
3. **连接池取证**：`hikaricp_connections_max=5`、`active` **恒为 5**、`pending` **43~46**、`idle` **0**；
   **每次获取连接 517ms（排队）+ 每次使用 65ms（执行）** → 排队占 **89%**（`docs/P-01-...md:27-39`）。
4. **反证三条**（这是"定位"而不是"猜"的关键）：
   - **不是 Feign**：`trade.queryOrderById#1` P99 只有 22ms；
   - **不是 MySQL 慢/行锁**：全程 `Threads_running ≤ 7`、行锁当前等待峰值 **0**；
   - **不是单账号行锁竞争**：换 50 个账号（每人一条余额行）后 Avg 只降 **9.5%**（1185→1072），
     P99 降 30.6%，**吞吐仍被压在 ~25~26 单/秒**（与账号是否相同无关）
     （`docs/P-01-...md:113-127`；bench:245-262）。
5. **天花板能算出来且与实测吻合**：`5 ÷ 0.065 = ≈77 次 DB 操作/秒`；实测 4575 次 ÷ 60s = **76.3 次/秒**
   —— 已经贴着天花板（`docs/P-01-...md:41-48`）。

**怎么修（抬池 −47%）**
- 池 5 → 20：`POST /pay-orders` **Avg 1083→573ms（−47%）**、P99 **2374→950ms（−60%）**、
  整链路吞吐 **74.8→85.6 req/s（+14%）**；分段 `queryByBizOrderNo 557→326`、`save 512→233`
  （`docs/P-01-...md:198-219`）。
- **落地踩了个坑**：外部参数**盖不过 Nacos 下发的键**（5 种方式全失败），最后用**服务专属 dataId**
  `llmall-pay-service.yaml` 只覆盖一个键 → pay=20.0、其余 8 个仍 5.0，MySQL 连接总账 `8×5+20=60 ≤ 100`；
  改前 8 份 Nacos 配置**逐份备份 + 改后 sha256 回读比对全部一致**（`docs/P-01-...md:176-196、291-311`）。

**溯源**：`pay/PayOrderServiceImpl:118-183`；`docs/P-01-申请支付单耗时定位-2026-10-17.md:8-48、113-127、172-249、274-311`；bench:235-262。

**诚实收尾（这句一定要说）**：抬池**没让排队归零** —— `pending` 仍 30，且单次占用从 65ms 涨到 **221ms**
（DB 侧摩擦上来了）。所以"排队是主因"**证伪了一半、证实了一半**；
继续优化应做 **OPT-B（每请求 2 次取连接 → 1 次）**，而不是继续加大池（`docs/P-01-...md:221-247`）。

### Q5.4 ES 空索引静默空结果：三态对照怎么做的？

**是什么**：索引**建好了但没有数据**时，ES 返回 `200 + 0 命中`（不抛异常）→ 检索**静默空结果**、
不回落、不打 WARN，**只有 `/search/engine` 的 `esDocs:0, consistent:false` 能看出来**（bench:115-124）。

**怎么发现**：压测做**三态对照**，同一台容器 ES、同一个关键词 `火锅`：
① 索引有 30 条 ② 索引被删 ③ **索引存在但为空**。
发现台账原来**猜错了一半**："ES 对索引不存在返回 200+0"**不成立**（会抛 `index_not_found_exception`，
`engine=auto` 正常回落 MySQL，`total=2`）；但**更隐蔽的另一半成立**（bench:111-127）。

**怎么定位/判据**：`/search/engine` 返回的 `esDocs` 与 `consistent` 是唯一线索；
判据必须收窄成"**esDocs=0 且读模型非空**"（见 4.5）。

**怎么修**：`doSearch` 增加"命中 0 条 → 判定空索引 → 回落 MySQL"，判定**缓存 10 秒**且"命中非 0 即清零缓存"
（`search/SearchServiceImpl:95-102、162-181、229-246`）。
**为什么选"检索侧降级"而不是"建索引时自动 reindex"**：建索引那一刻读模型通常**还是空的**
（全新库顺序是"建索引 → 起服务 → `/search/view/rebuild` 才灌读模型"），自动 reindex 会写出 0 条，
**缺口的触发条件并不会被消除**（bench:132-137）。

**怎么验**：修复后空索引 `total=2` 并打 WARN；**负例（有数据但关键词无命中）仍 `total=0`**，没有误降级；
空索引 50 并发 × 60 秒 117,194 请求、错误率 0%（bench:146-164）。

**溯源**：`search/SearchServiceImpl:95-106、162-246`；bench:111-164；台账 C-03/OBS-02（台账:59、108）。

**这题的价值**：证明的是"**我验证了台账里的猜测，发现它一半错了一半更隐蔽**"，
而不是"我发现了一个 bug"。**三态对照**这个方法本身就是加分项（见 6.4）。

### Q5.5 Lombok 与 JDK 25 不兼容：为什么"闸门全绿"不等于"能构建"？

**是什么**：项目用 Lombok 1.18.30 做注解处理（`llmall/pom.xml:45`），它**打不开 JDK 22 以后版本的内部 javac API**，
在 JDK 25 上 `mvn package` 会以**注解处理崩溃**收场（`gates/gate-env.ps1:96-97`）。

**为什么这是"坑"而不是普通报错**
- 失败方式**极具误导性**：报错落在**某个业务类的编译上**，看起来像"代码写错了"，于是人会去翻代码而不是怀疑 JDK；
- 更糟：**只跑分析闸门时它还是绿的**（指纹闸门不编译），于是"`verify-all` 通过"**并不代表能构建**
  （`gates/gate-env.ps1:97-99`）。

**怎么修的**：把版本判断**前移到环境解析那一刻** —— `Assert-GateJavaSupported` 在主版本不在 `[11,17]` 时
**打印可操作提示并抛异常终止**，返回区间内主版本号才继续（`gates/gate-env.ps1:107-108、122-167`）。
两个实现细节值得讲（说明踩过）：
- **用 `throw` 而不是 `exit`**：本文件是被点源（`. gate-env.ps1`）进调用方作用域的，
  `exit` 在点源文件里**只结束本文件、不会结束调用方脚本** —— 实测调用方会继续跑完并最终以 **0** 收场，**等于闸门没拦**（`:125-127`）；
- **变量名坑**：不能叫 `$home`，PowerShell 7 把 `$HOME` 当只读自动变量，赋值报错（`:128-129`）。

**实跑证据（本次真实执行，见附录 C）**
```
【停止】JDK 版本不满足要求，闸门不启动
  当前 JAVA_HOME : <JDK>
  当前 java -version : java version "25.0.2" 2026-01-20 LTS
  解析结果        : 主版本 25，超出支持区间 11~17
  原因            : 本项目 Lombok 与 JDK 25 不兼容，请用 JDK 11
  ... throw: 本项目 Lombok 与 JDK 25 不兼容，请用 JDK 11（支持区间 11~17...）
```
**退出码 1**；把 `JAVA_HOME` 指向 JDK 11 后同一命令 **退出码 0 / 结论: 全绿**。

**渊源**：这条是**既有环境限制**，不是本次引入的 —— M1 验收里就写着"PATH 默认 JDK 是 25，
本工程必须显式用 `<JDK11>`"（`docs/internal/M1-进展与验收.md:91`）。

**溯源**：`gates/gate-env.ps1:94-167`；`gates/README.md:21`；`llmall/pom.xml:45`；`docs/internal/M1-进展与验收.md:91`；附录 C。

**边界／别说过头**：闸门**不会替你切换 JDK、不会改 `JAVA_HOME`**（注释里"严禁"），
理由是"**证据里记录的版本必须就是实际跑的版本**"（`gates/gate-env.ps1:105-106、167`）。这句话是这套闸门最值钱的地方。

- **分层的逻辑（能讲清这句就赢了）**：**1–3 证明"没改代码"，4 证明"该删的删干净了"，

### Q6.2 三态退出码怎么支持 CI 分级？

**问题**：闸门红了怎么处理？团队会不会把红当成常态？

**答案要点**

| 退出码 | 含义 | 该怎么办 |
|---|---|---|
| `0` | 全绿 | — |
| `1` | **硬闸门失败** —— 闸门失效，或出现未登记的违规 | **必须修**，不得继续 |
| `2` | 硬闸门全过，台账闸门报出**已登记**的待处理偏差 | 逐条核对《已知偏差台账》，确认每条都有 owner 与触发条件 |

- **为什么必须三分**：把"闸门失效"和"已登记偏差"压成同一个非零码，会逼出两种坏行为 ——
  **要么把真实违规当"已知问题"放过去，要么为了消红去改台账而不是改代码**（`gates/README.md:66-68`）。
- **实现方式**：硬闸门 `exit 1`、仅台账偏差 `exit 2`、全绿 `exit 0`（`gates/verify-all.ps1:160-168`）；
  分类在入口就声明：硬闸门 ①~⑤（必须绿）、台账闸门 ⑥⑦（允许红，红的每一条都必须在台账里找到）（`:19-20`）。
- **怎么支持分级**：
  - CI **阻塞门禁**只认 `0`；`1` 直接失败；
  - `2` **允许通过但必须留痕**（把台账 diff 贴进 PR 描述），相当于"把技术债显式化"而不是"把红灯关掉"。
- **一个反面案例（讲出来更有说服力）**：内容质量闸门曾经**打印了"待清理 1 处"但退出码是 0** ——
  **闸门只是在"说话"，不是在"拦人"**；这条是**注入式验收**（故意放 3 处违规）当场抓出来的，
  说明"闸门红了要能拦住流程"这一条**本身也需要被验证**（`docs/注释验收清单-2026-10-15.md:261、308-315`）。

**溯源**：`gates/README.md:58-68`；`gates/verify-all.ps1:16-20、160-168`；`docs/注释验收清单-2026-10-15.md:261、308-315`。

### Q6.3 台账机制：39 行怎么做到"全归属"？

### Q6.4 压测方法论：账实核对 / A/B 对照 / 三态对照

**问题**：你的压测数字可信吗？你怎么排除"测错了"？

**答案要点（三个方法，各举一个实例）**
1. **账实核对（红线：必须精确成立）**——不只看 QPS，必须核"钱对不对"：
   50 并发 60 秒后 余额减少 **35,097,600 ÷ 25,600 = 1371.0**，与**支付成功次数精确相等**，
   `balance_flow` 新增 1,371 条一一对应；`COUNT(DISTINCT biz_order_no)` = 总条数（一单一张支付单）
   （bench:168-177）。**任何一轮压测的最终判据都是这个，不是吞吐**。
2. **A/B 对照（消除混淆因素）**——第一轮 50 线程**共用 Jack 一个账号**，混进了"抢同一行余额"的锁竞争；
   第二轮造 50 个账号（`bench1~bench50`，各自一条余额行）对照：Avg 只降 **9.5%**、P99 降 **30.6%**，
   但**吞吐仍被压在 ~25~26 单/秒（与账号是否相同无关）** → 指向"**与用户无关的全局串行点**"（bench:235-262）。
3. **三态对照（区分"正常空"与"故障空"）**——ES 检索在同一台容器、同一关键词下做
   **索引有数据 / 索引被删 / 索引存在但为空** 三态（bench:115-124），
   才把"索引不存在 200+0"这个**错误猜测**和"索引存在但为空静默空结果"这个**真缺口**分开（见 5.4）。

**支撑证据的三个"反直觉"细节**
- **用 SQL 条数而不是延迟证明 N+1**：延迟随并发上升可能只是 CPU 饱和，不能当证据；
  所以用 `Com_select` 增量 ÷ 请求数，得出 `/feed` ≈2.01（收件箱非空时）、`/items/page` 恒 2.02 且与 pageSize 无关（bench:91-105）。
  **但要把覆盖缺口说在前面**：`/feed` 的 1.0 条是"收件箱为空提前返回"的分支
  （`content/FollowServiceImpl:242-244`，种子数据无关注关系，见 4.2 的 ⚠ 条），
  **非空收件箱的 2 条路径那次没压到** —— 诚实地说"这条我压得不完整"，比被问出来强。
- **资源红线与熔断是脚本化的**：并发封顶 100、JMeter 堆 `-Xmx512m`、每 5 秒采样宿主、
  CPU 持续 >90% 达 30 秒 / 内存 >90% / 盘 <5GB 直接停 JMeter 并标 `Aborted`（bench:35-41）。
  **独立进程采样**，理由是"JMeter 自己就是被测压力的一部分，让它监控宿主等于让被测方自证"（bench:304-308）。
- **写压测前记水位线、压完回滚并复核**：`SmokeRollback capture/rollback`（bench:41、292-296）。

**溯源**：bench:2-5、35-41、89-107、109-125、164-186、202-229、259-275；
`gates/README.md`（闸门部分）；`docs/P-01-...md:130-149`（账实核对表）。

**边界／别说过头**：见 7.1。**同一台宿主**、**非隔离环境**、**为腾内存停过部分服务**、
**100 并发是硬上限**（bench:311-324）。这些是**方法论的边界**，说清楚反而更可信。

### Q6.5 闸门自己的缺陷怎么固化？（5 缺陷 → 34 用例）

**问题**：你的闸门凭什么可信？如果闸门自己错了呢？

**答案要点**
- **前提认知**：**闸门本身也会出错，而且出错时不报警** —— "带缺陷的闸门比没有闸门更危险：
  它会放过真实损伤，或诱导出错误的『修复』"（`gates/selftest.ps1:3-8`）。
- **5 个真实缺陷**（每个都有"后果"和"修法"，能讲出 2 个就够）：

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | `verify` **只看 FP1、忽略 FP2** | 输出打印 `[FP2 格式被改动]` 却仍给"结论: 通过" + `exit 0`；**只改书写形态**（两行合成一行、改缩进、吞行尾换行）被放过；且与 `check` 模式口径不一致 | 两个 `verify` 同时判 FP1 与 FP2；"未被基线覆盖"也算失败 —— **未覆盖 ≠ 已证明** |
| 2 | `--[[`（4 字符）与 `#`（1 字符）的**长度陷阱** | 剥离器固定按 2 字符比较 → 块注释内部与 `#` 注释行被当成代码行 → **改注释反被判成改代码** | 按注释符**实际长度**比较；剥离逻辑抽成单一实现 `strip.ps1` |
| 3 | `历史叙述` 正则**误伤规范推荐措辞** | "误改后果"里含"改后"→ 被判历史叙述 → 执行者被迫绕开规范**要求**的写法 | 加 `(?<!误)` 守卫 |
| 4 | 内容质量闸门**报错但退出码 0** | 打印"待清理 1 处"却 `exit 0`；调用方按退出码判断时当 PASS | 加 `exit 1`；这条是**注入式验收**当场抓出来的 |
| 5 | `feign-lint` 用"**文件里出现过客户端类名**"判断是否使用 | 把 `item-service` 的**注释提及**当成"2 个写调用"（误判） | 判据改为**注入点**；item 现正确显示"无需（无写调用）" |

（缺陷 1–4 见 `docs/注释验收清单-2026-10-15.md:254-266`；缺陷 5 见台账 F-04（台账:91）与 `gates/feign-lint.ps1:38`）

### Q7.1 "你这 QPS 能上生产吗？"

**诚实答案要点**
- **不能直接用这个数字对标生产**。口径是"**单机同构对比**"：**JMeter 与被测容器跑在同一台宿主上、
  抢同一批物理核**；所以绝对值不可对标，**只有同环境下的梯度变化可信**（bench:32、346）。
- **主机规格**：i7-14650HX（16 物理核 / 24 逻辑核）、15.8GB、被测形态是 Docker 容器
  `mem_limit 256m` / `-Xmx192m`，**非隔离**（宿主同时还跑浏览器、IDE、一台 4GB VM）（bench:23-33）。
- **本机压测上限 ≈ 100 并发（硬上限）**：再往上会先撞内存 90% 熔断，**不是压出更多信息**；
  更高并发需要更强机器或远程压测环境，**不得在本机加码**（bench:347-351）。
- **能给出的可信结论是"结构性的"**，例如：
  Feed 读路径 **2.0 条 SQL/请求**（收件箱 1 + 批量笔记 1，与页大小无关）→ 无 N+1；写路径**零重复扣款**（账实核对精确）；
  `POST /pay-orders` 的瓶颈是**连接池排队**而不是 SQL/Feign（P-01 分段证据）；
  `GET /items/page` 的容量上限**由限流阈值决定**（bench:56-61）。

**边界提示**：如果被追问"给你一台 32 核机器能到多少"——**不要报数**。
正确答法是"**瓶颈已经定位到具体环节**（连接池排队 / DB 侧 fsync / 限流阈值），换机器后要重新跑同一套
A/B 与账实核对才有数；方法可复现，数字不可外推"。

### Q7.2 "trade 服务挂了，支付会怎样？"

**诚实答案要点（按下单/支付两条路分开说）**
- **余额支付链路会先失败在"回查交易订单"这一步**：`tryPayOrderByBalance` 扣款前**必须回查交易订单**并比对金额
  —— 订单侧有超时未支付自动关单，用户关单后再付就会变成"订单已关闭、余额却扣了"（`pay/PayOrderServiceImpl:278-297`）。
  trade 挂 → 这次查询失败 → **扣款不会发生**（这一步在扣款之前），支付单归位、锁释放。
- **扣款之后的情况才危险**：`markPayOrderSuccess` 之后"通知交易域改订单状态"的消息**发送失败不影响支付本身**，
  由对账兜底（`pay/PayOrderServiceImpl:317-322`）。所以 **trade 挂的窗口内，支付侧可能已成功、订单仍是待付款**。
- **兜底链条**：本地消息表重试（退避上限 10 分钟）→ 对账任务**问下游**（积分流水 / 消费记录在不在）→
  连续 3 轮"状态未知"升级 ERROR 提醒人工（`trade/OrderReconcileTask:19-47`）。
  **注意对账任务本身跑在 trade 里**：trade 整个挂掉时，**对账也停**，恢复后才追平 —— 这个盲区要主动说。
- **交易域自己的下单侧也有补偿**：下单事务未提交但库存已扣 → 自动回补库存；
  补偿失败打【需人工介入】（`trade/OrderServiceImpl:324-331`）。

**边界提示**：**没有**"trade 挂了支付侧自动冻结"这类熔断联动；
Sentinel 只保护 `itemPage` 一个资源，且**资金与库存链路刻意不做自动降级**
（"把扣库存失败降级成成功就是超卖，把支付状态未知降级成未支付就是资损"）（`common/SentinelRuleConfig:17-23`）。

### Q7.3 "Redis 锁过期了怎么办？"

**诚实答案要点**
- **锁 TTL 30s 不续期**（没有看门狗）。TTL 取值依据：一次余额支付 = 最多 2 次同键扣款尝试 + 一到两次本地条件更新，
  正常耗时远小于该值（`pay/PayOrderServiceImpl:68-75`）。
- **锁过期后的后果不是资损，是并发放大**：并发请求即可拿锁并通过"待支付"检查；
  但拿到锁之后**还有第二道裁决** —— `claimDeductAttempt` 的条件更新（要求 `status` 仍为 1）决定谁能继续，
  最终去重落在**下游余额流水唯一键**上（`:224-235`）。
- **所以锁是优化，不是安全边界**：原话"锁失效不会造成资损，但会放大下游的并发冲突"（`common/IdempotentKeys:164-165`）。
- **释放也必须防护**：值一致才删（`if get(KEY)==ARGV[1] then del`），直接 DEL 会误删"锁超时后别人刚拿到的那把"（`:75-78`）。
- **锁 TTL 调小的真实危险**：一次支付还没结束锁就自动过期 → 并发请求拿到锁并通过待支付检查 →
  同一支付单出现多个支付尝试（`:70-72`）。

**边界提示**：**没有**实现"自动续期 / 重入 / 公平锁"（不是 Redisson）。被问"为什么不用 Redisson"就答：
**当前只有一处锁、且锁不是正确性依赖**，引 Redisson 是为了一个不需要的能力；
如果将来锁需要承担正确性（例如防重入的业务），再引既有库而不是自己写看门狗。

### Q7.4 "为什么不用 Seata 做全链分布式事务？"

> **本轮（2026-10-17）已经把它跑通并做了对照**，所以这题从"没做"变成"做过、有数据、有判断"。
> 完整证据见 `docs/P-03-Seata-AT对照-2026-10-17.md`。

**诚实答案要点（先结论 → 再理由 → 再数据 → 最后边界）**
- **结论：分层，不搞全链**。用户等结果的短链路（扣库存、核销券）适合强一致；加积分、加销量、发通知
  这类**允许延迟**的动作放进全局事务只会拉长锁持有时间（README:77-83）。
- **理由（技术性）**：
  1. 全局事务会**把远程调用的等待时间变成锁持有时间** —— 抬池实验已量化过代价：余额支付 `@Transactional`
     内发 Feign 扣款，连接被整段占住，抬池后 **Avg 反升到 953ms**（台账 OPT-D）；
  2. 允许延迟的动作**天然不需要强一致**，本地消息表 + 重试 + 对账更简单可解释；
  3. 换来的兜底是真实故障场景都有去处（消费者停机、消息重复投递 1000 次 → 零丢单、零重复扣减，README:252-257）。
- **现状（按"五层"答，别笼统说"没做"也别笼统说"做了"）**：

| 层 | 状态 | 证据 |
|---|---|---|
| ① 依赖与角色 | ✅ | trade=TM，item/promotion=RM（`M8-Seata与ES落地.md:11`） |
| ② 配置 | ✅ 代码里保留完整配置段；**开关默认 `false`**（对照实验期曾三开关同开，实测后已回落） | `seata.enabled: false`：trade `trade-service/application.yaml:22`、item `item-service/application.yaml:20`、promotion `promotion-service/application.yaml:5`（实验期改 true 那版基线见 P-03 第七节） |
| ③ 注解 + 互斥守卫 | ✅ | `@GlobalTransactional(name="llmall-create-order")`（`trade/OrderServiceImpl:108`）；守卫在 `:213-219` |
| ④ 服务端 | ✅ **VM 上一直活着** | Nacos `SEATA_GROUP@@seata-server` → `<vm-ip>:8091`，`healthy=true`；控制台 7091；`store.mode: db` |
| ⑤ **真正跑起来** | ✅ **已跑通（含回滚）** | 见下面三条判据 |

- **三条硬判据怎么验的（这是最能加分的一段：验收方法本身有坑）**：
  1. **`undo_log` 落行**：`item` 1→2、`trade` 0→2；
  2. **TC 有分支**：飞行中采到 `global_table=1 / branch_table=3 / lock_table=5`；
  3. **守卫被跳过**：DEBUG 命中"Seata AT 已开启，库存回滚交给全局事务"4 次，**本地补偿日志 0 条**。
  > **坑**：**事后查这两张表必然是空的** —— AT 在二阶段提交成功后会**异步清理** undo_log 与 TC 会话。
  > 所以"事后为空"**不能**证明"没跑"，必须**在飞行中高频采样**（本轮用 150ms 轮询抓到的）。
  > 同理，日志里的 `SeataFeignBuilderBeanPostProcessor ... NEVER_RETRY` **不是**事务在跑的证据（那是 SCA 的 Feign 自动配置）。
- **回滚实证（比提交更重要，因为这是资损防线）**：用 trade 自带故障注入在扣库存后人为失败 →
  item 侧 `RmBranchRollbackProcessor` → `AbstractUndoLogManager` 读 undo 反查 → **`Branch Rollbacked result: PhaseTwo_Rollbacked`**，
  且 **`stock` 176 →（扣 1→175）→ 176 不多不少**、本地补偿日志 0 条 → **守卫与 TC 没有双回滚**。
- **对照数据（50 并发 × 60s，多账号，两态只差开关；两态账实核对都精确成立）**：

| 指标 | ON（AT） | OFF | 变化 |
|---|---|---|---|
| 整链路吞吐 | 58.5 rps | 73.9 rps | **−20.8%** |
| 整链路 Avg / P99 | 791.1 / 2,004 ms | 626.1 / 1,747 ms | +26.4% / +14.7% |
| **`POST /orders` Avg** | **247.7 ms** | **68.9 ms** | **+259%** |
| `POST /pay-orders` Avg | 1,250.5 ms | 1,073.2 ms | +16.5% |
| 余额差额 ÷ 25,600 = 成功次数 | 28,876,800 ÷ 25,600 = **1,128** | 36,838,400 ÷ 25,600 = **1,439** | 两态都精确 ✅ |

- **一句话总结**：
  "**AT 的代价是每个订单多出 TM 开启 + 分支注册 + 二阶段通知，`POST /orders` 从 69ms 涨到 248ms（+259%），
  整链路吞吐 −21%；而收益只在下单失败回滚时才兑现。所以我实测完的结论是：默认关，留给'券与库存不能有中间态'
  这类需求来开启。**"
- **一个必须主动交代的耦合**：**三个开关必须同进同退**。SCA 的条件是
  `${seata.enabled} && ${enable-auto-data-source-proxy}`（读字节码得来），item/promotion 关着就**没有 RM**；
  而 trade 在 `seata.enabled=true` 时会**跳过本地库存补偿**。**只开 trade** → 守卫跳过但 TC 覆盖不到 item →
  **下单失败时库存无人回补（少卖）**。这条已登记台账 S-10。
- **`undo_log` 还有一个缺口**：`01-undo-log-all.sql` 未给 `llmall-search` 建 `undo_log`，
  给 search 开全局事务会报表不存在（台账 S-05）。
- **还有一个版本问题（本轮发现，未修）**：客户端 `1.6.1` 对服务端 `1.5.2`（官方要求服务端 ≥ 客户端，当前倒挂），
  且 jar 内 `seata-all-1.6.1` 与 `seata-core/common/discovery/config-1.5.2` 混装（台账 S-11）。
  若被问"那你们版本对齐了吗"，**照实说没对齐、已登记、是开启 AT 的前置条件**。

**边界提示（三条不许说过头）**：
1. **不要再说"Seata 没做"**——已经跑通并对照过了；也**不要说"生产在用"**——实测后默认已回落 `false`。
2. 压测是**单机同测口径**，绝对值不可对标生产，**只有同环境下 on/off 的差**可信。
3. 收益要说清**边界**：AT 只覆盖"本地库 DML 的分支回滚"，**不覆盖 redis 锁、不覆盖 MQ 投递**；
   消息那条链路仍然是本地消息表 + 重试 + 对账（分层没变）。

**如果被追问"那到底该开还是关"**：答"**已经定了：默认关（回落 `false`）**。因为 +259% 花在最热的写接口上，
而我们的失败兜底（补偿钩子 + 消息表 + 三重幂等 + 对账）已经过故障注入验证；真要开，前置条件是先对齐依赖版本 + 三开关同开（P-03 第七节）"。

### Q7.5 "还有什么是没做完的？"

**诚实答案要点（按"登记不排期"和"功能缺口"两类答，直接报台账编号）**

**A. 功能缺口（用户能感知的）**
- **C-01 Feed 超阈值跳过推送** → 大 V 粉丝看不到该笔记（已转 WARN 信号，**功能未补**）（台账:57、108）；
- **C-03 ES 空索引** → 已修（读侧降级），但**启动自检只有 ERROR 日志，没有指标与告警规则**（台账:59、26）；
- **C-04 评论举报/审核链路** → **写侧完全没有**，只有显示侧过滤被固化成单测（台账:60、136-149）；
- **C-05 `user_info.introduce` 无长度校验**（`VARCHAR(128)` 超长直接 DB 异常，不是可读的业务错误）（台账:61）。

**B. 登记不排期的优化方向（都用压测数据支撑，但按决定不动代码）**
- **OPT-B**：`applyPayOrder` 每请求取 2 次 DB 连接（无事务，SELECT 与 INSERT 各借还一次）→ 合成 1 次。
  **这是当前性价比最高的一步**（台账:191）；
- **OPT-C**：单次 SQL 连接占用偏高（抬池后 65ms → 221ms），怀疑与每次 INSERT 提交的 fsync 有关；
  **任何 `innodb_flush_log_at_trx_commit` 调整都是持久性取舍、属资损红线**（台账:192）；
- **OPT-D**：余额支付在**事务内部**发起远程调用，连接被整段占住。**风险最高**，必须小步走 + 每步过闸门 + 复跑压测 + 账实核对（台账:193）。

**C. 架构/平台侧的"没有"**
- **没有链路追踪**（Micrometer Tracing / SkyWalking 未做，只有 traceId 贯穿日志）（README:407）；
- **没有优雅停机之外的发布能力**（灰度、优雅发布未做）（README:408）；
- **Sentinel 规则未持久化到 Nacos**（控制台推送重启即丢）（README:409）；
- **Seata 默认关**（实测后回落）：AT 已跑通并有对照数据，但 `POST /orders` +259%、吞吐 −21%，故默认关（见 7.4）；
- **单测很少**：仓库内共 **5 个测试类**，且本机 `mvn test` **跑不了**（离线仓库缺
  `surefire-junit-platform` provider，台账:131-132）；能跑的验证入口是
  `gates\selftest.ps1`（34 用例）与 `scripts/MallE2E.java`（37 项）。
- **前端只有演示台**：`frontend/index.html` 是**单文件、零依赖、零构建**的演示页
  （`frontend/README.md:3`），**没有**路由 / 构建 / 权限菜单等业务前端形态。

**边界提示**：这一题答得好不好，取决于你**报编号而不是报印象**。
建议的顺序：**功能缺口（用户能感知）→ 登记不排期（有数据支撑但按决定不做）→ 平台能力缺失**，
最后补一句"**每一项都在台账里有 owner 与触发条件，触发条件出现才立项**"（台账:9）。
