# 支付与订单补偿可靠性改造

本轮范围：余额支付、取消/退款、订单用券、支付成功事件和相应前端状态。改造不改变金额单位（分），不替换现有微服务架构。

## 解决的问题与状态模型

| 场景 | 原风险 | 本轮处理 |
| --- | --- | --- |
| 支付失败退款后再次支付 | 复用已扣款的旧幂等键，未重新扣款却支付成功 | 每次支付生成持久化 attempt；新尝试使用新键，重复请求沿用该尝试的键 |
| 扣款响应丢失 | 无法判断是否应退款，异常留痕可能随事务回滚 | 用户域扣款/撤销共用操作行锁；撤销先到则保存墓碑，扣款先到则原子退款 |
| 支付与取消并发 | 查询未支付后，另一线程开始付款 | 支付域关闭未支付单时锁行；未建单时创建已关闭占位，阻止后续建单/支付 |
| 退款中核销 | 钱已退，但本地回滚又允许核销 | 先提交订单状态9；核销仅允许2；补偿全部确认后才关闭为5 |
| 库存/券/支付账本回写失败 | 只记日志，缺少重启后继续处理的依据 | 订单8/9是持久化待办；每30秒扫描重试幂等动作 |
| 券释放后复用、旧请求重试 | 旧退券误释放新绑定；迟到锁券绑定已取消订单 | 券行锁串行化操作，取消墓碑按券ID和订单ID永久保存，解绑限制订单号 |
| 支付成功消息发送失败 | 调用发送后即视作成功 | 成功 attempt 作为持久化消息待办，收到 broker ack 且未 returned 才标记已发送 |

支付状态：`1待支付 → 4处理中 → 3成功`；失败时 attempt `ACTIVE → CANCELING → CANCELED`，用户域撤销确认后支付单才回到1。另一条成功路径是 attempt `ACTIVE → SUCCEEDED`。成功尝试不再撤销。

订单状态：取消 `1 → 8 → 5`，退款 `2 → 9 → 5`，核销 `2 → 7`。8/9期间不可支付或核销。API返回取消/退款请求已受理，不代表所有远程步骤都已结束；客户端应刷新订单状态。

余额凭据：`PAYMENT_V2:<attemptId>`。同一个凭据的扣款和撤销在 `balance_payment` 行上串行，余额变化、流水和凭据状态在同一个本地事务内提交。撤销为 `CANCELED`（未扣）或 `REFUNDED`（已扣已退）；二者都禁止迟到扣款。

优惠券：`voucher_order_cancel(user_voucher_id, order_id)` 保存取消墓碑；即使锁券请求尚未到达也保留取消。另一订单可正常使用这张券，旧订单的重复释放不会改新绑定。

## 事务、恢复与消息边界

- `PaymentAttemptStore` 每次状态转换先锁支付单，事务内不调用远程服务；`BalancePaymentCoordinator` 负责事务之间的调用与补偿。
- 支付请求停在任意一步后，超过2分钟的 ACTIVE 尝试由恢复任务撤销；不保存、重放支付密码。CANCELING 持续重试，未确认撤销前不允许新支付。
- 订单补偿顺序：退款到账（仅9）→ 恢复库存 → 释放券 → 关闭支付账本（仅9）→ 订单关闭。每一步失败都保留8/9。下游幂等键沿用订单ID。
- `afterCommit` 的 MyBatis 会话仍可能含旧缓存；恢复阶段独立事务读取已提交状态，避免忽略刚写入的8/9。
- 定时扫描每批100条；失败任务推迟下次检查或更新时间，避免固定首批失败长期阻挡后续任务。多实例可能重复执行，正确性依赖数据库条件更新和下游持久化幂等。
- RabbitMQ确认只表示消息被 broker 接受并路由；不代表消费者已完成。消费者仍需幂等，死信队列仍需处理。`SUCCEEDED/notified=0` 的记录持续重投，不依赖请求线程存活。
- 日终 `PayReconcileTask` 保留为告警工具；其历史窗口不能替代全量财务核对。

## 现有环境升级步骤（必须维护窗口）

**不支持旧、新支付/交易/用户/营销写入实例混跑。** 新状态与扣款键不能只升级其中一个服务。此次代码交付没有执行任何业务数据库迁移，也没有部署服务。

1. 备份用户余额与流水、支付、交易、营销库。停止入口写请求，停掉并排空旧 user/pay/trade/promotion 实例、任务和相关消费者，确认没有在途旧扣款或锁券请求。
2. 核对旧支付状态4、`result_code=UNCERTAIN`，以及未支付单关联的旧 `PAY:<payId>:<amount>` 扣款流水。不能只查 UNCERTAIN，因为旧事务回滚可能把该标记一起撤销。根据真实余额、流水和订单决定补偿或推进；不能直接清空标记、改状态绕过检查。
3. 执行 `sql/merged/64-payment-recovery.sql`，使用遇错停止的 MySQL批处理客户端，**禁止 `--force`，不要使用遇错继续的交互式 SOURCE**。例如在 Bash 或 Windows cmd 中运行 `mysql --batch -u migration_user -p < sql/merged/64-payment-recovery.sql`（替换实际迁移账号），检查退出码为0且没有任何错误。脚本的临时唯一键守卫故意在旧未决数据存在时失败；看到 `llmall_payment_upgrade_guard` 重复键错误代表升级被阻止，必须先核对数据并退出该会话。
4. 脚本只新增三张表，不改余额、历史流水或订单。检查 `balance_payment`、`payment_attempt`、`voucher_order_cancel` 均存在、InnoDB、主键和索引完整。已有库先具备原 `04-balance-flow.sql` 等基础迁移；全新演示初始化已接入64脚本。
5. 同时部署新版 user/pay/trade/promotion 与相关 API依赖，部署新版前端；确认服务间令牌一致。支付服务必须实际启用 `spring.rabbitmq.publisher-confirm-type=correlated`、`publisher-returns=true`、`template.mandatory=true`。Nacos/环境变量如覆盖同名配置，以运行时有效值为准。
6. 先在测试账号验证下单→付款→退款；故障后确认4或8/9保留并自动恢复，再开放写流量。不要把“请求返回200”当作订单补偿已完成。

旧数据定位SQL（只读，具体处理需要逐笔核对）：

```sql
SELECT id, biz_order_no, status, result_code, result_msg
FROM `llmall-pay`.pay_order WHERE status=4 OR result_code='UNCERTAIN';

SELECT p.id, p.biz_order_no, p.status, d.user_id, d.biz_no, d.change_amount
FROM `llmall-pay`.pay_order p
JOIN `llmall-user`.balance_flow d
  ON d.biz_type='DEDUCT' AND d.biz_no LIKE CONCAT('PAY:',p.id,':%')
LEFT JOIN `llmall-user`.balance_flow r
  ON r.biz_type='REFUND' AND r.biz_no=CONCAT('PAYFAIL:',d.biz_no)
  AND r.user_id=d.user_id AND r.change_amount=-d.change_amount
WHERE p.status IN (0,1) AND r.id IS NULL;
```

回滚代码前仍须停流并核对全部新 ACTIVE/CANCELING、订单8/9以及未发送成功事件；旧代码不能识别这些待办。不要删除新表或墓碑，不要仅回退jar后恢复写入。新流程的余额流水与旧流水共同保留，实际故障优先向前修复。
