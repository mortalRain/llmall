# 事故复盘：Nacos 配置随容器重建全部丢失（2026-10-18）

> 一句话：`docker compose up -d --force-recreate nacos` 之后，Nacos 上一份配置都不剩，
> 应用侧大面积进入重启循环；其中 8 份能从仓库恢复，**1 份只存在于 Nacos，是真丢失**，
> 只能照着文档重建。根因不是"手滑"，是两处设计缺陷叠在一起：数据没落卷、配置没入库。

## 一、现象

按"重建一个容器"的常规操作对 nacos 执行强制重建后：

| 观察点 | 结果 |
|---|---|
| `docker inspect nacos -f '{{range .Mounts}}{{.Name}}{{end}}'` | 输出为空 —— 容器没有任何挂载点 |
| `GET /nacos/v1/cs/configs?...pageSize=100` 的 `totalCount` | `0` |
| 应用容器 | 9 个业务服务反复重启，日志停在拉不到 `shared-*.yaml` / `gateway-routes.json` |
| 重建前的同一条 `docker inspect` | 同样是空 —— 也就是说这不是"这次搞坏的"，而是从来没配过 |

第一条和最后一条合起来才是关键：**容器从来就没有卷**。之所以以前没出事，是因为以前没有执行过"删容器再建"，
一旦执行，"重建容器"就等价于"清空数据库"。

## 二、根因

分三层，缺任何一层都不会丢数据：

1. **运行期状态没落盘（直接原因）**
   `docker/docker-compose-infra-lite.yml` 里 nacos 服务原先没有 `volumes:`。standalone 模式的全部已发布配置
   都存在内嵌 derby 的 `/home/nacos/data` 下，这个目录在容器可写层里，容器一删就随之消失。
   镜像文档不会替人挂卷，也没法替你决定用不用卷。

2. **有一份配置只存在于运行态（为什么"从仓库重新导入"没能完全恢复）**
   8 份共享配置在 `nacos-config/` 里都有，一条命令就能重新发布。但支付域的服务专属 dataId
   （连接池上限 20）是当初调优时直接发到 Nacos 上的运行态配置，仓库里没有对应文件。
   它随着 derby 一起没了，且没有任何地方能回滚 —— 只能按
   `docs/P-01-申请支付单耗时定位-2026-10-17.md` §七 记下的结论重建。

3. **"每次启动都幂等导入配置"把第 2 层长期掩盖了（为什么一直没被发现）**
   `demo.ps1` 每次跑都会把 `nacos-config/` 全量导入一遍。它的效果是：无论 Nacos 上缺什么，
   启动流程都会顺手补齐。于是"仓库里少一份配置"这件事，在日常使用中**永远不会暴露** ——
   缺了也被补上，补上就当它存在。只有把 Nacos 单独重建、且不走导入流程时，才会露出来。

结论：这是一次**隐性依赖被显性化**，不是配置写错了。

## 三、修复

四处改动，按依赖顺序：

| # | 改动 | 文件 | 作用 |
|---|---|---|---|
| 1 | nacos 增加命名卷 `nacos-data:/home/nacos/data` | `docker/docker-compose-infra-lite.yml` | 让"重建容器"不再等于"清空配置"，从根上堵住第 1 层 |
| 2 | 支付域专属 dataId 入库 | `nacos-config/llmall-pay-service.yaml` | 消灭"只存在于运行态"的配置，堵住第 2 层 |
| 3 | 导入段保持 glob 而不是白名单 | `demo.ps1` | 新 dataId 放进目录就自动生效，不需要再登记一份清单；"目录有、Nacos 没有"会被自动补齐 |
| 4 | 基线随 YAML 文件数增加重建 | `gates/baseline/yaml.round2.txt` | 新 YAML 进仓必须进指纹基线，否则第 2 道闸门会漏保护 |

修复后用同一套动作再验一遍（重建 nacos → 导入 → 检查），卷的落盘是可见的：

```
$ docker inspect nacos -f '{{range .Mounts}}{{.Type}} | {{.Name}} -> {{.Destination}}{{end}}'
volume | docker_nacos-data -> /home/nacos/data

$ docker exec nacos sh -c "ls -1 /home/nacos/data"
derby-data
naming
protocol
```

配置对账：`nacos-config/` 目录里 9 份（8 份共享 + 1 份服务专属），Nacos 上 `totalCount` 也是 9，
逐条 dataId 一一对应。

顺带验了一件事，值得单独记下来 —— **HikariCP 的连接池上限不在 Spring Cloud 动态刷新范围内**：

| 时点 | `hikaricp.connections.max` |
|---|---|
| 导入配置之后、重启之前 | `5.0`（新配置已下发，但进程内连接池没变） |
| `docker restart llmall-pay-service` 之后 | `20.0` |

也就是说，这类参数改完"配置中心显示已生效"是假的，必须重启进程。
把这一条留在 dataId 的头部注释里，是为了下次改池大小时不必重新踩一遍。

## 四、教训（可执行的部分）

1. **凡是"状态"，先问它落在哪。** 中间件容器的数据卷不是一个可选优化项。判断标准很简单：
   删掉容器再建一个，这个服务还算不算"同一个服务"？Nacos 的配置、RabbitMQ 的 mnesia、MySQL 的库，
   答案都是"不算"—— 那就必须有卷。反过来，只有真正的无状态副本才配得上"随便重建"。

2. **配置中心是分发通道，不是事实源。** Nacos 负责"把配置送到进程里"，不负责"记得这份配置该是什么"。
   事实源必须是仓库里能 diff、能 code review、能回滚的文件。
   判据：把 Nacos 整个删掉，能不能只靠仓库恢复到一模一样？只要有一份不能，那份就是负债。

3. **"幂等自愈"会掩盖缺失，必须配一条独立的对账。** 自动补齐很方便，代价是它同时掩盖了
   "为什么需要补"。所以补完之后要加一条不复用自愈路径的检查：目录里几份、Nacos 上几份、
   差哪几份。本次就是靠这条对账确认了 9 ↔ 9。

4. **区分"可恢复"与"真丢失"。** 这次 8 份能在两分钟内恢复，1 份不能。区别不在配置有多重要，
   而在仓库里有没有它。事故里真正花时间的从来不是"恢复",是"确认哪一份恢复不了"。

5. **"改完没生效"要先怀疑配置的作用域，而不是配置的内容。** 连接池 5 → 20 那次，
   配置中心回读是对的、服务也是健康的，唯一不对的是进程里的值。这类参数（连接池、线程池、
   各种 `@ConfigurationProperties` 绑定的客户端实例）都是启动期一次性绑定，
   改配置必须重启，且要有一个能读到进程内真实值的探针（`/actuator/metrics/hikaricp.connections.max`）
   来证明它真的变了。

## 五、本次没有覆盖的部分（别当成已经解决）

- **卷本身没有备份策略**：现在只是"不随容器消失"，宿主机磁盘坏了一样没。这对演示环境够用，
  对任何需要恢复目标的环境都不够。
- **配置没有版本与回滚**：Nacos 自带的配置历史未被使用，仓库侧靠 git，两者之间没有对账机制。
- **只验证了 standalone 单机模式**：集群模式的 derby 不适用（要外置数据库），本次结论不能外推。
- **`demo.ps1` 全流程仍未在带容器运行时的机器上完整跑过**（脚本头部已声明该缺口）。
  本次事故修复是逐条手工执行并验证的，不是靠跑通 `demo.ps1` 验证的。
