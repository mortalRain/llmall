# 员工管理并发保护：不能把最后一个店主一起撤掉

一家门店可以有多位店主，但不能没有店主。以前“先数店主、再撤销”的流程，在两个请求同时执行时会出错：两位店主都看到“还有另一位”，于是都撤销成功，最后没有人能管理员工。

本轮让同一家门店的员工新增、改角色、删除操作，在MySQL事务里排队执行。轮到自己时重新检查当前权限、目标员工和剩余店主，不能继续使用排队前的旧记录。没有引入Redis锁或新中间件，也没有改变现有店主/店长/员工的业务规则。

## 实现

1. 写入口仍使用原有Spring事务。先校验门店/操作者非空，再用门店主键 `SELECT id FROM shop WHERE id=? FOR UPDATE` 获取本店的共同锁。门店不存在时拒绝管理操作。
2. 操作者、目标员工和OWNER集合都用FOR UPDATE当前读。先检查操作者，再查询目标，保留权限边界。
3. 只有当前仍是管理者才能继续；撤销OWNER时必须确认至少还会保留一位。正因为所有本店员工写入口用同一个锁，两个操作不会各自基于“还有两个店主”同时通过。
4. 操作提交或回滚后由数据库释放锁。查询员工列表、核销员工身份校验不加这把锁。

只加父行锁仍不够：如果调用者的外层REPEATABLE READ事务早已读取过旧数据，普通SELECT可能继续看到旧权限和旧店主数量。因此这三类管理判断必须使用当前读，不能只把原来的COUNT包进事务就当作并发安全。

## 实际验证

使用新建的私有MySQL库、InnoDB、真实ShopStaffMapper及Spring事务代理执行6项检查：

- 两位OWNER同时把自己降级：只能一人成功，另一人被拒绝，最后保留一位OWNER。
- 两位OWNER同时删除自己：同样保留一位OWNER。
- 店长已被撤权，但外层事务仍记着旧MANAGER角色：继续加人的请求被拒绝。
- 外层事务记着“有两个店主”，另一位已提交降级：不能据旧数量再撤掉最后一个。
- 外层事务回滚：角色恢复，锁释放，后续请求可以继续管理。
- 一家店实际变更员工后暂不提交：测试中的另一家店仍能修改员工。

最终6项全部通过。原服务使用相同回归、强制重新编译后有4项断言失败，分别对应前四种问题；不是仅靠模拟对象推测并发窗口。常规单测另覆盖缺身份不查库、门店不存在不查询目标，以及列表查询不拿写锁。

## 代价与边界

- 同店员工写操作会短暂等待，门店热度等同样更新shop行的操作也可能与之互斥。员工管理不在高频读链路中，事务内只有本地SQL，没有远程调用。
- “不同店可以继续”是所测场景的结果，不保证InnoDB范围/间隙锁或跨多店外层事务绝不发生竞争、死锁。应保持事务短小，多店调用统一锁顺序；本轮不加自动重试。
- 所有员工写入方都必须遵循协议。升级时应先排空旧请求，并确保所有相关实例升级；旧版本或手工SQL绕过父行锁，不能靠新代码单方面保证不变量。
- 不自动修复历史零OWNER数据，不限制多个OWNER，不修改现有店长授权规则。数据库脚本、初始化和人工运维仍需保证初始数据正确。
- 本轮未部署服务、未做HTTP压测或性能提升比较；真实MySQL测试也不是线上故障演练。
