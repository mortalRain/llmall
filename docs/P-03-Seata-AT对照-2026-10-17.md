## 一、步骤 1：seata-server —— 判定「已满足」，不执行容器命令

### 1.1 实际做了什么

**没有**执行任务书里的 `docker compose -f docker/docker-compose-infra-lite.yml --profile full up -d seata`，原因是两条：

1. **宿主没有可用的容器运行时**（Docker CLI 存在，但 `dockerDesktopLinuxEngine` 未就绪；
   `com.docker.service` 需要提权、WSL 枚举被拒），这条命令在本机跑不起来；
2. **更关键：TC 已经在 VM 上活着**，而在宿主再起一个 Seata 容器会向**同一个 Nacos**
   注册第二个 `seata-server` 实例（compose 里 `SEATA_IP=${VM_IP:-192.168.189.128}` 还会把实例
   IP 写成 VM 的地址），属于**污染注册中心**，比不启动更糟。

### 3.2 判据怎么才测得出来（本轮的方法学结论）

**事后查 `undo_log` 与 TC 三表必然是空的** —— AT 在二阶段提交成功后会把 undo_log 与 TC 会话
**异步清理**。所以"事后为空"**不能**证明"没跑"，必须**在飞行中采样**。

做法：`poll-gt.ps1` 每 ~150 ms 轮询一次 `seata.global_table / branch_table / lock_table` 与两侧 `undo_log`，
同时发起一次下单。

### 3.3 判据 1 + 判据 2：飞行中抓到（同一行样本）

```
ts,gt,bt,lt,item_undo,trade_undo,promo_undo
22:19:21.429,0,0,0,1,0,0     ← 下单前
22:19:23.910,1,3,5,2,2,0     ← 全局事务飞行中
22:19:24.717,0,0,0,2,2,0     ← 已提交，TC 会话清理
22:19:25.545,0,0,0,1,0,0     ← undo_log 异步删完
```

| 判据 | 要求 | 实测 | 判定 |
|---|---|---|---|
| **1. undo_log 落行** | 相关库 undo_log 有数据 | `item` **1 → 2**、`trade` **0 → 2** | ✅ |
| **2. TC 有分支** | global/branch 表出现对应记录 | `global_table=1`、`branch_table=3`、`lock_table=5` | ✅ |

> `branch_table=3` 对应「trade 本地写 + item 扣库存 + 一次内部本地事务」，与代码路径吻合。

> **关于 OFF 态那 28 单**：`+1,442` 与销量完全一致，差额由 `OrderTimeoutScanTask`/`OrderCloseGuard`
> 在窗口内关闭未支付订单并回补库存造成（日志可见 `支付状态已确认为未支付，关单并回滚库存`），
> **不是账不平**。两态的共同不变量是"**库存增量 ≡ 销量增量**"与"**余额差额 ≡ 成功次数 × 单价**"。

### 4.4 结论（一句话 + 归因）

> **AT 的代价是真实的、可量化的、且集中在"被 `@GlobalTransactional` 标注的下单接口"上：
> 每个订单多出 TM 开启 + 分支注册 + 二阶段提交通知，`POST /orders` 从 68.9 ms 涨到 247.7 ms（+259%），
> 把整链路吞吐从 73.9 压到 58.5 rps（−21%）；而收益（跨服务分支可被 TC 回滚）只有在下单失败时
> 才兑现 —— 这就是"默认关"的全部理由。**

**收益侧也不是空的**：本轮实测证明 AT 的回滚是真的（`PhaseTwo_Rollbacked` + undo 反查 + 库存精确复原）。
如果将来把"下单跨库存 + 锁券"的强一致要求做实（例如券与库存不能出现中间态），AT 是可用方案；
但代价要按上面的数字买。

## 七、默认值决定：**已回落 `false`（2026-10-17 定稿）**

**结论：三个 `seata.enabled` 回落 `false`，即维持本轮之前的状态。**

理由（按权重）：

1. **代价落在最热的写接口上**：`POST /orders` +259%、整链路吞吐 −21%，而这一层收益在"下单成功"这条
   99%+ 的路径上是**零收益**（AT 的意义只在失败回滚）。
2. **当前系统已有等价的失败兜底且经过验证**：本地库存补偿钩子 + 本地消息表 + 三重幂等 + 定时对账，
   其中"下单事务未提交 → 库存回补"这条路径在本轮之前已用故障注入验证过（`OrderServiceImpl:208-256`）。
3. **AT 的真价值需要"券与库存不能中间态"这类需求来兑现**，目前业务上没有这个硬约束。
4. **版本倒挂（问题 1、2）没解决前，不适合把 AT 设为默认。**

**回落是怎么做的（可复核）**：
1. 三个 yaml 的 `enabled` 改回 `false`；
2. 重新取 YAML 指纹快照，与"改前留档"比对 —— **SHA256 完全一致（`4960BBAA…`）**，证明回落是**逐字节精确**的；
3. 用该快照覆盖 `gates/baseline/yaml.round2.txt`，并删除留档 `yaml.round2.pre-seata.txt`
   （恪守 `gates/README.md` 的"基线只保留现行一份"）；
4. `verify-all` → **七道闸门全绿、退出码 0**。

**如果将来决定开启**，前提条件清单：
- [ ] 先解决依赖版本（把 client 与服务端对齐到同一 minor，台账 S-11）
- [ ] 三开关必须一起开（单独开 trade 会造成少卖，台账 S-10）
- [ ] 压测复核 `POST /orders` 的 SLO 是否可接受（当前 +259%）
- [ ] 闸门基线随开关一并重建（流程见 `gates/README.md` 第八节）

**当前工作树状态**：三个 yaml = `false`（与 HEAD 一致，不再有配置差异）；AT 的代码、配置段、
`@GlobalTransactional` 注解与守卫**全部保留**，只差一个开关即可复跑本报告的全部实验。
