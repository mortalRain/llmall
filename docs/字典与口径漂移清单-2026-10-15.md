## 三、这项检查的边界（先说清楚，避免误用）

1. **它能自动裁决的**：同一字段名 + 同一标签下的**取值冲突**（检查 ①，当前 0 处）、
   **库名指向错误**（检查 ③）、**同表同列在不同文件里的表述不一**（检查 ④）。这三类是确定的。
2. **它只能给候选的**：检查 ②「DDL 声明了、Java 侧找不到」——因为「找不到」有三种成因：
   DDL 错（声明了不存在的状态）、代码错（该状态没实现）、**代码用裸字面量表达**（既不是 DDL 错也不是没实现）。
   后两者需要人判断，所以它**不构成自动结论**。
3. **它覆盖不到的**：字段名不同但语义相同的漂移（如 `state` vs `status`），以及跨语言的枚举映射。
   这类只能靠人工核对 —— 这也是「错误注释率无法自动测量」的具体体现。

## 四、结论

- **9 处确认漂移**里，8 处集中在 **DDL COMMENT 与代码脱节**（尤其 `sql/llmall-pay.sql` 与 `sql/llmall-trade.sql` 这两个**非 merged 的原始 DDL**，
  它们的注释停留在其它项目/课程原版的取值），1 处是 Java 注释（已修）。
- 这 8 处**不是注释问题，是 DDL 问题**：改它们需要 `ALTER TABLE ... MODIFY COLUMN ... COMMENT` 才对已建库生效，
  且会让「代码零改动」的指纹闸门失效 —— 因此按既定边界，**不在本轮注释治理内交付**，作为一次独立的 DDL 变更。
- 闸门本身已固化为 `dict-lint.ps1`：以后新增状态值、改枚举、动 DDL 时跑一次即可，**不必再靠人工通读**。
