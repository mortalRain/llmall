# 服务端下单边界

本批将输入校验、商品校验和金额计算集中到 `OrderInputPolicy`，交易服务继续负责事务和调用编排。接口及表结构不变，不引入拆单系统。

## 受支持的请求

- 一单 1–50 行不同商品，每行 1–99 件；商品、可选地址和券实例编号必须为正数。
- 支付类型沿用现有 1/2/3。客户端令牌去除首尾空白，非空最多 64 个字符；相同用户、令牌及订单参数重试返回原订单。
- 一单同一门店、同一履约类型：实物或门店套餐。套餐必须有正数门店编号；兼容历史实物全部无门店、类型为空的数据（空类型按实物处理），但有门店和无门店不能混单。
- 商品服务返回的编号必须与请求一一对应，不能缺失、多余、重复或含空行；状态必须上架，单价必须是非负整数分。
- 使用服务端商品价格，用 long 乘加并检查现有 int 存储上限：最高 2,147,483,647 分。允许零单价赠品和正价商品一起下单，实付必须大于零。
- 券面额必须为正且不超过 int 上限，先检查再做抵扣；面额大于等于总价的组合明确拒绝，因为当前没有零元订单的完成链路。

请求结构在查询幂等订单之前校验。合法重放按持久化订单与参数哈希判断，不重新查询当前商品价格、库存或状态，避免已经成功的请求因商品后续变化而不能重放。

库存调用使用请求的独立副本，仅复制商品编号和数量；门店、业务类型和业务号由服务端填写。客户端伪造这些字段不会传到库存接口，服务也不会修改调用者传入的 DTO。

## 验证和边界

- 服务级边界用例检查错误请求不会到达保存订单或扣库存。
- H2 + 真实 MyBatis 订单/明细服务 + Spring 本地事务验证正常金额与明细、请求副本、顺序无关重放、赠品、最大整数金额、历史实物兼容、套餐抵扣和失败回滚。外部库存、券和消息接口仍为 mock，不是 MySQL 或完整微服务部署证明。
- 本批没有修复提交后锁券与付款的竞态，没有实现库存预占或取消墓碑，未改变远程失败补偿协议，也未改变通用消息发布确认机制。它们不属于输入校验的保证。
- 上架和价格是查询时的快照；下单与后台修改价格、下架不构成跨服务原子事务。最终库存仍由商品服务裁决。
- 历史已落库的异常订单不在本批自动清理；现有幂等/恢复所需 64/65 迁移和搜索精度 66 迁移的部署闸门仍然保留。
