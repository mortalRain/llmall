## 二、问题清单

### 🔴 致命（资金安全 / 越权 / 数据错乱）

#### A1 支付时不校验交易订单状态与金额 → 已关单仍扣款
- **位置**：`llmall-pay-service` `PayOrderServiceImpl#tryPayOrderByBalance`
- **问题描述**：只校验支付单自身 `status`，不校验交易订单是否已关单、金额是否与订单一致。而订单侧存在「超时未支付自动关单」的延迟消息，两者天然存在竞态。
- **风险影响**：**资损** —— 订单已关闭、用户余额却被扣走，且订单不会变成已支付，形成"钱货两空"的投诉场景。
- **整改建议**：扣款前用 Feign 拉交易订单，校验「存在 + 属于当前用户 + 状态=待付款 + 金额与订单一致」，任一不满足直接拒绝且不扣款。
- **参考示例**：
```java
TradeOrderDTO t = tradeClient.queryOrderById(po.getBizOrderNo());
if (t == null) throw new BizIllegalException("交易订单不存在，无法支付");
if (t.getStatus() != 1) throw new BizIllegalException("订单已超时关闭，无法支付");
if (!t.getTotalFee().equals(po.getAmount())) throw new BizIllegalException("支付金额与订单金额不一致");
```
- **状态**：✅ 已修复并实测（`已关闭订单禁止支付`、`支付金额篡改被拒绝` 两项断言通过）

#### A2 订单超时时间硬编码 10 秒 → 用户来不及付款
- **位置**：`llmall-trade-service` `OrderServiceImpl#createOrder` 延迟消息 `messageProperties.setDelay(10000)`
- **问题描述**：订单超时是业务参数却写死在代码里，且取值 10 秒远小于真实支付耗时。
- **风险影响**：用户输完密码时订单已被关单 → 表现为「去支付却变成已取消」；叠加 A1 则直接产生资损。
- **整改建议**：抽成配置 `llmall.trade.order-timeout-seconds`，默认 900（15 分钟）；延迟时间需做上限保护（RabbitMQ 延迟上限）。
- **状态**：✅ 已修复（实测「下单 12 秒后订单仍可支付」通过）

#### A3 余额扣减无充足性判断 + `${}` 拼接 → 余额可扣成负数
- **位置**：`llmall-user-service` `UserMapper#updateMoney`、`UserServiceImpl#deductMoney`
- **问题描述**：原 SQL 为 `set balance = balance - ${totalFee} where id = #{userId}`，**没有 `balance >= #{totalFee}` 条件**，方法返回 `void`，调用方无法感知失败；`${}` 直接拼接金额还存在注入面。
- **风险影响**：余额被扣成负数（账实不符）；异常被吞成一句"扣款失败，可能是余额不足！"，无法定位。
- **整改建议**：条件更新 + 返回受影响行数 + `#{}` 预编译；余额不足时给出「当前余额 X 元 / 本单应付 Y 元」。
- **状态**：✅ 已修复并实测（余额保持正数 864800 分）

#### A4 支付单创建不校验订单存在/归属/金额 → 可用任意单号建单
- **位置**：`llmall-pay-service` `PayOrderServiceImpl#applyPayOrder`（仅按 `bizOrderNo` 查重）
- **问题描述**：传入任意 `bizOrderNo` 都会成功建单；`amount` 完全采信前端；不校验订单归属，可为他人的订单建支付单。
- **风险影响**：①脏数据（支付单指向不存在的订单）；②被篡改金额；③跨用户操作他人订单。
- **整改建议**：建单前校验「订单存在 + 归属 + 状态=待付款 + 金额一致」，四条缺一不可。
- **状态**：🔄 修复中（未复核）

#### A5 对象级授权（IDOR）普遍缺失
- **位置（逐条）**：
  1. `llmall-pay-service` `GET /pay-orders` → `payOrderService.list()` **返回全库支付单**
  2. `llmall-pay-service` `GET /pay-orders/biz/{id}` → 无归属校验
  3. `llmall-pay-service` `tryPayOrderByBalance` → 无「支付单属于当前用户」校验
  4. `llmall-cart-service` `PUT /carts` → `updateById(cart)` 直接按 id 改，**无归属校验**，且允许改 `price`
  5. `llmall-cart-service` `DELETE /carts/{id}` → `removeById(id)` 无归属校验
- **风险影响**：**水平越权**。任何登录用户可查看他人支付金额/订单号、改删他人购物车、替他人付款；`PUT /carts` 还能篡改单价（下单按明细快照计价，若与购物车价不一致会造成展示与结算不一致）。
- **整改建议**：统一"先查后校验归属再操作"；写接口只允许更新白名单字段（如购物车只允许 `num`）。
- **参考示例**：
```java
Cart db = cartService.getById(cart.getId());
if (db == null || !db.getUserId().equals(UserContext.getUser()))
    throw new ForbiddenException("购物车条目不存在或不属于当前用户");
cartService.lambdaUpdate().eq(Cart::getId, db.getId()).eq(Cart::getUserId, db.getUserId())
        .set(Cart::getNum, cart.getNum()).update();
```
- **状态**：🔄 修复中（未复核）

#### A6 网关未剥离客户端伪造的 `user-info` 头（越权根因）
- **位置**：`llmall-gateway` `AuthGlobalFilter`
- **问题描述**：原实现只在鉴权通过后写入 `user-info`，而免鉴权路径直接放行 → 攻击者自带 `user-info: 1` 即可冒充任意用户，且正常流量完全看不出问题。
- **风险影响**：**全站身份可伪造**，下游所有"按 UserContext 取用户"的逻辑全部失守。
- **整改建议**：网关对**所有**请求先删除 `user-info`（区分大小写变体），再按鉴权结果写入；并提供自测接口固化证据。
- **状态**：✅ 已修复并实测（`/users/_debug/whoami` 带伪造头时 `userInfoHeader=null`）

### 🟠 严重（流程断点 / 数据一致性 / 口径矛盾）

#### B1 到店核销只有「核销码」没有「核销动作」→ 主流程无法闭环
- **位置**：`llmall-trade-service`（`order.verify_code` / `verify_time` 字段已建，`Order.STATUS_VERIFIED=7` 已定义）+ 全项目**无核销接口**
- **问题描述**：下单支付后生成核销码、订单进入「待使用」，但**没有任何接口把券核销掉**（无 `POST /orders/{id}/verify`）。终态 7（已核销）**只能靠 SQL 手工写入**。
- **风险影响**：**业务主流程断裂** —— 到店消费是本地生活的核心动作，目前无法完成"出示码→门店核销→订单终态"闭环；数据里那些"已核销"订单是种子数据伪造的，一旦面试官追问核销实现就会暴露。
- **整改建议**：新增核销接口（建议放在 llmall-trade-service）：
```
POST /orders/verify  body: { verifyCode, shopId }   （门店侧调用，需校验订单属于该门店）
校验：码存在 / 订单状态=2 / 门店一致 / 未被核销过（条件更新 status 2→7 保证幂等）
成功后：置 verify_time，投递 order.verified 事件（门店销量/对账可选消费）
```
  并补反向流程：核销后不允许取消/退款。
- **状态**：❌ 未修复（**建议列为下一步第一优先**）

#### B2 优惠券只能「领」不能「抵扣」→ 券与订单未打通
- **位置**：`llmall-promotion-service`（8 个接口已实现） vs `llmall-trade-service#createOrder`
- **问题描述**：券有 `actual_value`（抵扣金额）、有 `use(orderId)` 核销接口，但**下单请求体 `OrderFormDTO` 里没有 couponId 字段**，订单总价计算也不减抵扣额。
- **风险影响**：营销能力形同虚设 —— 用户领了券但结算时无法使用，与前端「优惠券」页面形成"能看不能用"的口径矛盾。
- **整改建议**：`OrderFormDTO` 增加 `userVoucherId`；下单时：校验券归属/状态/有效期/适用门店 → `totalFee = Σ(单价×数量) - actualValue`（下限 0）→ 同事务内锁定券（状态 1→2 并写 orderId）；订单取消时反向退券（`refund(orderId)` 已就绪）。
- **状态**：❌ 未修复

#### B3 MQ 消息转换器从未生效 → 所有领域事件发送失败（闭环静默断裂）
- **位置**：`llmall-common/src/main/resources/META-INF/spring.factories`（缺 `MqConfig`）
- **问题描述**：`MqConfig` 提供了 `Jackson2JsonMessageConverter`，但没被注册为自动配置，于是 `RabbitTemplate` 用的是默认 `SimpleMessageConverter`，**任何 POJO 事件都会抛** `SimpleMessageConverter only supports String, byte[] and Serializable payloads`。
- **风险影响**：`order.paid`（发积分）、`review.created`（重算门店热度）、`shop.hot.changed`（搜索读模型）**全部静默失效** —— 三大亮点里的 B、C 两条闭环实际是断的，日志里只有一句 error。这类"不报错只失效"的问题最难在演示前发现。
- **整改建议**：补齐自动配置注册；同时把"事件是否真的被消费"做成可断言项（消费记录表 `consume_record` + E2E 断言）。
- **状态**：✅ 已修复并实测（`评价 → 门店热度重算 16.79→36.12`、`积分流水已发放(order.paid)` 两项断言通过）

#### B4 下单成功清理购物车静默失效（双重缺陷）
- **位置**：`llmall-cart-service` `OrderCreateListener`、`CartServiceImpl#removeByItemIds`
- **问题描述**：① 监听器字段 `private ICartService cartService;` **非 final 且无 `@Autowired`**，用 `@RequiredArgsConstructor` 时不会被注入 → 恒为 null；② 消费端用 `UserContext.getUser()` 过滤，而 **MQ 线程没有登录上下文**（ThreadLocal 由网关请求线程写入）→ `eq(user_id, null)` 恒不匹配。
- **风险影响**：下单后购物车不清空；且 ①会在消息真正到达时抛 NPE，属于"一上线就炸"的隐患。
- **整改建议**：字段改 `final`；事件体携带 `userId`（新增 `CartClearEvent`），**跨线程传递身份不能依赖 ThreadLocal**。
- **状态**：✅ 已修复并实测（购物车 4 项 → 0 项）

#### B5 状态与类型枚举口径不统一（三套并存）
- **位置**：`Order.paymentType`（3=扣减余额）/ `PayType.BALANCE`（**5**=余额）/ `PayStatus`（`TRADE_SUCCESS` 与 `TRADE_FINISHED` **同为 3**）/ `item.type`（1 实物 2 套餐）vs `order.order_type`（1 实物 2 券）
- **问题描述**：同一个"余额支付"在订单侧是 3、支付侧是 5；`PayStatus` 里两个枚举值相同（`equalsValue` 恒真，语义歧义）。前端按订单侧口径传 3 会被 llmall-pay-service 直接拒绝。
- **风险影响**：跨模块调用反复踩坑；状态判断"看起来对但语义错"；对账与报表口径不一致。
- **整改建议**：建立统一枚举字典（一份 `payment_channel` / `order_status` / `item_type` 定义，各服务只引用不自定义）；同一 code 只允许一个语义；接口文档标注单位与取值范围。
- **状态**：🟡 部分缓解（前端已按 5 传值并加注释；枚举未统一）

#### B6 前端把 19 位雪花 id 转 `Number` → 精度丢失产生脏数据与资损
- **位置**：`frontend/index.html`（`bizOrderNo: Number(order.id)`）
- **问题描述**：订单/支付单 id 是 19 位雪花号，JS `Number` 超过 2^53 会四舍五入 —— 实测数据库里留下 **5 张 `biz_order_no` 结尾为 `...600`/`...400` 的孤儿支付单**，其中 **3 张已支付，误扣 ¥1191**。
- **风险影响**：①支付成功也无法把订单改成已付款（表现为"付完还是待付款"）；②加校验后直接报"订单不存在"；③资金误扣、库存与订单状态错乱。
- **整改建议**：**长整型 id 在前端一律按字符串处理**（本项目后端已配置 Long→String 序列化，前端不得再 `Number()`）；DB 侧加清理脚本（已提供 `sql/merged/52-fix-orphan-pay-orders.sql`：关单 + 退款）。
- **状态**：✅ 已修复 + 数据已清理退款（余额已恢复）

#### B7 `blog.images` NOT NULL 无默认值 → 发布评价 500
- **位置**：`llmall-content.blog` 表 / `BlogServiceImpl#publishBlog`
- **问题描述**：图片为可选项，但字段 NOT NULL 且无默认值，不传图直接插入失败。
- **风险影响**：**核心闭环入口被卡死**（评价→热度→排序根本无法产生数据）。
- **整改建议**：应用层 `blankToDefault("")` + 库层补默认值（双保险）。
- **状态**：✅ 已修复（`23-content-image-default.sql`）

#### B8 `llmall-user.user` 时间字段无默认值 → 自动注册 500
- **位置**：`llmall-user.user`（课程老库表）/ `UserServiceImpl#loginByCode`
- **问题描述**：`create_time/update_time` NOT NULL 且无默认值，新增的"短信登录自动注册"路径没有显式赋值即插入失败。
- **风险影响**：新手机号首次登录必然失败，新用户进不来。
- **整改建议**：应用层显式赋值 + 库层补默认值；**并统一审计"老表 vs 新表"的字段约束差异**。
- **状态**：✅ 已修复（`22-user-time-default.sql`）

#### B9 统一异常处理未装配 → 所有业务异常退化为 500
- **位置**：`llmall-common` `CommonExceptionAdvice`（未注册自动配置）
- **问题描述**：`@RestControllerAdvice` 存在但没被任何服务装配；且直接写进 `spring.factories` 会让 WebFlux 网关因缺 `javax.servlet` 启动失败。
- **风险影响**：前端拿不到 `msg`，用户只看到"服务器内部异常"，问题无法定位（本次用户报错就是这个表现）。
- **整改建议**：用 `@Configuration + @ConditionalOnWebApplication(SERVLET) + @Import` 包装后注册。
- **状态**：✅ 已修复（现返回 `{"code":400,"msg":"订单不存在"}`）

| # | 主题 | 建议 |
|---|---|---|
| D1 | **"静默失效"防守** | 所有"配置/装配/外部资源"类依赖（自动配置、MQ 转换器、静态资源引用、消息队列绑定）必须有**启动期自检或冒烟断言**：例如启动时打印已加载的自动配置、E2E 断言"事件被消费后数据真的变了"。本项目 5 个最贵的 bug 全部属于此类 |

## 三、共性问题与可复用规范（给后续迭代用）

1. **凡是"不报错但行为不对"的地方，都要有断言**
   MQ 转换器没生效、样式表没被引用、`Number()` 精度丢失、`typeName` 为空 —— 这四类问题的共同点是"接口 200、日志干净、结果错"。规范：**验收脚本必须断言业务结果（订单变已付款、库存回到原值、热度真的变了），而不是断言 HTTP 状态码**。

2. **跨线程/跨服务传递身份，禁止依赖 ThreadLocal**
   `UserContext` 只在请求线程有效。MQ 消费、异步任务、定时任务必须由消息体/参数显式携带身份。规范：任何 `@RabbitListener`、`@Async`、`@Scheduled` 方法中出现 `UserContext.getUser()` 即视为缺陷。

3. **钱与库存的操作必须"前置校验 + 原子更新 + 幂等业务号"三件套**
   前置校验：对象存在、归属正确、状态合法、金额一致；原子更新：条件更新（`where balance>=amount` / `where stock>=num`）并按受影响行数判定；幂等：唯一键或业务号（`biz_type+biz_id+item_id`）。

4. **一切以 id 为入参的接口都要过一遍"IDOR 三问"**
   这个 id 存不存在？是不是当前用户的？操作后会不会影响别人？三个问题对应三条断言，可直接加进回归脚本。

5. **老表（课程遗留）必须先做约束体检**
   本项目 2 个 500 故障（`user.create_time`、`blog.images`）都源于老表 NOT NULL 无默认值。规范：新老库合并后，用一条 `information_schema` 查询对比所有 `create_time/update_time/NOT NULL 无默认值` 字段，先补齐再开发。
