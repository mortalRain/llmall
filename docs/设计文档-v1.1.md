## 0. 拆分原则（先回答"是不是一个功能一个服务"）

**拆分的三条判据**（面试也会问，要能背下来）：

1. **业务能力内聚**：一个服务 = 一个完整的业务能力，能对外提供闭环能力（不是一张表一个服务）
2. **数据所有权独占**：一个服务一个库，**只有它能写自己的表**；别人要数据只能通过 API 或事件
3. **可独立部署演进**：改一个域不需要同时发布其他服务

**反例（必须避免的"分布式单体"）**：
- 把"点赞""评论""签到"各拆成服务 → 每条业务链路跨 5 个服务调用，耦合度反而上升
- 多个服务共享一个库、互相直接查表 → 逻辑上是单体，只是部署上分开了
- 拆分后一个功能改动要同时发 4 个服务 → 边界划错了

**本项目的正确依据**：按**领域**拆（用户域 / 门店域 / 商品域 / 交易域 / 支付域 / 营销域 / 内容域 / 搜索域），每个域独占自己的库。

## 4. 业务闭环（"为什么该合"的答案）

```
用户浏览门店(shop) → 看评价笔记(content) → 买团购套餐(item) → 领券(promotion)
        ↑                                                        ↓
   ES 搜索/榜单曝光(search) ← 门店热度分(shop) ← 写评价(content) ← 下单(order) → 支付(pay) → 到店核销(order)
        ↑                                                                        ↓
   积分/会员等级(user) ←────────── 最终一致性事件 ──────────→ 销量/库存流水(item)
```

**评价内容影响门店曝光、门店热度影响搜索排序**——这条跨 `content → shop → search` 的链路，就是合并的业务理由。

## 5. 四个亮点设计

### 亮点 A：统一账号与跨服务身份透传

- **账号合一**：`user` 表以商城结构为基（`username` 唯一 + BCrypt + `status`/`balance`），补 `nick_name`/`icon`，`phone` 加唯一索引；点评的 `city/introduce/gender/birthday/credits/level/fans/followee` 全落入 `user_info`（1:1）。**密码统一 BCrypt**，不留两套校验分支。
- **登录双通道**：`/users/login`（用户名密码）+ `/users/login/sms`（验证码存 Redis，5 分钟过期）。
- **签发/校验**：网关用 jks 私钥签发 JWT（access 30min + refresh 7d 无感刷新）；下游不验签，只信网关。
- **透传**：网关解析 → 写 `user-id` 头 → `llmall-api` 的 `RequestInterceptor` 带入 Feign → 下游 `UserContext` 读取；异步线程用 `TaskDecorator` 传递。
- **【加分点】网关剥离外部伪造的 `user-id` 头**，否则任意越权；登出用 Redis 黑名单解决 JWT 无法主动失效。
- **量化**：下游取当前用户远程调用 = **0**；鉴权代码收敛到 1 处；登录→业务接口 TP99。

**追问预判**：JWT vs Session｜无法主动失效怎么办｜网关验签还是各服务验签｜ThreadLocal 泄漏｜Feign 异步丢上下文｜**伪造请求头越权**。

### 亮点 B：强一致 + 最终一致的**分层一致性策略**（有 Seata，做对比才有深度）

下单链路横跨 4 个服务：`order`（主）+ `item` 扣库存 + `promotion` 核销券 + `user` 加积分 + `shop` 更新销量。

**策略分层（这是核心回答）**：

| 环节 | 一致性要求 | 方案 | 理由 |
|---|---|---|---|
| 扣库存 + 核销券（用户等待结果） | 强一致 | **Seata AT** `@GlobalTransactional` | 链路短、必须即时反馈；AT 无侵入，适合非核心资金场景 |
| 加积分 + 更新销量 + 发通知 | 最终一致 | **本地消息表 + RabbitMQ + 消费幂等 + 定时对账** | 允许延迟，异步削峰，避免把长链路锁进全局事务 |

**并且做对比压测**（这是你区别于所有人的地方）：同一业务分别用 Seata AT 版 与 本地消息表版实现，压测对比 **TP99 / QPS / 数据库锁等待时间 / undo_log 增长**，得出"什么时候用哪个"的结论。
> 面试时这句会非常有力："我在自己项目里把两种方案都实现并压过，Seata AT 在 XX 并发下 TP99 是 A，消息表方案是 B，所以我按一致性要求分层使用，而不是无脑上 Seata。"

**落地要点**：`message_log` 表（biz_type/biz_id/payload/status/retry_count/next_retry_time）；消息写入与业务在同一本地事务；投递失败指数退避重试；消费端 `(biz_type,biz_id)` 唯一索引幂等；**对账任务**比对订单↔库存流水↔积分流水，缺口生成补偿（补偿本身也幂等）。每个参与库建 `undo_log`。

**量化**：故障注入（消费者停机 30s）丢单 = 0；重复投递 1000 次只生效 1 次；两种方案 TP99 对比数据。

**追问预判**：为什么不全用 Seata（长事务锁表、回滚边界、性能）｜消息丢失/重复｜对账怎么设计｜补偿会不会重复扣｜Seata AT 的脏读与全局锁｜TC/TM/RM 角色。

### 亮点 C：评价 → 门店热度 → **Redis 榜单 + ES 综合排序** 准实时闭环

**链路**：`llmall-content-service` 写评价 → 事件 `review.created` → `llmall-shop-service` 消费：更新 `shop.comments`/`shop.score` + 计算热度分 → ① 写 Redis ZSet `hot:shop:{cityId}` ② 发事件 `shop.hot.changed` → `llmall-search-service` 消费并更新 ES 文档 `hotScore` → 门店搜索用 **function_score** 综合排序。

**热度公式（参数要能讲清设计意图）**：
```
base  = score/10*4 + log10(comments+1)*3 + log10(sold+1)*3
decay = 1 / (1 + Δdays/7)        // 7 天衰减一半
hot   = base * decay
```
评分权重最高但用 log 抑制单次刷量；时间衰减给新店冷启动机会；预留运营权重位。

**两条读路径（要讲清为什么两条都要）**：
- 榜单/列表 → Redis ZSet（`ZREVRANGE` + 游标分页，避免深分页）
- 搜索/多条件筛选（关键词 + 分类 + 距离 + 热度）→ ES function_score

**兜底**：定时任务按 DB 重算校准 ZSet；ES 与 DB 对账重建索引。

**量化**：热度更新延迟秒级（对比 T+1 批量）；榜单接口 QPS；缓存命中率；ZSet 与 DB 偏差 0。

**追问预判**：为什么榜单用 ZSet 不用 ES（排序规则简单 + 极低延迟 + 省 ES 压力）｜为什么搜索用 ES 不用 ZSet（多条件 + 分词 + 距离）｜**深分页**｜缓存与 DB 不一致｜刷分怎么防｜**ES 与 MySQL 数据同步方案**（用 MQ 事件而非 Canal 的理由：无需 binlog 权限、与现有架构一致；代价是首次全量要写初始化任务）。

### 亮点 D：秒杀团购券

Redis Lua 原子「校验库存 + 一人一单 + 预扣减」→ MQ 异步下单 → 订单超时回滚库存（延迟队列）→ 分布式锁兜底。压测：QPS、超卖 0、一人一单拦截率。

## 8. 简历 bullet（定稿草案）

1. 基于 Spring Cloud Alibaba 将本地生活服务平台按领域拆分为 **10 个服务**（网关/用户/门店/商品/购物车/交易/支付/营销/内容/搜索），**一服务一库**实现数据所有权隔离；以 Nacos 做注册与配置中心，Gateway 统一鉴权与限流，Feign + Sentinel 完成服务间调用与熔断降级；将两套历史账号体系合并为统一账号中台，鉴权逻辑由各服务收敛至网关并透传用户上下文，同时加固请求头防伪造。
2. 针对下单链路跨 4 个服务的场景，落地**分层一致性策略**：库存扣减与优惠券核销采用 **Seata AT** 保证强一致；加积分、更新销量、消息通知采用**本地消息表 + RabbitMQ 最终一致性 + 消费幂等 + 定时对账补偿**。对两种方案做了同场景对比压测（TP99 / QPS / 锁等待），据此确定分层选型；并通过故障注入（消费者停机、消息重复投递千次）验证零丢单、零重复扣减。
3. 设计并实现「**用户评价 → 门店热度 → 搜索排序**」准实时闭环：评价落库后经 MQ 异步聚合，热度分融合评分、评论量、销量并引入**时间衰减因子**（抑制刷量、扶持新店冷启动）；热榜走 Redis ZSet（游标分页规避深分页），门店搜索走 **Elasticsearch function_score** 综合评分；榜单更新延迟由 T+1 降至秒级，并以定时对账保证缓存、ES 与库内数据一致。
4. 基于 Redis Lua 实现团购券秒杀（原子校验库存 + 一人一单 + 预扣减），MQ 异步下单削峰，超时未支付自动回滚库存；JMeter 压测 QPS 达 **X**（实测），超卖 **0** 单。

## 9. 风险

| 风险 | 应对 |
|---|---|
| **服务多、联调成本高** | 严格"一服务一库 + 只走 llmall-api"；每个里程碑必须整体可跑；用统一 traceId 定位跨服务问题 |
| **VM 内存不足** | ES/Kibana 限堆、VM ≥8G；先起 M0 基线并做快照 |
