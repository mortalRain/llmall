# M2 进展与验收：亮点 A · 统一账号与跨服务身份透传

> 目标：把商城（用户名密码 + BCrypt）与点评（手机验证码 + 自研 Token）两套账号体系合并为一套，
> 并把"鉴权"从散落各服务收敛到网关，同时解决 JWT 无状态带来的**无法主动失效**问题。

## 二、本轮实现（4 项增强）

### 1. 【安全】修复越权漏洞：网关剥离伪造的 `user-info` 头
- **漏洞**：原实现只在**鉴权通过后**写入 `user-info`；而 `excludePaths`（`/items/**`、`/search/**` 等）是**直接放行**的。
  攻击者只要自带 `user-info: 1` 访问这些路径，下游 `UserInfoInterceptor` 就会直接采信 → **可冒充任意用户**。
- **修复**：在过滤器最前面（早于任何放行判断）统一移除该请求头，下游只会收到网关写入的可信值。
- **可复现**：新增自测接口 `GET /users/_debug/whoami`（默认关闭，`llmall.debug.enabled=true` 开启），
  它故意位于免鉴权路径中，会回显"下游实际收到的头"与"被采信的身份"。

### 2. 【可用】双令牌 + 无感刷新
- access token（30 分钟，随请求携带）+ refresh token（7 天，仅用于换新）；
- 网关解析到 **access 过期** 时（`TokenExpiredException`），自动用 `x-refresh-token` 换发新 access，
  通过响应头 **`x-access-token`** 返回，请求继续正常执行 —— 用户全程无感知，不会操作到一半被踢下线；
- refresh 采用**轮换**：每次刷新都作废旧 refresh，泄露后可被发现（OAuth2 推荐实践）。

### 3. 【可控】主动失效：黑名单 + 白名单
JWT 无状态，天生无法"撤回"。这里的做法是**只对需要失效的部分引入状态**，而不是退回 Session：

| 令牌 | 服务端状态 | 目的 |
|---|---|---|
| access token | Redis 黑名单 `auth:blacklist:{jti}`（TTL = 令牌剩余寿命，自动清理） | 注销/踢人后立即失效，且黑名单不会无限膨胀 |
| refresh token | Redis 白名单 `auth:refresh:{jti}` → userId | 服务端可主动作废、支持轮换 |
| 用户维度 | Redis 集合 `auth:refresh:user:{userId}` | **登出所有设备**（注销时批量作废该用户全部 refresh） |

### 4. 【正确】令牌类型校验 + ThreadLocal 异步透传
- 令牌带 `type`（access/refresh），**refresh token 不能直接访问业务接口**（原实现没有这个校验，属于常见漏洞）；
- `type` 校验缺失时，攻击者可拿长效 refresh 当 access 用，短 TTL 的安全收益归零；
- 新增 `UserContextTaskDecorator`（TaskDecorator）：**@Async / 线程池里也能拿到当前用户**。
  ThreadLocal + 异步是经典坑——异步线程里 `UserContext.getUser()` 恒为 null，会导致下游丢 `user_id`，而且很难发现。

### 5. 附带：账号合一与统一入口
- `user` 表补 `nick_name` / `icon`（点评侧字段），`phone` 加唯一索引；点评的用户画像（积分/等级/粉丝）落到 `user_info`（1:1）；
- 两条登录通道收敛到同一套令牌逻辑：`POST /users/login`（用户名密码）、`POST /users/code` + `POST /users/login/sms`（手机验证码，含 60 秒频控、5 分钟有效、一次性使用、未注册自动注册）；
- 新增 `GET /users/me`（前端必需，也是验收脚本的关键接口）、`POST /users/token/refresh`、`POST /users/logout`；
- `UserLoginVO` 保留旧字段 `token`（= accessToken），**旧前端不需要改**。

## 五、验收步骤（环境就绪后执行）

```powershell
# 1. 启动：Nacos / MySQL / Redis，然后启动 llmall-gateway 与 llmall-user-service
# 2. 跑脚本
pwsh -File <repo-parent>\scripts\verify-auth.ps1
```

脚本覆盖：
1. 免鉴权路径 + 伪造 `user-info` 头 → 期望 `userInfoHeader = null`（**证明越权已被修复**）
2. 无令牌访问 `/users/me` → 期望 401
3. 发送验证码接口可调用（验证码打印在 llmall-user-service 日志中）
4. 用户名密码登录 → 拿到 access + refresh
5. 带令牌访问 `/users/me` → 200
6. 注销后再访问 → 401（黑名单生效）
7. 无感刷新：手工把 `tokenTTL` 临时改成 `10s`，带旧 access + refresh 访问，期望 200 且响应头出现 `x-access-token`

> 注意：脚本里示例账号是 `Jack / 123456`，请按你库里的实际密码调整。

## 六、评审怎么讲这一段

> "原项目的身份透传其实已经通了，所以我把重点放在三个教程没做的地方：
> **一是安全**——我发现免鉴权路径上可以伪造 `user-info` 头冒充任意用户，在网关入口做了剥离并写了可复现的自测接口；
> **二是可用性**——JWT 过期会让用户操作中途掉线，我做了双令牌 + 网关无感刷新 + refresh 轮换；
> **三是可控性**——JWT 无状态无法撤回，我用'access 黑名单（TTL 等于剩余寿命）+ refresh 白名单'实现登出与踢人，
> 并支持登出所有设备；另外补了 refresh 不能当 access 用的类型校验，还有 ThreadLocal 在异步线程丢失的修复。"

追问预判：
| 追问 | 答题要点 |
|---|---|
| 为什么不直接用 Session？ | 无状态、跨服务免共享存储；代价用黑名单+短 TTL 折中 |
| 黑名单会不会爆？ | key 的 TTL = 令牌剩余寿命，令牌自然过期即自动清理 |
| 为什么 refresh 要轮换？ | 泄露后可被发现（双方互相刷失效）；旧令牌立即作废 |
| 网关验签还是各服务验签？ | 只网关验签 + 内网信任 + 入口剥离伪造头；若内网不可信需加内网签名 |
| Redis 挂了怎么办？ | 黑名单查询 fail-open + 告警（可用性优先），生产中再加本地缓存兜底；这个取舍要主动说出来 |
| 异步任务丢用户怎么办？ | TaskDecorator 传递并在 finally 清理，防止线程池复用导致"身份串号" |
