### 4.1 启动期真实故障与修复（本轮实测，面试可讲）

| # | 故障现象 | 根因 | 修复 | 代价 |
|---|---|---|---|---|
| 1 | llmall-shop-service 启动失败：`Failed to start bean 'documentationPluginsBootstrapper'` → `WebMvcRequestHandlerProvider` NPE | springfox 2.10.5 假设 `HandlerMapping` 里只有 `RequestMappingHandlerMapping`，Boot 2.6+ 默认 `PathPatternParser` 后混入其他 mapping，遍历时 NPE | 4 个新服务加 `springfox.documentation.auto-startup: false` | 这 4 个服务的 `/doc.html` 不可用（其余 5 个服务文档正常） |
| 2 | llmall-content-service / llmall-search-service 启动失败：`No fallbackFactory instance of type ShopClientFallback found for feign client llmall-shop-service` | 降级类放在 `llmall-api` 里靠 `spring.factories` 自动装配，而 `llmall-api` 是普通 jar（无 `@Configuration` 扫描入口），**实测该类未被打进 jar**，自动装配不生效 | 在各自服务包内显式声明 `@Bean ShopClientFallback` | 每个用到该 Feign 客户端的服务需重复 3 行声明 |
| 3 | Nacos 共享配置拉取报 `YAMLException: MalformedInputException: Input length = 1` | 共享配置里的中文注释在 Windows 平台默认字符集下被写成非 UTF-8 字节，Nacos 按 UTF-8 解析失败 | `shared-mq.yaml` / `shared-swagger.yaml` / `shared-es.yaml` 改为**纯 ASCII** 后重新推送 | 共享配置里不能再写中文注释 |
| 4 | `/shops/nearby` 恒返回 `[]`（"附近门店"功能空白） | `queryHotList` 对 ZSet 榜单做了"未预热则回源 DB 并预热"，但 `nearby` 直接读 Redis GEO，**GEO 索引从未构建**（`rebuildGeoIndex()` 只有手动接口，没有调用方） | `nearby` 增加与榜单一致的惰性重建：GEO 为空时按 DB 坐标重建一次再重试查询 | 首次附近查询多一次 DB 全表扫描（仅冷启动一次，之后走 Redis） |
| 5 | 短信验证码登录（新手机号自动注册）返回 500：`Field 'create_time' doesn't have a default value` | `llmall-user.user` 是既有库里的表，`create_time/update_time` 是 `NOT NULL` 且**没有默认值**；而 `sql/merged` 里新建的 20+ 张表都写了 `DEFAULT CURRENT_TIMESTAMP`，只有这张老表漏了。自动注册是新增能力，初版没有这条插入路径，于是踩中 | 双层修复：① 应用层 `UserServiceImpl#loginByCode` 显式 `setCreateTime/setUpdateTime`（不依赖库默认值，换库也安全）；② 库层补 `sql/merged/22-user-time-default.sql`（与其它表对齐，双保险） | 无 |
| 6 | 网关日志出现 `parse data from Nacos error, dataId:gateway-routes.json`，且一度怀疑"网关没有路由表" | 网关的路由**不走路由属性源**：`com.llmall.gateway.router.DynamicRouteLoader` 用 Nacos `getConfigAndSignListener` 直接拉 `gateway-routes.json`，再用 `cn.hutool JSONUtil` 反序列化成 `RouteDefinition` 写进 `RouteDefinitionWriter`。我一度"多此一举"地在 bootstrap 里用 `extension-configs` 又导入了一遍同一份配置——根节点是数组的 JSON 无法展开成 PropertySource 键值对，于是报错；而配置里的中文注释在中文 Windows 上又会触发 `MalformedInputException`（同故障 3） | 删掉多余的 `extension-configs`（在 bootstrap 里写清原因，避免后人再踩）；路由表继续由 `DynamicRouteLoader` 从 Nacos 的 `gateway-routes.json` 读取，并给 shop 路由显式补上 `/shop-types` 路径 | 无（恢复原有机制后 ERROR = 0） |

> 排错小结 1（环境陷阱）：把 Sentinel 日志目录（`~/logs/csp`）设为不可写时，Sentinel 的 `DateFileLogHandler` 会在类初始化阶段抛 NPE，
> 导致**所有接口 500**。这不是业务代码问题，`-Dcsp.sentinel.log.dir=<可写目录>` 即可恢复——排查时先看是不是环境问题，别急着改代码。
>
> 排错小结 2（验证陷阱）：只断言"未登录返回 401"**不能证明网关配置正确**——鉴权过滤器在路由之前执行，
> 没有路由表时 401 一样会出现。必须再断言"公开接口能真正取到下游数据"（如 `/shops/hot` 返回 200 且有门店名），
> 否则会得出"网关已通过验证"的错误结论（本轮就踩了这个坑）。

### 7.3 本轮发现并修复的 7 个真实缺陷（按严重程度）

| # | 缺陷 | 后果 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | **`MqConfig` 没有注册进 `spring.factories`** | Jackson 消息转换器从未生效，**所有领域事件（order.paid / review.created / shop.hot.changed）发送即抛异常**，亮点 B、C 的事件闭环一直是断的（评价不影响热度、支付不发积分），且只在日志里表现为一句 error | `llmall-common` 的 spring.factories 只注册了 MyBatis/Mvc/Json 三个 Config，漏了 MqConfig | 补注册 `MqConfig`；经 E2E 验证"评价 → 热度重算 16.83→36.12""支付 → 积分到账" |
| 2 | **`CommonExceptionAdvice` 没有注册** | 所有业务异常返回 Spring 默认 500 错误页，前端拿不到 `msg`，用户只看到"HTTP 500" | 同上，且直接放 advice 进 spring.factories 会让**网关（WebFlux）因缺 `javax.servlet` 起不来** | 新增 `AdviceAutoConfiguration`（`@ConditionalOnWebApplication(SERVLET)` + `@Import`），网关不受影响，业务异常现在返回 `{"code":400,"msg":"订单不存在"}` |
| 3 | **购物车下单后清不掉** | "下单自动清购物车"静默失效 | 消费端用 `UserContext.getUser()` 过滤，而 **MQ 监听线程没有登录上下文**（恒为 null）；同时 listener 的 `cartService` 字段非 final 也无 `@Autowired`，Lombok 不注入 → 恒为 null | 事件改带 `userId`（新增 `CartClearEvent`）；字段改 final；消费端显式传 userId |
| 4 | **支付方式枚举不一致** | 前端按订单侧约定传 `payType=3`，llmall-pay-service 直接拒绝："抱歉，目前只支持余额支付" | 订单侧 `paymentType=3` 表示余额，支付侧 `PayType.BALANCE=5`，两套枚举含义不同 | 前端支付单申请改传 `payType=5`，并在代码注释里写明两套枚举的差异 |
| 5 | **`blog.images` 无默认值** | 前端"发布评价"不带图片就 500，**整条评价→热度闭环被卡住** | 既有表 NOT NULL 且无默认值 | 应用层 `blankToDefault("")` + `23-content-image-default.sql` 补默认值 |
| 6 | **门店人均价格单位不一致** | 门店卡片显示"人均 ¥0.8"（应为 ¥80） | `shop.avg_price` 存的是"元"，而对外契约与前端 `money()` 都按"分" | 门店 DTO 转换时 ×100；注意 Redis 缓存的旧 DTO 需要失效后才看得到 |
| 7 | **`product` 分页查询缺筛选** | 商城无法按分类/门店/关键词筛选，也没有"我的订单"列表、地址没有增删改 | 原工程只做了无条件分页与只读地址 | 补齐 `/items/page` 筛选与 `/items/categories`、`/orders` 列表与 `/orders/{id}` 明细、`PUT /orders/{id}/cancel`、`/addresses` 增删改 |

### 7.8 第五轮：支付与订单链路的三个真缺陷（用户实测"付完变待付款/已取消"）

**用户反馈**：前端买套餐，支付完成后订单没变"已支付"，反而显示"待付款"或"已取消"。

排查后确认是三个独立缺陷叠加，全部已修复并用端到端断言固化：

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 1 | **订单 10 秒就被自动关单** | `createOrder` 里写死 `setDelay(10000)`（10 秒）发延迟关单消息。用户从下单到输完支付密码往往超过 10 秒 → 订单已被关成"已取消"，此时再支付就变成"钱扣了、单关了" | 改为可配置 `llmall.trade.order-timeout-seconds`，**默认 900 秒（15 分钟）**；要演示"超时关单"把它改成 30 秒重启即可 |
| 2 | **支付时不校验交易订单状态与金额**（资损） | `tryPayOrderByBalance` 只校验支付单自身状态；`TradeClient` 里连"查询订单"的方法都没有，支付侧根本看不到订单是否已关闭；金额也完全采信前端传来的支付单 | llmall-api 新增 `TradeOrderDTO` 与 `TradeClient#queryOrderById`；支付前校验：订单必须存在、状态必须是"待付款"、**金额必须与订单一致**，否则直接拒绝（不扣款） |
| 3 | **支付成功后前端只等 800ms 就跳转** | 订单状态是「llmall-pay-service 发 MQ → llmall-trade-service 异步改」，跳早了页面还是"待付款"，用户以为没付成功 | 支付后**轮询订单状态**（最多 8 次 × 700ms）再跳转；订单详情页遇到"待付款"也会自动重刷 3 次 |

**端到端断言（`scripts/MallE2E.java` 扩到 34 项，本次实测 34/34 通过）**：

```
[通过] 已关闭订单禁止支付（防资损）      —— 拒绝原因: 订单已超时关闭，无法支付，余额 7529.0 未变
[通过] 重复支付被拒绝                    —— 交易已支付或关闭！
[通过] 支付金额篡改被拒绝                —— 支付金额与订单金额不一致，无法支付
[通过] 已支付订单不会被取消              —— 订单状态仍为 2
[通过] 下单 12 秒后订单仍可支付          —— 12 秒后状态 = 1（修复前第 10 秒就会被关单）
```

### 7.6 🔴 最重要的一条：`theme.css` 从来没被加载过（第三轮返工的根因）

用户反馈"排版乱了、空间利用率太低、上一轮问题没解决"，用真实浏览器测量后发现根因不在布局代码：

```
document.styleSheets 只有 1 个样式表：inline（125 条规则）
→ index.html 里只有一份 13KB 的内联 <style>（第一轮做的设计系统副本），
  而 theme.css（280 条规则，含商品卡/订单卡/核销码/分类金刚区/两列详情页…）根本没被 <link> 引用。
```

**后果**：页面是「新 HTML 结构 + 旧 CSS」，所有新组件样式全部失效 ——
`.item-top`/`.pkg-grid`/`.two-col` 的 `display:grid` 不存在，网格塌成一列（商品详情页封面高度只有 52px、套餐一行一个），
于是表现为"排版乱了、右半边全空"。

**修复**：删掉 index.html 里的内联样式副本，改为 `<link rel="stylesheet" href="theme.css" />`（设计系统单一来源），
并顺手把主题样式集中在 theme.css 维护。

**修复前后实测对比**（1440px 视口，真实渲染测量）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `.item-cover`（商品详情封面） | 1140 × **52** | **776 × 484** |

| 留白检测（子元素占用率 <75%） | 多处 | **无** |
| 样式表 | inline 125 条 | **theme.css 269 条** |

> 本轮新增 `scripts/StaticServer.java`（本地静态服务器，避开 file:// 的 CORS 干扰）与
> `scripts/layout-probe.js`（注入页面的布局探针：网格列数 / 留白率 / 横向溢出 / 接口错误 / 文本裁切），

## 九、收尾轮：Sentinel 地址统一（2026-10-11）

### 9.1 排查到的问题

清点 11 个模块的 `spring.cloud.sentinel.transport.dashboard` 后发现**三种口径并存**：

| 模块 | 原值 | 问题 |
|---|---|---|
| llmall-cart-service | `localhost:8090` | 从教程抄来的，服务跑在别的机器上时指向自己 |
| content / promotion / search / llmall-shop-service | `<vm-ip>:8090` | 值对，但硬编码，改地址要改 5 个文件 |
| llmall-gateway / item / pay / trade / llmall-user-service | **未配置** | 完全没有，接控制台时这 5 个服务看不到 |
| README 服务表 | `notice-service = 8090` | 与计划中的 Sentinel 控制台端口冲突 |

另外确认：VM（<vm-ip>）与宿主机的 **8090 都未监听**，即控制台从未部署过；
Sentinel Dashboard 默认端口 **8080 会与网关冲突**，这是"照默认命令起控制台必然失败"的坑。

### 9.2 落地的改法

所有服务统一读同一个占位符，**默认值即 VM 地址**，因此不配任何东西也能跑，改地址只改一处：

```yaml
spring:
  cloud:
    sentinel:
      transport:
        dashboard: ${llmall.sentinel.dashboard:<vm-ip>:8090}
```

- 5 个缺失的模块：在各自 `application.yaml` 的 `spring.cloud:` 下新增 `sentinel.transport.dashboard`；
- llmall-cart-service：`localhost:8090` → 占位符形式；
- 其余 4 个：硬编码值 → 占位符形式（值不变，但收敛为单点可覆盖）；
- 覆盖方式：`--llmall.sentinel.dashboard=ip:port` / 环境变量 `LLMALL_SENTINEL_DASHBOARD` / Nacos 里加 `llmall.sentinel.dashboard` 任选其一，**不需要改代码**；
- README：`notice-service` 端口 8090 → 8091，8090 显式保留给控制台，并补「Sentinel 控制台（可选部署）」一节
  （含 `-Dserver.port=8090` 的启动命令与 `sentinel/sentinel` 默认口令）。

### 9.3 验证证据（不是"改完就说好了"）

1. 中途一次批量替换把正则捕获组里已含的 `dashboard: ` 又拼了一遍，4 个文件变成
   `dashboard: dashboard: ${...}` —— **YAML 里这是语法错误（值中不允许出现 `: `），会导致服务起不来**；
   已用 `^(\s*)dashboard:\s*dashboard:\s*` → `${1}dashboard: ` 修正，并逐行打印确认。
2. 启动实测：`llmall-gateway`（新增配置者）与 `llmall-shop-service`（被误改后修正者）均
   `Started ... Application`，**无 ERROR、无 `Failed to parse / mapping values are not allowed`**，
   网关 `Netty started on port 8080`，证明 `application.yaml` 合法且占位符默认值可解析。
3. 静态断言：10 个服务（网关 + 9 个业务）的 `dashboard` 行**逐字符一致**、无重复键；
   `llmall-api` / `llmall-common` 是公共库，本就不需要该配置。
4. 进程卫生：验证用的 JVM 全部已 `Stop-Process`，残留 java 进程 = 0。

> 说明：因为控制台未部署，"客户端能否连上控制台"无法验证；已验证到的是
> **配置合法 + 占位符可解析 + 服务可正常启动**。规则本身由 `@SentinelResource` 注解定义，
> 不依赖控制台即生效——这也是"不部署控制台也能交付"的原因。

## 十、修正轮：控制台落位与网络口径（2026-10-11）

### 10.1 结论变了：控制台留在宿主，不进 VM

第九节的默认值 `<vm-ip>:8090` 建立在"控制台部署在 VM"的前提上。实际运行拓扑是
**服务在 Windows IDEA、中间件在 VM**（见各服务 `application-local.yaml` 的注释），于是：

- 若控制台真按第九节进 VM，规则推送方向是**控制台 → 客户端 8719**，而客户端上报的是 WLAN 地址
  （`192.168.31.20`），VM 连不上 → "机器列表能看到、规则推不下去"；
- 结论：控制台**与应用同机**（宿主 Windows 8090），默认值随之改为 `localhost:8090`，
  IDEA 里起服务即可直接连上；换环境用 `--llmall.sentinel.dashboard` / `LLMALL_SENTINEL_DASHBOARD` /
  Nacos 配置项覆盖（三种方式都无需改代码）。

改动：10 个 `application.yaml` 的占位符默认值 `<vm-ip>:8090` → `localhost:8090`，
注释同步改为"默认与宿主同机 + 三种覆盖方式 + 控制台默认端口 8080 会撞网关"。

### 10.2 顺带修掉的三个真实缺陷

| # | 问题 | 证据 / 影响 |
|---|---|---|
| 1 | `llmall-shop-service/application.yaml` 里 `dashboard: ${...}# Sentinel 控制台（部署在虚拟机内）` —— `#` 前**没有空格** | YAML 规定注释必须与值之间有空白，否则整段说明属于标量值本身。客户端拿到的地址是 `localhost:8090# Sentinel 控制台…`，Sentinel 连接必然失败（不是"连不上控制台"这么简单，是地址本身就是坏的） |
| 2 | infra compose 的 Redis 密码写的是 `123` | 实测 VM Redis 密码是 **123456**（`AUTH 123` → WRONGPASS，`AUTH 123456` → OK，版本 7.0.15），各服务 `application-local.yaml` 里也是 123456。按原文件起中间件会"启动即 Redis 连接失败"，已改成 `${REDIS_PASSWORD:-123456}` 并加注释 |
| 3 | 两份中间件 compose 打架 | `docker/docker-compose-infra-lite.yml`（容器名 `mysql`/`redis`/`nacos`/`rabbitmq`、无 networks）与 `llmall/deploy/docker-compose-infra-lite.yml`（容器名 `infra-*`、接 local-life）；`.env.example` 与应用编排用的是前者那套容器名 → 用后者起中间件必然 `UnknownHostException: mysql` |

### 10.3 网络口径统一

同一件事此前有三种写法：无 networks（用项目默认网络）、`infra-net` 兜底 `${INFRA_NETWORK:-bridge}`、
`local-life`（external）。现在统一为**一个 external 网络 `local-life`**（`${APP_NETWORK:-local-life}`）：

- `docker/docker-compose-infra-lite.yml`：把 compose 的**默认网络**整体改名成 `local-life`（服务不必逐个写 `networks:`）；
- `docker/docker-compose-addon.yml`：Seata/ES/Kibana 的 `infra-net` 指向同一网络；
- `llmall/deploy/docker-compose-infra-lite.yml`：**废弃**（只留说明，防止第二份事实来源继续漂移）；
- `llmall/deploy/docker-compose-apps.yml` + `.env.example`：新增 `LLMALL_SENTINEL_DASHBOARD`（默认 `<host-gw>:8090`，即容器经 VMnet8 回连宿主控制台），Redis 密码样例改为 123456。

### 10.5 本轮新发现：客户端默认是"惰性注册"

`spring-cloud-sentinel` 的 `SentinelAutoConfiguration.init()` 只在
**`spring.cloud.sentinel.eager=true`** 时才在启动阶段调 `InitExecutor.doInit()`；
默认 false 时客户端要**等第一次业务请求**才会初始化（绑定命令端口 + 向控制台发心跳）。
所以"服务起来了但控制台里空的"很可能不是没连上，而是还没人访问过它。

实测对比（llmall-cart-service，同一份代码只改配置）：

| 配置 | 起服务后不发任何请求 | 控制台结果 |
|---|---|---|
| 默认（不配 eager） | 8719/8720 都没有监听 | `/app/names.json` 只有 `sentinel-dashboard` ❌ |
| `eager: true` | 命令端口 8720 立即可见 | `/app/names.json` = `["llmall-cart-service","sentinel-dashboard"]` ✅ |

因此给**5 个真正引了 Sentinel 客户端的服务**（cart / shop / content / promotion / search）的
`application.yaml` 都加了 `spring.cloud.sentinel.eager: true`；
另外 5 个（gateway / item / pay / trade / user）只有 dashboard 配置、没引客户端依赖，
配置本来就是空转的，可读性上保持原样（要接控制台得先补依赖）。

### 10.7 VM 中间件实况（按实机截图核对后修正，2026-10-11）

在 VM 上执行 `docker network ls && docker ps` 得到的实况，和文档原先的假设有出入，据此改了 `.env.example`：

| 项 | 原先的假设 | VM 实测 | 影响 |
|---|---|---|---|
| RabbitMQ 容器名 | `rabbitmq` | **`mq`** | 容器化时 `LLMALL_MQ_HOST=mq`，照默认值会 `UnknownHostException` |
| Redis | 容器 `redis` | **不在容器里**（原生安装，7.0.15，密码 123456） | 容器里不能用容器名/127.0.0.1，要写宿主 IP `<vm-ip>` |
| 网络 | 单一网络 | `nacos` 在 bridge，`mysql`/`mq` 在 llmall-net | 所以要**逐个** `docker network connect local-life <容器>` |
| Redis 与 infra compose | 可直接起 compose | 6379 已被原生 Redis 占用 | 以后真要迁 Redis 进容器，必须先停原生 Redis，否则端口冲突 |

执行接入时两条"错误"都是预期，不是失败：

- `No such container: redis` ← Redis 不是容器，本来就不该 connect；
- `endpoint with name X already exists in network local-life` ← 重复执行 connect 的提示，
  恰好证明上一次已经连上了（`docker network inspect local-life` 能看到 `mysql nacos mq` 即为成功）。

> 结论：VM 上只能走"**接现役容器**"这条路；"按 compose 重建"会新建数据卷（库表全空），
> 且现役容器已占用容器名与端口（3306/8848/5672），`docker compose up` 起不来。
> 这一点已写进 `deploy/部署说明.md` 第 3.1 节和 `docker/docker-compose-infra-lite.yml` 的文件头。
