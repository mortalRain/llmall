# M7 进展与验收：搜索域落地（补齐最后一个骨架服务）

> 本轮把 `llmall-search-service` 从骨架做成可用的搜索域，**在不引入 ES 的前提下**完成
> 「评价 → 门店热度 → 搜索排序」闭环的**最后一跳**：门店检索结果按热度加权排序。

---

## 一、为什么不用 ES（这是本轮最重要的一个"选型判断"）

| 维度 | ES 方案 | 本轮方案（本地视图 + MySQL + Redis） |
|---|---|---|
| 内存 | 单节点至少 1G（还要 +Kibana 1G） | **0 额外进程**（复用已有 MySQL/Redis） |
| 适用规模 | 十万级以上、需要分词/相关性打分/聚合 | **万级门店**，条件为"关键词 + 类型 + 按热度排序" |
| 运维 | 索引 mapping、分片、重建、版本对齐 | 一张表 + 一个重建接口 |
| 能力边界 | 全文检索、拼音、纠错、复杂聚合 | 前缀匹配 + LIKE + 组合索引排序 |

**结论**：万级数据用组合索引 + 热度排序即可满足；**"评估过 ES 但按规模选择不引入，并预留演进路径"本身就是加分回答**。
若日后要上 ES，`shop_search_doc` 的结构可直接作为索引映射，业务代码只换检索实现。

## 二、本轮实现

### 核心设计：事件驱动构建本地读模型（CQRS 的最小落地）

```
llmall-shop-service 热度重算 → MQ(shop.hot.changed) → llmall-search-service 更新本地视图 shop_search_doc
                                                          ↑
                             首次部署/视图损坏时：POST /search/view/rebuild 全量重建
检索时：只查本地视图表（按 hot_score 排序），**检索路径上没有任何跨服务调用**
```

| 文件 | 说明 |
|---|---|
| `domain/po/ShopSearchDoc.java` | 门店搜索视图（读模型），含 `eventTime` 用于防乱序 |
| `domain/po/SearchHotWord.java`、`SearchHistory.java` | 热词落库、搜索历史 |
| `service/impl/SearchServiceImpl.java` | 检索、热词、建议、历史、视图增量与全量维护 |
| `listener/ShopHotChangedListener.java` | 消费 `shop.hot.changed`，闭环最后一跳 |
| `task/HotWordSyncTask.java` | 热词定期落库（高频写走 Redis，低频汇总进 MySQL） |
| `controller/SearchController.java` | 检索 / 热词 / 建议 / 历史 / 重建视图 |
| `llmall-api/dto/ShopPageDTO.java` | 跨服务分页 DTO（**契约模块不引 ORM 依赖**） |
| `sql/merged/40-search.sql` | 新增 `shop_search_doc` 表 |

### 接口清单
```
GET    /search?keyword=&typeId=&page=&size=   门店检索（公开，按热度排序）
GET    /search/hot-words?limit=               热词 Top N（Redis ZSet）
GET    /search/suggest?prefix=&limit=         搜索建议（前缀匹配）
GET    /search/history?limit=                 我的搜索历史（需登录）
DELETE /search/history                        清空历史
POST   /search/view/rebuild                   全量重建搜索视图
```

## 三、两个值得讲的工程细节

### 1. 事件幂等 + **防乱序**（比幂等更进阶）
视图更新是 upsert，重复消费结果一致 → 天然幂等；但 **MQ 不保证顺序**，旧事件后到会把新数据覆盖回去（典型"数据回退"故障）。
处理方式：用事件里的 `occurredAt` 与视图记录的 `eventTime` 做**版本比较**，只接受更新的：

```java
if (exist != null && eventTime.isBefore(exist.getEventTime())) {
    log.info("收到过期的热度事件，忽略");
    return;
}
```
> 可以这样讲：幂等解决"重复"，版本号解决"乱序"，两者是不同的问题，都要处理。

### 2. 契约模块（llmall-api）不能引 ORM 依赖
一开始我把 Feign 方法的返回类型写成 `llmall-common` 的 `PageDTO`，编译立刻失败：
`PageDTO` 内部引用了 MyBatis-Plus 的 `Page`，而 llmall-api 是"纯契约模块"，没有（也不该有）ORM 依赖。
**修复**：在 llmall-api 里新建轻量 `ShopPageDTO`（字段名与 `PageDTO` 一致，JSON 可直接反序列化）。
> 这是真实的编译期反馈，也是一个很好的"共享库要尽可能小"的实践案例。

## 五、验收步骤

```powershell
$gw = "http://localhost:8080"

# 0) 首次部署：先全量重建搜索视图（依赖 llmall-shop-service 已启动）
Invoke-RestMethod -Method Post -Uri "$gw/search/view/rebuild"

# 1) 检索（公开接口，未登录也能搜）
Invoke-RestMethod -Uri "$gw/search?keyword=烧烤&page=1&size=10" | ConvertTo-Json -Depth 3

# 2) 热词（刚搜过的词应已计入 ZSet）
Invoke-RestMethod -Uri "$gw/search/hot-words?limit=10" | ConvertTo-Json -Depth 3

# 3) 建议（前缀）
Invoke-RestMethod -Uri "$gw/search/suggest?prefix=烧" | ConvertTo-Json -Depth 3

# 4) 闭环验证：给某门店发一条 5 分评价，等几秒后重搜，
#    观察该门店在检索结果中的排名提升（原因：热度分上升 → 视图更新 → 排序变化）
```

**期望结果**：重建接口返回同步条数；检索按 `hotScore` 倒序；热词 ZSet 有计数；
发评价后同一关键词的检索结果里，被评价门店排名上升。

## 六、常见追问预判

| 追问 | 答题要点 |
|---|---|
| 为什么不用 ES？ | 数据规模万级、查询是"关键词 + 类型 + 热度排序"，组合索引足够；ES 要多 1G+ 内存与整套运维，**按规模选型**；并说明已留好演进路径 |
| 搜索数据怎么和门店保持一致？ | 事件驱动增量（`shop.hot.changed`）+ 全量重建接口兜底；检索不跨服务调用，避免 N+1 与延迟放大 |
| 为什么不用 Canal 订阅 binlog？ | 需要 binlog 权限与额外组件；用业务事件与现有架构一致，代价是必须提供全量重建入口（已提供） |
| 消息重复/乱序怎么处理？ | 幂等靠 upsert，乱序靠事件时间版本比较（分两个问题回答） |
| 热词为什么放 Redis 再落库？ | 每次搜索 +1 属高频写，直接写库会打满 MySQL；ZINCRBY 原子累加，定时汇总落库 |
| 深分页怎么办？ | 检索侧用游标或限制 max page；榜单 ZSet 用分数区间，避免 `ZRANGE 10000 10020` |
| 前缀建议为什么不用 ZSet 的 ZRANGEBYLEX？ | 热词 ZSet 的 score 是次数，字典序区间查询会失效；当前用 MySQL `LIKE 'kw%'` 走索引（数据量小）；要更强的建议能力才需要 ES completion suggester |

> 注意：搜索域的实现细节（如"检索侧 max page 限制"）目前只做了 `size` 上限，`page` 上限可后续补 —— 被问到时**如实说明**即可。
