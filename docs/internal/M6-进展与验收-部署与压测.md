## 二、配套的配置改造（让"同一产物到处能跑"）

| 改造 | 位置 | 原因 |
|---|---|---|
| Nacos 地址改用环境变量占位 | 6 个服务的 `bootstrap.yaml`：`${NACOS_ADDR:<vm-ip>:8848}` | 原本硬编码 VM IP，镜像一上云就连不上 Nacos |
| 数据源/Redis/MQ 地址统一走 `llmall.db.host` 等占位符 | 各服务配置（此前已就绪） | 容器里用 `LLMALL_DB_HOST=mysql` 通过 Spring 宽松绑定覆盖，**不用改一行代码或重打镜像** |
| 父 pom 统一产物名 `<finalName>${project.artifactId}</finalName>` | `llmall/pom.xml` | 让 11 个 jar 路径可预测，Dockerfile 才能按固定路径 COPY |

> 这三条合起来就是"配置分层"的落地：**代码里只有占位符，具体值来自环境变量 / profile / Nacos**。
> 可以这样讲：换环境只改一份配置，不用重新打包。

### 一处环境限制（需要你联网一次）
**打包（`mvn package`）无法离线完成**：本地仓库缺插件自身的传递依赖，实测缺：

```
org.codehaus.plexus:plexus-archiver:4.2.7
org.codehaus.plexus:plexus-io:3.2.0
org.codehaus.plexus:plexus-utils:3.3.1
org.iq80.snappy:snappy:0.4
org.tukaani:xz:1.9
```

**处理**：在 IDEA 里打开 `<repo-root>` → Maven 面板 **Reload All Maven Projects**（联网）即可，
这一次同时会把之前缺的 `spring-boot-starter-actuator` 与 `spring-boot-starter-data-elasticsearch` 拉下来，
拉完后请把 4 个新模块 pom 里标了 `TODO(依赖下载后取消注释)` 的依赖恢复。

> 编译（`mvn compile`）可完全离线验证，这是每轮我都在做的检查；打包是"部署前的最后一步"，需要网络。

## 四、压测三组对比（这是"数据有判断力"的关键）

| 实验 | 做法 | 产出结论 |
|---|---|---|
| 缓存开 vs 关 | 压 `GET /shops/{id}` 两次，第二次前清空 Redis 且临时关闭回填 | "缓存把 QPS 从 X 提到 Y，P99 从 A 降到 B" |
| 批量查 vs 逐条查 | `queryHotList` 已是批量 `listByIds` + 内存还原顺序 | 说明"为什么 ZSet 榜单要批量回源" |
| **消费者停机下的写链路** | 停掉 llmall-user-service，压 `POST /blogs` / 下单 | **写链路吞吐不受影响、消息堆积在队列、恢复后补齐** —— 亮点 B 最有力的证据 |

> 后两条比"QPS 多少"更有价值：它们证明的是**架构特性**，而不是机器性能。
