## 二、本轮修掉的真实缺陷（都是"能讲的故事"）

| # | 缺陷 | 危害 | 修复 |
|---|---|---|---|
| 1 | **扣库存 SQL 没有库存充足性判断**：`UPDATE item SET stock = stock - #{num} WHERE id = #{itemId}` | 并发下库存被扣成**负数（超卖）**；且原代码用 `SqlHelper.executeBatch` 的返回布尔值判断"库存不足"，那个值只表示"批次没抛异常"，**永远拦不住超卖** | 改为 `AND stock >= #{num}` 原子更新，按**受影响行数**判定（0 → 抛"库存不足"），整批放在本地事务内 |
| 2 | `ItemClient` 路径写成 `items//stock/deduct`（双斜杠） | 部分网关/客户端 404 | 改为 `/items/stock/deduct` |
| 3 | 服务间调用缺少幂等与流水 | 消息重投/重试时**重复扣减**，且事后无法对账 | `(biz_type, biz_id, item_id)` 唯一索引 + 先查流水再扣减 + 唯一键兜底 |
| 4 | `Page.of(...)`、`BaseMapper#exists(...)` | 编译不过 | 本项目 MyBatis-Plus 是 **3.4.2**，`Page.of` 与 `exists` 分别是 3.5.0 / 3.5.3 才引入，改用 `new Page<>()` 与 `selectCount()` |

## 三、技术要点（可直接使用）

### 1. 缓存三兄弟，一次讲清
| 问题 | 本项目的做法 |
|---|---|
| **穿透**（查不存在的数据，绕过缓存打 DB） | 查不到也缓存"空值"，TTL 只有 2 分钟（短 TTL 避免长期脏数据） |
| **击穿**（热点 key 过期瞬间并发全部回源） | **逻辑过期 + 互斥锁 + 异步重建**：发现逻辑过期先返回旧数据（可用性优先），拿到锁的线程异步重建；拿不到锁的线程直接返回旧数据，不确定等 |
| **雪崩**（大批 key 同时失效） | TTL = 基础 30 分钟 + **随机抖动 0~5 分钟** |

### 2. 热度分公式（亮点 C 的计算核心）
```
base  = score/10×4  +  log10(comments+1)×3  +  log10(sold+1)×3
decay = 1 / (1 + Δ天/7)          // 以「最近一次评价时间」为锚点
hot   = base × decay
```
- 评分权重最高，但除以 10 是因为评分按 ×10 存储；
- 评论数/销量用 **log** 抑制"刷量"和"爆款通吃"的边际效应；
- **锚点必须是"最近一次评价时间"**，不能用"重算时间"——否则每次重算都把衰减重置成 1，衰减形同虚设（这是设计时最容易写错的一处）。

### 3. ZSet 榜单的顺序坑
`SELECT ... WHERE id IN (...)` 的返回顺序**不保证**与 ZSet 一致，必须"按榜单 id 顺序还原成列表"，
否则榜单会莫名乱序。代码里已按这个方式实现并注释说明。

### 4. GEO 与 UV
- 附近门店用 `GEORADIUS`（`opsForGeo().radius` + `includeDistance().sortAscending().limit(n)`），返回距离；
- UV 用 **HyperLogLog**：0.81% 误差、固定 12KB，适合亿级 UV；每日落库一份到 `shop_stat`。
