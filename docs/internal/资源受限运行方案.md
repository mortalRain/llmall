# 资源受限运行方案（16G 内存机器）

> 背景：单跑 llmall（未起 ES / Seata / nginx）时，宿主 16G 已被占到 15.5G。
> 结论先说：**主要矛盾是"虚拟机固定吃掉了大半内存" + "每个 JVM 默认堆太大"，不是服务数量本身。**
> 按本方案改造后，10 个服务 + 全套中间件可以在 16G 机器上跑起来（ES 除外，见第四节）。

---

## 一、先算账：那 15.5G 到底花在哪

| 项目 | 默认状态 | 典型占用 | 可压到 | 说明 |
|---|---|---|---|---|
| Windows 系统 | — | 3.5–5 G | 3.5 G | 关掉无关启动项 |
| **VMware 虚拟机** | 常见分配 8 G | **8 G（全量占用，不归还宿主）** | **4 G** | ⚠️ **最大的一笔**，Docker 里的 MySQL/Nacos/MQ/Redis 实际只需 ~1.6G |
| IDEA | 默认堆 2048M | 2–3.5 G | 1–1.5 G | 调堆 + 关插件 + 索引完成后不再吃 |
| 浏览器 | Chrome 多标签 | 1.5–4 G | 1 G | 少开标签，或用 Edge |
| 业务服务 JVM | **默认堆 = 物理内存 1/4** | 8 个服务 ≈ 4–5 G | **10 个服务 ≈ 2.0 G** | 关键：加 `-Xmx` 限制 |

> **"默认堆 = 物理内存 1/4"** 是这里最隐蔽的坑：不加参数时，每个 Spring Boot 服务在 16G 机器上最大可申请 4G 堆，
> 8 个服务同时膨胀，内存瞬间见底。**加上 `-Xmx192m` 后，每个服务稳定在 150–250M。**

### 让你先确认三件事（1 分钟）
1. VMware 里这台虚拟机分配了几 G？（如果不是 4G，先改 4G 并重启虚拟机）
2. IDEA：`Help → Change Memory Settings`，看是不是 2048 或更大 → 改成 1024
3. 任务管理器按内存排序，看前三名是谁（大概率是 `vmware-vmx` + `java` + 浏览器）

---

## 二、措施一：给每个服务上"内存紧箍咒"（收益最大、改动最小）

IDEA → `Run → Edit Configurations` → 每个 Spring Boot 配置的 **VM options** 里填：

```
-Xms64m -Xmx192m -XX:MaxMetaspaceSize=128m -XX:+UseSerialGC -XX:TieredStopAtLevel=1 -Dspring.jmx.enabled=false -Dspring.main.lazy-initialization=false
```

| 参数 | 作用 |
|---|---|
| `-Xmx192m` | 堆上限；开发态业务量极小，192M 足够（堆小了 GC 也更快） |
| `-Xss512k`（可选） | 每个线程栈，服务线程多时可省几十 M |
| `-XX:MaxMetaspaceSize=128m` | 元空间上限，避免类加载器膨胀 |
| `-XX:+UseSerialGC` | 单核小内存下最省内存的 GC，避免 G1 的额外开销 |
| `-XX:TieredStopAtLevel=1` | 只做 C1 编译：**启动更快、JIT 内存更省**（开发态首选） |
| `-Dspring.jmx.enabled=false` | 关掉 JMX，省一点内存与启动时间 |

**效果**：单个服务从 400–600M 降到 **150–250M**。10 个服务 ≈ 2.0G，而不是 4–5G。

> 一次性做法：先配好一个服务的 VM options，其余服务复制粘贴即可（IDEA 支持选中多个运行配置批量编辑模板）。

## 三、措施二：中间件用「低内存编排」+ 按需启动

用 `docker/docker-compose-infra-lite.yml` 替换原来的编排，它做了三件事：

| 组件 | 关键限制 |
|---|---|
| MySQL | `innodb-buffer-pool-size=128M`、**关掉 performance_schema**（省 200–400M）、`mem_limit 512m` |
| Redis | `maxmemory 96mb`、关持久化、`mem_limit 160m` |
| Nacos | standalone + 内嵌 derby、`JVM_XMS/XMX=256m/384m`、`mem_limit 640m` |
| RabbitMQ | 内存水位 0.4、`mem_limit 320m` |
| Seata / ES | 放进 `profile=full`，**平时不起** |

要点：
- **VM 内存设 4G**（不是 8G）。中间件常驻只需约 1.6G。
- Seata 只在做 M4/M5 分布式事务实验时起：`--profile full up -d seata`
- ES 同理，只在 M6 需要时起，且用 `-Xms256m -Xmx256m`；**Kibana 直接不装**（省 1G，用 curl 看索引即可）。
- **nginx 不是内存问题**（进程才 10–20M），别为它纠结；真正吃内存的是浏览器标签页。

## 四、措施三：ES 到底要不要（三个选项，我的建议）

| 方案 | 本地内存 | 对外价值 | 适用 |
|---|---|---|---|
| **A. v1.0 不引入 ES**：搜索用 MySQL 多条件查询 + Redis ZSet 热度排序 | 0 | 中高（有选型理由） | **推荐**，先跑通闭环 |
| B. 用**云上免费 ES**（Elastic Cloud / Bonsai 免费层，或云厂商试用），本地只跑业务服务 | 0 | 高（是真 ES） | 有外网、想保留 ES 技能点 |
| C. 加内存条到 32G（DDR4 16G ≈ 200–400 元） | — | 高 | **最省事**，一次投入解决全部问题 |
| D. 需要时用 `profile=full` 起 ES（256M 堆） | 约 1.2G | 高 | 演示/压测时临时开 |

**关键认知**：不做 ES **不等于**对外材料里就不能写搜索。
本地生活场景里，门店量级在 1 万左右，**多条件筛选 + 热度排序用 MySQL + Redis ZSet 完全够用**；
而"我评估过 ES，但按当前数据规模与机器条件选择不引入，并把索引结构设计好了、留作规模化演进"——
这本身就是一个**加分的技术选型回答**，比"堆了个 ES 却说不出为什么"强得多。

> 对外材料措辞建议（不提 ES，但体现判断力）：
> "热度榜单采用 Redis ZSet（游标分页规避深分页），门店检索采用 MySQL 组合索引 + 热度加权排序；
> 针对十万级以上数据量的全文检索场景，已设计 ES 索引与 function_score 方案作为演进路径。"

## 五、措施四：开发态"最小启动集"（不是每次都要起 11 个）

| 里程碑 | 需启动的服务 | 需启动的中间件 | 常驻内存 |
|---|---|---|---|
| M2 亮点 A | gateway + llmall-user-service | MySQL + Redis + Nacos | ≈ 1.2 G |
| M3 门店/商品域 | gateway + llmall-shop-service + llmall-item-service | + RabbitMQ | ≈ 1.4 G |
| M4 交易闭环 | gateway + user + shop + item + cart + trade + pay | 全套 + **Seata** | ≈ 2.2 G |
| M5 亮点 B | M4 全套 + promotion | 全套 + Seata + MQ | ≈ 2.4 G |
| M6 亮点 C | gateway + content + shop + search | 全套（ES 可选） | ≈ 2.0 G |
| 最终演示/压测 | 全部 11 个（小堆） | 全套 + Seata（ES 按需） | ≈ 3.5 G |

按这个方式，日常开发时同时只有 2–4 个 JVM 在跑，**中间件的 1.6G 才是大头**，整机占用可以稳定在 8–10G。

## 六、改造前后对比（16G 机器）

| 项 | 改造前 | 改造后 |
|---|---|---|
| VM 占用 | 8 G | 4 G |
| 服务 JVM（11 个） | 4–5 G | 2.2 G |
| IDEA | 2–3 G | 1.2 G |
| 浏览器 | 2 G | 1 G |
| Windows | 4 G | 4 G |
| **合计** | **20 G+（爆）** | **12.4 G（可行，余 3.6 G）** |

## 七、终极方案（若仍吃紧）

- **把中间件搬到云服务器**：入门级 2C4G 云主机跑 MySQL/Redis/Nacos/MQ，
  本地只跑 IDEA + 服务，VMware 直接不用了 —— 省下整个 4G，还能顺便当"上线环境"，
  对外材料里"部署到云服务器"这一条也顺手有了。
- 这是我最推荐的长期方案：**本地轻、线上真**，还避免"只有本机能跑"的演示尴尬。

2. [ ] 用 `docker/docker-compose-infra-lite.yml` 重建中间件（先备份数据）
3. [ ] 给每个服务的运行配置加 VM options（第二节参数串）
4. [ ] 按里程碑"最小启动集"开发，不要一次起全部
