### 1.2 现成资产（可直接用，别重复造）

- **点评**：9 个 Controller、10 个实体、11 张表 —— `tb_shop` 自带 `score` / `comments` / `sold` 字段，是**亮点 C 的天然落点**；`tb_user_info` 自带 `credits`（积分）/ `level`（会员等级），是**亮点 B 的落点**。
- **商城**：`llmall-gateway`（已含 JWT + 限流骨架）、`user/item/cart/trade/pay` 五个业务服务、`llmall-api`（`ItemClient/CartClient/TradeClient/PayClient/UserClient` + DTO + Fallback）、`llmall-common`。
- **SQL**：`llmall-user / llmall-item（含 35MB 商品数据）/ llmall-cart / llmall-trade / llmall-pay` + 点评 `上游单体工程.sql`（11 张表 + 数据）。
- **中间件你都有**：VMware Ubuntu `<vm-ip>`（Redis、Nacos 8848）；本地 `nacos`、`sentinel-dashboard.jar`、`rabbitmq-plugins`、MySQL 安装包、Redis 7.2。
- **前端**：`llmall-nginx`、点评 `nginx-1.18.0` 静态页（可直接复用，避免做前端）。

### 1.3 五个必须统一的冲突（合并的全部难点都在这）

1. **版本**：Java 8 → 11、SB 2.3 → 2.7（点评代码要过一遍编译与 API 适配）
2. **用户体系**：点评 `tb_user`（phone 唯一 + MD5 密码 + nick_name/icon）vs 商城 `user`（username 唯一 + BCrypt + status/balance）
3. **订单模型**：商城 `order`（实物订单，status 1~6）vs 点评 `tb_voucher_order`（团购券订单，无状态机）
4. **数据源**：6 个库 → 归位到 5 个库 + 1 个新库
5. **鉴权**：点评拦截器链 vs 商城网关 JWT

## 2. 目标架构

### 2.1 服务与数据归属（核心表）

| 服务 | 端口 | 库 | 主要表 | 来源 |
|---|---|---|---|---|
| `llmall-gateway` | 8080 | — | 路由、JWT 校验、限流、**剥离外部伪造的用户头** | 商城（改造） |
| `llmall-user-service` | 8081 | `llmall-user` | `user`（**合并 `tb_user`**：补 `nick_name`/`icon`/`phone` 唯一索引）、`address`、`user_info`（点评扩展字段+`credits`/`level`）、`user_sign` | 商城 + 点评 |
| `llmall-item-service`（门店商品域） | 8082 | `llmall-item` | `item`、`sku`、`category` + **`shop`、`shop_type`**（新增） | 商城 + 点评 |

| `llmall-trade-service`（交易+营销域） | 8084 | `llmall-trade` | `order`（**加 `order_type`/`shop_id`/`voucher_id`/`verify_time`**）、`order_detail`、`order_logistics`、`voucher`、`seckill_voucher`（`tb_voucher_order` 并入 `order`） | 商城 + 点评 |
| `llmall-pay-service` | 8085 | `llmall-pay` | `pay_order` | 商城 |
| **`llmall-content-service`（新建）** | 8086 | `llmall-content` | `blog`、`blog_comments`、`follow`、`message_log`（本地消息表） | 点评（重写） |
| `llmall-common` / `llmall-api` | — | — | 工具类、Feign 客户端、DTO、`UserContext`、`RequestInterceptor` | 商城（扩展） |

> `legacy-monolith`（单体版遗留）**不迁移**，保留作为「单体 → 微服务拆分」的对照素材——面试讲演进过程时很好用。

### 2.2 业务闭环（这就是"为什么这两个项目该合"的答案）

```
用户浏览门店 → 看评价/笔记 → 买团购套餐 → 下单支付 → 到店核销
      ↑                                                    ↓
   榜单/推荐曝光  ←  门店热度分更新  ←  写评价/笔记  ←  核销完成
                          ↑
              营销（优惠券 / 秒杀团购 / 积分）
```

**评价内容影响门店曝光、门店热度影响搜索排序**——这条链路是点评域与商城域真正咬合的地方，也是面试时"为什么合并"的标准答案。

### 2.3 三条关键决策（每条都要能讲"为什么不那么做"）

1. **只新增 1 个服务**：营销（券/秒杀/积分）暂并入 `llmall-trade-service` 的「营销子域」。理由：券的本质是下单特例，独立 `llmall-promotion-service` 会带来跨 3 服务的强耦合与联调成本；**当营销规则复杂到影响交易主链路时再拆**——这个"何时拆"的判断本身就是架构能力。
2. **门店归 `llmall-item-service`**：门店 = 商家的"货架"，套餐/商品必须挂在门店下，同域内做关联查询，避免跨服务 join。
3. **不引入 ES / Canal / K8s**：本地（`<maven-repo>`）没有 ES 依赖，你的命令沙箱也无外网；用 **Redis ZSet + MySQL 聚合** 实现热度排序，反而让"缓存设计"成为可讲的技术点。**能跑起来 + 有一手数据 > 技术名词堆砌**。

## 3. 三个亮点设计

> 每个亮点都按同一模板准备：**背景 → 方案对比 → 落地步骤 → 量化指标 → 追问预判**。
> 面试官只会深挖 2-3 个点，所以只做 3 个，但每个都要能讲 10 分钟、能画图。

### 3.1 亮点 A：统一账号与跨服务身份透传

**背景**：原点评用「RefreshToken 拦截器 + LoginInterceptor + Redis 共享 session」，原商城用「网关 JWT + jks 密钥对」，两套用户表、两套登录、两套权限判断。

**方案**：
- **账号合一**：`user` 表以商城结构为主，补 `nick_name` / `icon`，`phone` 加唯一索引；点评的 `city/introduce/gender/birthday/credits/level/fans/followee` 全部落到 `user_info`（1:1）。
  密码策略：**统一 BCrypt**（点评的 MD5 历史数据在测试库里直接重置即可，不要为兼容留两套校验分支——面试官会追问"你到底用哪种"）。
- **登录双通道**：`/users/login`（用户名密码）+ `/users/login/sms`（手机号验证码，来自点评，验证码存 Redis，5 分钟过期）。
- **签发与校验**：网关用 jks 私钥签发 JWT；**下游服务不验签，只信网关**。
- **身份透传**：网关解析 JWT 后把 `userId` 写入请求头 → `llmall-api` 的 `RequestInterceptor` 把 `userId` 带进 Feign 调用 → 下游用 `UserContext`（ThreadLocal，finally 清理）取当前用户。
- **无感刷新**：access token 30min + refresh token 7d；网关侧对即将过期的 token 续期；登出时把 token 写入 Redis 黑名单（解决"JWT 无法主动失效"）。
- **【关键加分点】**：网关必须**剥离**外部请求里伪造的 `user-id` 头，否则任何人都能越权。这一点主动说出来，面试官会眼前一亮。

**量化指标**：下游服务取当前用户的远程调用次数 = **0**；鉴权代码从 N 处收敛到 **1 处**（网关）；登录→业务接口全链路 TP99（压测得出）。

**追问预判**：

| 追问 | 答题要点 |
|---|---|
| 为什么用 JWT 不用 Session？ | 无状态、跨服务免共享存储；代价是无法主动失效 → 用 Redis 黑名单 + 短 TTL 折中 |
| JWT 被窃取怎么办？ | 短 TTL + refresh 机制 + 黑名单 + HTTPS；承认"无法做到 Session 那样即时踢人" |
| 网关验签还是各服务验签？ | 只网关验签，内部网络信任 + 请求头剥离；若内网不可信则加内网签名 |
| ThreadLocal 内存泄漏？ | 拦截器 afterCompletion / finally 里 remove |
| 服务间调用用户丢失？ | Feign RequestInterceptor 透传，异步线程用 TaskDecorator 传递 |

### 3.2 亮点 B：跨域最终一致性（本地消息表 + MQ + 幂等 + 对账）

**背景**：一次团购下单要同时完成——① `llmall-item-service` 扣套餐库存 ② `llmall-trade-service` 建订单 ③ `llmall-user-service` 核销券/加积分 ④ 发通知。跨 3 个服务、4 个库。

**方案对比（一定要讲这张表）**：

| 方案 | 一致性 | 性能 | 侵入 | 适用 |
|---|---|---|---|---|
| Seata AT | 强 | 差（全局锁、undo_log） | 低 | 内部短事务、链路短 |
| TCC | 强 | 好 | **高**（每个参与方写 3 个方法） | 资金类核心 |
| **本地消息表 + MQ** | **最终** | **好** | 中 | **下单/发券/积分等可补偿业务（选它）** |
| RocketMQ 事务消息 | 最终 | 好 | 低 | 你用 RabbitMQ，不支持 |

**落地步骤**：
1. `message_log` 表：`id / biz_type / biz_id / payload / status(待发送/已发送/已完成/失败) / retry_count / next_retry_time / create_time`；
2. 下单主流程：**同一个本地事务**内写 `order` + 写 `message_log`（status=待发送）→ 提交后异步投递 MQ；
3. 消费端幂等：`consume_record` 表 `(biz_type, biz_id)` 唯一索引 + 冲突即跳过（或用 Redis `SETNX` 快速挡一层）；
4. 投递失败：定时任务扫 `status=待发送 且 next_retry_time<=now`，指数退避重发（1s/5s/30s/5min）；
5. **对账补偿**：定时任务（如每 5 分钟）比对「订单表已支付」与「库存扣减流水/积分流水」，发现缺口生成补偿消息；**补偿本身也要幂等**；
6. **故障演练（面试必讲）**：关掉 MQ 消费者 30 秒后再开，验证零丢单；同一条消息重复投递 1000 次，验证只生效一次。

**量化指标**：订单创建 TP99；故障注入后丢单数 = **0**；重复消息幂等命中率 100%；补偿任务最长恢复时间 < 1 分钟。

**追问预判**：为什么不用 Seata？（长事务锁表、AT 的脏读与回滚边界、跨库 undo_log 成本）｜消息丢了怎么办？（本地消息表 + 重试 + 对账三层兜底）｜消息重复怎么办？（唯一索引幂等，不能靠"MQ 不重复"）｜对账怎么设计？（按 biz_id 比对流水，缺口生成补偿）｜补偿会不会重复扣？（补偿走同一套幂等入口）。

### 3.3 亮点 C：评价 → 门店热度 → 榜单排序 准实时闭环

**背景**：原点评的笔记/评价与门店列表是**两件不相干的事**（评论数只增不减，列表按固定字段排序）；原商城有搜索但没有热度概念。这里把它们咬合起来——**这是你区别于所有教程项目的地方**。

**方案**：
1. `llmall-content-service` 写评价/笔记 → 落库 → 发 MQ 事件（`blog.created`）；
2. `llmall-item-service` 消费 → 更新 `shop.comments`、`shop.score`（聚合）→ 计算热度分 → 写 Redis ZSet `hot:shop:{cityId}`；
3. 门店列表接口：先读 ZSet 拿 id 序（`ZREVRANGE` + 分页），再批量查 DB 补详情；缓存 miss 时回源 DB 排序并回填；
4. 热度公式（**参数要能讲清**）：
   ```
   base   = score/10 * 4 + log10(comments+1) * 3 + log10(sold+1) * 3
   decay  = 1 / (1 + Δdays/7)          // 时间衰减，7 天衰减一半
   hot    = base * decay
   ```
   设计意图：评分占权重最高但用 log 抑制单次刷量的影响；时间衰减让新店有曝光机会（冷启动）；后续可加「人工运营权重」。
5. 一致性兜底：定时任务按 DB 重算并校准 ZSet（防止缓存漂移）。

**量化指标**：热度更新延迟 **秒级**（对比 T+1 批量统计）；榜单接口 QPS（压测）；缓存命中率；DB 与 ZSet 偏差 = 0（对账任务）。

**追问预判**：为什么不用 ES？（数据量 1w 级、排序规则自定义、引入 ES 的运维成本 > 收益；讲清"技术选型看规模"比硬上 ES 加分）｜ZSet 深分页怎么做？（游标 + 分数区间，避免 `ZRANGE 10000 10020`）｜缓存与 DB 不一致？（先写 DB 再发事件、对账校准、允许短暂不一致）｜会不会被刷分？（频率限制 + 权重衰减 + 异常检测，承认当前是简化版）。

### 3.4 亮点 D：秒杀团购券（白送，成本≈0）

点评已有完整实现，迁移即可：Redis Lua 原子「校验库存 + 一人一单 + 预扣减」→ MQ 异步下单 → 订单超时未支付回滚库存（延迟队列）→ 分布式锁兜底。**压测数据**：QPS、超卖 = 0、一人一单拦截率。

| **W7** | 亮点 D + 加固 | 秒杀团购券迁移（Lua + 一人一单）；缓存穿透/击穿防护；Sentinel 限流规则 |

### 砍功能优先级（保命规则：某周延期 > 3 天立刻执行）

1. 先砍 **亮点 D**（它是白送的，不影响故事完整性）
2. **亮点 C 降级**：MQ 实时 → 定时任务每 5 分钟批量重算热度
3. 搜索/复杂查询 → MySQL `LIKE`；前端 → 直接用现成 nginx 静态页，不做改造
4. **绝不砍**：亮点 A、亮点 B、上线可访问、压测数据（这四样是简历的骨头）

## 6. 简历与面试材料

### 6.1 项目名（三选一，别叫"合并项目"）

- 「同城生活电商平台」
- 「TongCheng 本地生活服务聚合平台」
- 「拾光 · 城市生活服务平台」

### 6.2 简历 bullet 草案（面向中小厂 + 国企银行，措辞稳健，不吹高并发）

1. 基于 Spring Cloud Alibaba 将本地生活平台拆分为 **9 个微服务**（网关/用户/门店商品/购物车/交易/支付/内容社区等），使用 Nacos 注册配置、Gateway 统一鉴权与限流；将两套历史账号体系（手机号验证码 + 用户名密码）合并为统一账号中台，鉴权逻辑由各服务收敛至网关，配合 Feign 请求头透传用户上下文，消除重复鉴权代码。
2. 下单链路需跨库存、营销、积分 **3 个服务 4 个库**协同，采用「**本地消息表 + RabbitMQ 最终一致性 + 消费幂等 + 定时对账补偿**」替代 Seata AT 强一致方案，规避长事务锁表；通过故障注入（消费者停机 30s、消息重复投递 1000 次）验证**零丢单、零重复扣减**。
3. 设计「**用户评价 → 门店热度 → 榜单排序**」准实时闭环：评价落库后经 MQ 异步聚合，热度分融合评分、评论量、销量并引入**时间衰减因子**抑制刷量、扶持新店冷启动，结果写入 Redis ZSet；门店榜单排序更新延迟由 T+1 降至秒级，并通过定时对账保证缓存与库内数据一致。
4. 基于 Redis Lua 脚本实现团购券秒杀（原子校验库存 + 一人一单 + 预扣减），MQ 异步下单削峰，配合订单超时回滚库存，JMeter 压测 QPS 达 **X**（实测值），超卖 **0** 单。

### 6.3 必答的"送命题"

> **Q：你为什么把两个功能差异很大的系统合在一起？**
> A（业务驱动，绝不能说"为了简历"）：本地生活到店场景里，**内容与交易是互相喂养的**——用户看评价决定买什么券，交易完成后的评价又反过来决定门店曝光；拆成两个系统，评价数据无法影响门店排序，闭环就断了。所以我把门店、套餐、交易、内容社区拆成 4 个域、9 个服务，并重点解决了跨域的一致性和"评价→热度→排序"的实时性问题。

## 7. 风险与降级

| 风险 | 应对 |
|---|---|
| **工期风险（最大）** | W1-W2 严格收口，W3 之后**冻结架构**；执行"砍功能优先级"；每周日自查进度，落后即砍 |
| **环境风险** | 中间件全在一台 VM（`<vm-ip>`），**先做快照**；Nacos/Redis/MQ 配置备份到 `<repo-parent>` |
| **缝合怪风险** | 每个模块必须能回答"它属于哪个域、为谁服务"；跨域调用一律走 `llmall-api`，禁止直接查别人的库 |
| **数据虚标风险** | 所有量化数据必须自己压测；测不出来就写定性描述（如"显著降低"），**不要编数字**——面试官一问细节就穿 |
| **时间被 Agent 项目挤占** | 若只剩 6 周：砍 W7，把 W5/W6 合并为 1.5 周（亮点 C 用定时任务版），保 W1-W6 主线 |
