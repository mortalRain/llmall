# llmall 面试手册（优化版）

更新：2026-10-30。配套[项目完整分析](项目完整分析-优化版.md)。本文件面向“能讲清楚、能找到代码、能承接追问”，不是需要逐句背诵的宣传稿。简历文件本轮不再修改。

## 1. 先建立一张项目地图

**一句话定位**：一个 Spring Boot/Cloud 同城生活电商个人项目，覆盖门店套餐、券、订单、余额支付、核销和内容搜索；优化重点是读链路效率、支付重复/未知结果处理，以及身份和权限边界。

**数量口径**：12 个 Maven 子模块 = 2 个共享库 + 网关 + 9 个业务服务；10 个 Java 运行服务。不要答“12 个微服务”，也不要把 MySQL、Redis 等中间件当业务服务凑数。

**数据归属**：商品管库存，交易管订单，支付管尝试与支付单，用户管余额和账号，营销管券；门店管员工关系；搜索和 Feed 是派生读路径。遇到追问，先说事实归谁，再说谁通过什么接口调用。

**关键组件的价值**：

| 组件 | 本项目里具体解决的问题 | 不能从它推导的结论 |
|---|---|---|
| MySQL/InnoDB | 行锁、条件更新、唯一键和持久状态，裁决同一笔业务的重复与先后 | 用了事务不等于跨服务原子提交 |
| Redis/Lua | 会话撤销/refresh 白名单、错误预算、缓存重建令牌、秒杀预扣、Feed/ZSet/GEO | Lua 只保证一次 Redis 执行原子，不覆盖 MySQL/MQ；哨兵同容器不等于 HA |
| RabbitMQ | 支付/订单结果传播、清购物车/积分等派生处理、延迟关单、失败重试/死信留存 | ACK 不代表消费者业务已完成，也不代表恰好一次消费 |
| Elasticsearch | 检索、建议和读侧索引，避免用业务表硬扛全文检索 | 不是订单/门店权威库，不保证与所有业务写实时强一致 |
| Nacos/Feign/Gateway | 配置/发现、跨域契约、统一身份入口 | 服务注册成功不代表所有依赖和流程就绪 |
| HikariCP/线程池 | 限制稀缺连接和后台任务的资源使用，提供等待/拒绝边界 | 增大池不必然提高容量，可能把排队转移到 DB |

## 2. 最值得主讲的三个专项

结合本次 Java 开发实习岗位的接口开发、排错、联调、AI 辅助和文档要求，继续采用**性能定位与优化 → 支付幂等与恢复 → 鉴权与权限保护**。缓存/搜索是性能里的深挖例子，通用 MQ 是支付恢复的支撑，不因新增一个测试就硬拆成第四段。第四备用专项为 Feed 游标和推拉读路径，有时间再讲。

### 专项一：从连接等待到减少读放大

**背景与挑战**：接口慢不只可能是 SQL 慢，还可能在等连接、串行 RPC 或做了额外探测；热点到期/Redis 故障又容易把压力集中到数据库。只改索引或盲目加线程无法解释问题。

**实现方案**：

- 用接口分段计时和连接池/SQL 信息区分排队与执行；合并 SQL、调整池参数，比较同条件结果。
- 门店缓存使用逻辑过期、短空值、异步重建；旧重建必须持有发布 token，写后失效撤销旧资格，防止旧值回填；后台任务和故障回源有上限。
- 搜索区分“没命中”和“整个索引未初始化”，缓存短期非空证据，冷/过期探测单飞；命中无需等待 count，搜索历史正常重复走 upsert。

**可量化成果**：历史支付申请接口 AVG **1083→360ms**、P99 **2374→620ms**，为 SQL 合并与连接池优化累计结果；当前门店组件 6000 热读 AVG 约 **1.000ms**、P99 约 **2.197ms**，无优化前对照；搜索组件 1 万文档、24000 请求，额外 count **5991→0**，旧策略为受控复刻。不要把几个环境混成同一份压测。

**可用的一句话**：通过分段计时定位连接等待与冗余查询，结合 SQL 合并、连接池调整及缓存/探测优化，历史申请支付接口 AVG 由 1083ms 降至 360ms、P99 由 2374ms 降至 620ms，并以组件实验验证热点读与搜索减放大。

**代码入口**：`PayOrderServiceImpl` 的分段计时；shop `ShopDetailCache` / `ShopCacheFallback`；common 缓存重建；search `EmptyIndexFallbackProbe` 和查询服务。数字入口为 `docs/P-01…`、`docs/shop-detail-http-verification.md`、`D:/codex/llmall-search-probe-20261029`。

### 专项二：支付幂等、未知结果与消息恢复

**背景与挑战**：用户双击、HTTP 重试、远程已扣款但回包丢失、本地提交成功但确认丢失、取消与扣款竞态，都可能使“超时就退款/重扣”产生错误。只用 Redis 锁或 `@Transactional` 覆盖不了全部过程。

**实现方案**：

1. 先在短本地事务中锁支付单、创建持久尝试；跨服务余额调用放在事务外，减少连接和行锁占用。
2. 同一尝试使用稳定业务键；用户域根据 MySQL 操作记录、行锁与流水决定扣款/取消，数据库唯一约束是最后防线。
3. 取消先记录意图再远程执行；已确认成功的尝试不能被失败回包误退，未知状态留给恢复扫描而不是猜测未支付。
4. 带券支付重新核对券绑定、订单 ID/用户/金额/状态；取消退券有锁与墓碑，避免取消先到后又绑定。
5. 支付成功通知可重发；通用本地消息表与业务同事务记录，提交后有界后台投递；**ACK 且无 return** 才记 SENT，失败独立短事务落重试状态。死信转发失败保留原消息，精确路由至所属服务死信队列。
6. 消费端用业务状态/唯一约束处理重复。发送成功和消费完成分开，不声称 Exactly Once。

**可量化成果**：HTTP/MySQL 组件验证 **100 并发、1500 组下单→建支付单→余额支付**；三轮 100 请求争同一支付单均 **1 次成功、99 次业务拒绝**，独立 SQL 检查只扣一次。最终通用 MQ 另有真实 Rabbit/MySQL **六场景**验证。当前构建另通过私有网关/服务联调基本闭环，不能把这些拼成“100 并发全栈压测”。

**可用的一句话（较完整）**：设计持久支付尝试与稳定业务幂等键，通过 MySQL 行锁、取消栅栏和恢复扫描处理重复请求及未知结果，100 并发 HTTP/MySQL 组件竞争每轮仅一次支付成功；结合消息确认、失败重试与死信保留完善结果传播。

**更短版本**：以持久支付尝试、数据库幂等和取消恢复保障余额支付，并通过消息确认、重试及死信兜底处理支付结果通知失败。

**如何补简历**：这轮最适合增加的是后半句 MQ 内容，或替换抽象的“保证可靠性”，不必把每一种异常塞满同一条。简历最终结果可写，过程和六个场景留面试展开。本手册提供文案，不代表已修改 PDF。

**代码入口**：pay `PaymentAttemptStore` / `BalancePaymentCoordinator` / `PaymentSuccessPublisher`；user 余额支付操作；promotion `VoucherPurchaseCoordinator` 和券绑定/取消；common `AbstractMessageLogService` / `ConfirmedMessagePublisher` / `MqDeadLetterConfig`。证据入口为 `docs/pay100-component-verification.md`、`docs/payment-reliability.md` 和本批收尾记录。

### 专项三：鉴权故障策略与门店权限并发

**背景与挑战**：token 有效不代表可以访问任意订单；“经过网关”不等于内部支付指令；Redis 出故障也不代表 token 已过期。员工管理还有两个店主同时撤销对方、旧快照沿用已撤销权限的问题。

**实现方案**：

- 网关剥离外部伪造头，再验证 JWT/撤销状态；私有资源 Redis 故障返回 503，公开读移除身份匿名继续，刷新拒发新令牌。
- access 黑名单、refresh 白名单与用户 iat 水位支持主动撤销；登录/支付口令分离，密码 BCrypt，支付连续每 5 错锁 5 分钟。
- 资源查询按当前用户检查归属；资金和内部变更要求独立服务凭据，不能仅凭正常登录。
- 管理员工先锁同店父行，再用当前读重查操作者与 OWNER 集合；同店串行、不同店独立，拒绝删除最后 OWNER。

**量化成果/价值**：员工权限 **6 项真实 MySQL 并发场景**覆盖最后 OWNER、旧事务快照、回滚、不同店等；鉴权故障分支有回归；新增真实改密页面验证了成功后清会话、旧 JWT 被拒绝。价值是把权限不变量落实到数据库和失败分支，不能换算成虚构吞吐或“100% 防攻击”。

**可用的一句话**：完善网关身份传播、会话撤销与依赖故障策略，以同店行锁和当前读保护员工权限及最后 OWNER 不变量，并通过真实 MySQL 并发与改密联调验证关键边界。

**代码入口**：gateway `AuthGlobalFilter`、user `TokenServiceImpl` / `PasswordAttemptGuard`；shop `ShopStaffServiceImpl` 与 Mapper。阅读 `docs/gateway-auth-dependency-failure.md`、`docs/shop-staff-concurrency.md`、`docs/pay-password-protection.md`。

### 第四备用：Feed 的游标边界

挑战是同分值、分页重复/漏项、hasMore 错误及推拉来源合并。实现统一 v2 游标与继续位置、受控候选集/合并及明确末页语义，有真实 MySQL 与前端回归。业务价值是翻页稳定性，不宣称对持续变化的数据形成数据库全局快照；历史 v1/v2 P99 不能直接当新版结果。

一句话：统一 Feed 推拉读取的 v2 游标与末页判断，覆盖同时间分值和边界翻页，提升动态信息流读取的可解释性与稳定性。

## 3. 必须讲清的决策与权衡

| 决策 | 为什么这样选 | 成本/边界 |
|---|---|---|
| 单店单履约，拒绝混单 | 让价格、券、核销归属明确，避免个人项目出现半套拆单 | 少支持一些业务组合，接口必须明确拒绝 |
| 默认本地事务+事件，Seata 关闭 | 不要求演示环境始终依赖协调器，也便于显式理解幂等/补偿 | 需要持久状态和重试；完整订单库存创建恢复仍未实现 |
| 支付 RPC 移出本地事务 | 本地事务回滚不了远程已提交余额；避免网络等待长期占连接/行锁 | 分成多个阶段，必须有持久尝试、取消裁决和恢复，不能只删注解 |
| MySQL 幂等作最终裁决 | 锁超时、进程崩溃、重复投递后仍保留业务事实 | 需要唯一键、短事务，热点行会排队 |
| Redis 用于控制和缓存 | 低延迟、TTL、原子计数，适合频控和重建协作 | 持久化/驱逐必须治理；不能代替余额账本 |
| 有界异步投递+扫描兜底 | 用户提交后不同步等 Broker，池满仍保留持久待办 | 通知可能变慢/重复；需监控待办年龄和失败，不是无限吞吐 |
| 死信失败重入队 | 不能 ACK 一个未确认转存的消息 | 可能重复/持续失败，须保留重试退避和人工处置，恢复原消息不等于永不热循环 |
| 缓存旧值可读+发布栅栏 | 到期不让所有请求等待数据库，防慢重建覆盖新状态 | 存在受控陈旧；Redis 失效失败仍要 TTL/恢复策略 |
| 源端时间+消费侧防旧写 | 小成本解决常见乱序 | 无严格全局因果序，同毫秒/时钟回拨仍有限制 |

## 4. 高频追问与推荐回答

### 支付与事务

**问：把远程扣款放在 `@Transactional` 里面，不就都能回滚了吗？**

答：Spring 的本地事务只控制本地数据源。用户服务余额提交后，支付服务回滚不会自动撤销那笔钱。放在事务内还会在网络等待时长期占支付连接/行锁。我先落持久尝试，再在事务外调用余额，最后短事务记结果；失败按同一业务键取消/查询，未知留恢复。这是在本项目约束下更合适的做法，不是所有系统唯一最优方案。

**问：请求超时能否直接重试？**

答：先区分查询和有副作用命令。远程扣款超时可能已成功，不能换业务键再扣。稳定键让同一次操作可识别；支付/取消由持久状态裁决。如果状态不能确认，返回待查询结果并恢复，不把异常当未支付。

**问：幂等是不是多次请求都返回成功？**

答：不是。业务效果不重复才是重点；接口可回放同一结果，也可拒绝已完成状态。本项目同单竞争的 99 个请求是业务拒绝，不能说 100 个都成功。还要检查余额、流水、支付尝试和终态，不能只数 HTTP200。

**问：100 并发只有几个数据库连接，算不算造假？**

答：并发请求数是系统内同时在途的请求，包含等待连接的时间；不等于同一瞬间有 100 条 SQL 执行。实验记录客户端和服务端实际在途峰值均为 100，数据库连接池限制了并行 SQL。介绍时同时说清配置和测试范围。

**问：全栈 100 和组件 100 哪个更好？**

答：全栈能覆盖网关、身份、RPC、Redis、MQ和部署参数，范围更广；组件实验更容易控制变量并定位幂等问题。两者价值不同，面试官关心能否说明边界和证据。本项目已有 100 HTTP/MySQL 组件证据和真实基础闭环联调，没有把它们改名为全栈 100。

**问：Redis 在支付里没有价值吗？**

答：有。网关验撤销/刷新、支付口令错误预算、限流和必要协作都能用 Redis，它能更早挡掉无效请求。扣款最终依靠 MySQL 业务键/行锁/账本，因为 Redis 锁过期、丢失或重启不能改变已经发生的资金事实。可使用 Redis 优化入口，不能用它单独证明只扣一次。

**问：普通购券和秒杀是同一套可靠性吗？**

答：不是。普通付费购券有持久购买尝试；旧收费秒杀新请求被关闭，免费秒杀仍是演示预扣流程，有 Redis→MQ 窗口。不要把普通购券的保证套给所有秒杀。

### MQ 与恢复

**问：发送返回了，为什么不能记成功？**

答：可能只是客户端写出，Broker 还没确认；即便 ACK，也可能无队列绑定而 return。因此要 correlated confirm 并检查 return，再记录 SENT。SENT 只是 Broker 接受/路由层面的状态，消费完成另外处理。

**问：afterCommit 为什么还要新事务？**

答：提交后的回调阶段可能仍保留原连接/会话资源，但原事务已经提交。直接写状态不等于会再次提交；旧一级缓存也可能读到过时数据。后台任务重新读取，在 `REQUIRES_NEW` 短事务落状态；等待 MQ 放在事务外。

**问：线程池满会不会丢消息？**

答：丢的是这次立即执行机会，持久消息记录仍是 PENDING，扫描会再投递。池使用拒绝策略，不让提交业务线程代执行 Broker 等待；有回归验证池满后记录仍在、扫描可恢复。还要监控积压，不能说无限故障下永远及时送达。

**问：为什么 SENT 还要补偿？**

答：Broker 接受不代表下游业务完成。对账可重发 SENT，但 DONE 不再重发；下游必须能处理重复。成功消息和业务处理之间不存在本项目级 Exactly Once 承诺。

**问：死信投递失败后怎么办？**

答：如果 recoverer 吞掉异常正常返回，监听容器可能确认原消息，而副本也没进死信队列。本项目只有确认转发后才完成恢复；失败抛显式重入队异常保留原消息。死信按所属服务精确路由，保留原队列、异常和 trace，等待人工/补偿处理。

**问：你真的测了故障，还是只 mock？**

答：单测覆盖 ACK/NACK/return/无确认/状态竞争和提交回调；另外真 Rabbit+私有 MySQL 验证了提交后 SENT、无路由、队列满真实 NACK、连接故障、死信路由失败保留原消息和恢复后的服务隔离。一个集成测试方法包含六场景，不说成六个独立测试类。

### 缓存、搜索和性能

**问：逻辑过期为什么还要令牌？**

答：逻辑过期解决请求是否等待，发布令牌解决谁还能写缓存。慢重建读完旧库值后，期间可能有新写入和失效；若失效不撤销旧任务，它会重新填旧值。发布前校验令牌，失去资格就不发布。

**问：“门店/类型 Mapper 查询为 0”什么意思？**

答：特定热读测量区间内，这两类数据库查询没有被调用，表示数据由缓存返回。它只说明这两条查询，不等于所有数据库、Redis、网关都零开销。简历不一定要堆这句，能解释缓存效果即可。

**问：调大连接池是不是通用最优？**

答：不是。先测连接等待和 SQL/RPC 耗时，结合 DB 最大连接和并发成本评估。增大后如果 DB 饱和，P99可能更差。1083→360 是多步累计结果，不能归因于唯一一个池参数。

**问：搜索 count 减到 0 会不会查不到新数据？**

答：减少的是额外的初始化/空索引判断，不是搜索本身。命中能证明索引非空；空结果按 TTL/单飞探测决定是否走读模型兜底。证据有寿命，索引被重建/清空后有过渡边界，不能缓存为永久非空。

**问：DATETIME(3) 就能解决所有乱序吗？**

答：只能避免原秒精度丢失毫秒，再结合锁内比较和 ES 条件更新挡常见旧写。源端同毫秒、跨节点时钟回拨仍可能不可比较；严格顺序要每实体单调版本或源端序列，本项目没有冒称已实现。

### 身份、权限和隔离级别

**问：access 黑名单、refresh 白名单、iat 水位是什么？**

答：黑名单记已经退出但尚未自然过期的 access；refresh 必须存在可用登记才能换新；用户水位记“此前签发的都失效”的时间界线，适合改密后统一撤销。它们解决不同粒度问题，Redis 驱逐/恢复也必须纳入运行治理。

**问：为什么有 token 还要服务凭据？**

答：token证明用户身份，不证明服务已完成扣款。标记已支付、余额内部指令必须要求服务调用凭据；网关会给普通已登录请求注入身份凭据，所以不能用同一个头判断内部命令授权。

**问：401、403、503 如何区分？**

答：401 是凭证无效/登录失效，403 是身份已知但无权限，503 是鉴权所需依赖暂不可用。把 Redis 故障说成401会误踢用户；更不能因读不到黑名单而放行私有资源。

**问：最后一个 OWNER 为什么不能 count 后再删？**

答：两个事务都可能看到有两个 OWNER，然后各删一个。先锁同一门店父行串行化管理，再当前读重新核验 OWNER 和操作者。RR 下先拿锁后做普通快照读仍可能沿用旧快照，不能认为“加了 FOR UPDATE”就自动修好所有后续读。

**问：锁住同一门店会不会影响整个站点？**

答：锁粒度是同店管理写入，不同店仍可并行；员工日常读取不等于全部要拿这个锁。用真实 MySQL 不同店用例确认粒度，而不是把全局 synchronized 当权限方案。

### 工程与个人贡献

**问：项目有什么明确没做完？**

答：完整订单创建库存预留/取消恢复、ES 持久索引 outbox和严格全局事件版本、跨主机 Redis HA、商用短信/真实支付等保留。最小流程和重点不变量做了验证，未实现功能按范围限制或明确标注。前端后台恢复也不能混为一谈。

**问：用 AI 做的，如何证明你理解？**

答：说明自己定义了范围和不变量，用 Codex辅助读代码/补丁，核对生成差异、事务、异常和副作用，再以失败回归、真实组件和 SQL核对确认。现场挑一处讲：支付订单 ID 校验为何在扣款前、afterCommit 为何新事务、旧快照为何当前读。不要把使用 AI 工具说成开发了大模型平台。

**问：Skills、MCP 与项目的关系？**

答：Skills 可组织复用的流程与资源，MCP 是工具/上下文接入协议。本项目本身没有 AI办公 Skill/RAG业务；真实可讲的是 AI辅助开发的审查和验证流程，不编造 Agent产品。

## 5. 面试表达顺序

### 30 秒开场

“这是一个同城生活电商个人项目，用 Spring Boot/Cloud 拆了网关和九个业务服务，支持套餐、券、订单支付和到店核销。我主要围绕慢接口定位、支付重复与未知结果、鉴权权限做优化。每项都保留代码、测试和数据库核对；组件测试与完整联调分别记录。我可以先讲一次接口优化，或讲支付超时为什么不能直接重扣。”

### 2–3 分钟主体

1. **20 秒业务地图**：用户买什么、在哪付款/核销、各域事实归谁。
2. **50 秒主专项**：症状→证据→根因→两三个关键改动→结果→一个边界。
3. **40 秒第二专项**：选一条异常时序，例如扣款回包丢失，用状态和稳定键讲清。
4. **30 秒第三专项**：用最后 OWNER 或 Redis故障区分401/503说明授权和失败策略。
5. **10 秒收住**：报证据入口，让对方选择深入哪处；不要把全部中间件名字念完。

### 追问展开模板

每次按“**输入/触发→原本会错在哪里→事实保存在谁那里→锁/事务/键如何裁决→失败怎样恢复→如何验证→还保留什么限制**”展开。先画三个盒子（调用者、事实所属服务、数据库/MQ）再讲代码，比背注解更容易。

若面试官问数字，先报测试范围，再报数据量/并发/指标/错误定义，最后给证据位置。不会或没测的部分直接说边界，不把设计推论变成实测。

## 6. 面试前按顺序复习

1. 对着本文画出“用户→网关→交易→支付→用户余额→MQ→交易”的调用图，写出每个域自己的表。
2. 阅读 `PaymentAttemptStore`、`BalancePaymentCoordinator` 和用户余额处理，手动推演：双击、扣款回包丢失、取消先到、成功提交丢确认。
3. 阅读通用消息基类，说明 record / afterCommit / ACK / SENT / DONE / retry 的区别；再读 recoverer。
4. 阅读一个缓存栅栏和一个 OWNER当前读例子；准备说出不用它们会错在哪个时序。
5. 查自己准备报的三个数字的原始证据；牢记 HTTP/MySQL 组件100与真实基础联调是不同实验。
6. 准备现场改一个小接口：参数边界、归属判断、错误码、失败用例、日志；这比背出更多框架词更符合本次实习岗位。
