# 通用 MQ 确认、重试与死信

范围：common 基类及交易/门店/内容本地消息表使用方。支付专用通知已有独立恢复协议，本批是补通用链路，不把二者说成同一个实现。

## 行为

1. `record` 与调用方业务同事务写消息。业务回滚就没有待办。新增事件必须登记 payload 类型，并具备业务唯一键。
2. `dispatchAfterCommit` 只把后台投递任务加入有界池：2 工作者、64 等待任务；拒绝时保留 PENDING，不在用户提交线程等待 Broker。扫描任务仍需启用调度。
3. 后台重新读记录；默认跳过 SENT/DONE，对账允许重发 SENT，DONE 不降级。
4. Broker 等待不占本地事务。`ConfirmedMessagePublisher` 使用 mandatory 与 correlated confirm；ACK 且无 return 才算本次已确认。默认确认等待 5000ms，可用 `llmall.mq.confirm-timeout-ms` 设置，合法区间 1–30000ms。网络连接等还受 Rabbit 自身超时控制，不能把此数误当全调用硬截止时间。
5. 发送状态通过 REQUIRES_NEW 短事务加行锁写入；失败指数退避，最多间隔 10 分钟。迟到失败不覆盖其他发送者的 SENT，任何发送结果不覆盖 DONE。
6. `markDone` 保持调用方事务语义；不能为了“独立提交”让它早于消费业务成功提交。
7. 重试耗尽转存死信时，必须确认 Broker 接受且有路由。失败抛 `ImmediateRequeueAmqpException`，原消息保留，不能正常返回导致容器确认原消息。已带死信标记再失败也不二次克隆。
8. 死信 routing key 精确使用 `<application>.dead.letter.queue`，保留来源/异常/trace。旧 `#.dead` 绑定不会匹配新版 `.queue` routing key；混合旧版发布者及遗留队列仍须升级时盘点。

SENT 代表发送层确认，不是消费者完成。超时、进程退出和对账都可能导致重复，消费者必须幂等；本实现不提供 Exactly Once。死信失败重入队可能重复和持续积压，需要退避、监控和人工修复，不宣传无限故障下零丢失/零热循环。

## 验证

自动回归包含 ACK、NACK、return、transport error、无确认、重试恢复、DONE 防覆盖、并发成功结果防覆盖、消费者先完成、真实事务提交/回滚；另验证线程池饱和拒绝和持久 PENDING 被扫描恢复、trace 不泄漏。

真实私有 Rabbit+MySQL：

- afterCommit 正常确认，独立连接可读到 SENT，原 trace 保留。
- 无路由 mandatory return，FAILED；补绑定后 retry 可发。
- 队列满 `reject-publish` 真实 NACK，不能 SENT；腾空后可恢复。
- 真实连接失败，FAILED；恢复连接后重试成功。
- 监听容器重试耗尽而死信无路由，即便 default-requeue-rejected=false 也保留原消息。
- 修复死信路由后，源消息被确认、所属死信队列有正确原文，其他服务死信队列为空。

原始结果：`D:/codex/llmall-final-closeout-20261029/mq-real-final/results.json`；1 个 JUnit 方法覆盖 6 个场景，不是六个方法。私有 DB 为 `llmall_outbox_test_*`；测试 Broker 有所有权标签、384MiB 上限和 loopback 端口，验收后停止。没有在业务 Rabbit 执行故障注入。

兼容边界：保留的四参数 `DeadLetterPublisher.publish` 仍计算旧 `<原队列>.dead` routing key，在只有新绑定时会失败返回 false。当前生产 recoverer 使用五参数显式目的地，没有现有四参数调用；后续应弃用旧重载或要求目的地，不把签名保留写成行为完全兼容。

## 升级与运维

- 部署前确认 Rabbit 的 confirm/return、业务与死信拓扑均可用，消费者重试与 recoverer 已装配，各消息表存在。
- 不删除积压旧消息、队列或历史记录来“消除错误”。迁移先盘点原 routing key、消费端版本、死信去向，再协调发布。
- 关注 PENDING/FAILED 数量、最老待办年龄、重复处理、死信积压、线程池拒绝和数据库连接等待；扫描串行处理在 Broker 故障时会变慢。
- 本批不新增消息平台/表，也没有改变正式业务环境；64/65 资金升级闸门依旧有效。
