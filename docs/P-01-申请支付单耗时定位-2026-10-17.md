# P-01 定位报告：申请支付单的 1072 ms 到底花在哪

> **状态：停点 —— 只定位、不改业务逻辑，等拍板优化方向。**
> 本报告不含任何优化改动；支付链路（`PayOrderServiceImpl`）本轮只增加了只读的分段计时。
>
> **2026-10-26 更新**：已落地方向 B（每请求取连接 2 次 → 1 次）+ 池 20 → 25，复测三轮见**第八节**。
> **目标 Avg ≤ 200 ms 未达成**（实测最好 358.5 ms），剩余瓶颈已量化到"同一连接池上余额支付事务内的
> 跨服务扣款"；第一节的定位结论保持不变。

---

## 一、结论先说

| 段 | 内容 | Avg | P50 | P95 | P99 | 占整条链路耗时 |
|---|---|---|---|---|---|---|
| `trade.queryOrderById#1` | 同步 Feign 查交易订单（`checkOrderPayable`） | **4.4 ms** | 2 ms | 5 ms | 22 ms | **0.4 %** |
| `pay.queryByBizOrderNo` | 按交易订单号查支付单（`checkIdempotent` 第一步） | **557.2 ms** | 562 ms | 779 ms | 1137 ms | **51.8 %** |
| `pay.idWorker.getId` | 生成支付单号（本地计算） | **0 ms** | 0 | 0 | 0 | 0.0 % |
| `pay.save` | 插入支付单（`checkIdempotent` 落库） | **512.4 ms** | 519 ms | 748 ms | 1729 ms | **47.7 %** |
| **`applyPayOrder` 整条链路** | 入口 → finally（含上面各段与间隙） | **1075.2 ms** | 1122 ms | 1373 ms | 2329 ms | 100 % |

（n = 1487 条 `POST /pay-orders` 请求；App=应用侧耗时，单位为毫秒）

**一句话**：**不是 Feign 慢，也不是单号生成慢 —— 是 pay-service 自己访问 MySQL 的第一步和第二部各花了半秒，
而这两半秒里约 87% 是"排队等数据库连接"，不是 SQL 本身慢。**

### 根因：`hikari.maximum-pool-size: 5` 把 pay-service 的 DB 并发钉死在 5

同一轮压测里从 pay-service 自己的 Prometheus 指标取的增量证据：

| 指标 | 值 | 含义 |
|---|---|---|
| `hikaricp_connections_max` | **5** | 池上限 5（来自 `nacos-config/shared-jdbc.yaml`） |
| `hikaricp_connections_active`（全程采样） | **恒为 5** | 5 条连接 100 % 占用，没有空闲 |
| `hikaricp_connections_pending`（全程采样） | **43 ~ 46** | 同一时刻有 45 个左右线程在排队等连接 |
| `hikaricp_connections_idle`（全程采样） | **0** | 无空闲连接可借 |
| 每次获取连接的平均耗时（acquire） | **517 ms** | 这是排队时间 |
| 每次真正使用连接的平均耗时（usage） | **65 ms** | 这含 SQL 执行 + 驱动 + 网络 |
| MySQL `Threads_running` 峰值 | **7** | 数据库自己并不忙 |
| MySQL 行锁等待（当前等待峰值 / 增量） | **0 / 351** | 不是行锁把请求卡住 |
| 连接获取次数（本轮增量） | **4575 次** | 与"apply 每请求 2 次 + 支付每请求 1 次"完全对得上（1530×2 + 1509×1 = 4569） |

两项一比就是全部答案：**一次 DB 操作 = 517 ms 排队 + 65 ms 执行**。排队占了 89 %。

### 吞吐天花板（用同一组数算得出来，且与实测吻合）

- 池上限 5 ÷ 单次占用 0.065 s = **≈77 次 DB 操作/秒**；
- 实测本轮 4575 次获取 ÷ 60 秒 = **76.3 次/秒** —— 已经贴着这个天花板，几乎没有余量；
- 申请支付单**没有事务**，SELECT 与 INSERT 各取一次连接、各还一次（这是 2 次/请求的来源）；
  余额支付**有** `@Transactional`，整段只占 1 次连接（1 次/请求）。
  这解释了一个此前没有量化的现象：同一套并发下，`POST /pay-orders`（1083 ms）比
  `POST /pay-orders/{id}`（728 ms）慢 —— 前者比后者多一次"取连接"。

## 二、怎么测的（可复现）

### 1. 埋点（只读，不改业务逻辑）

`llmall-pay-service/.../PayOrderServiceImpl.java` 里增加了一个私有静态内部类 `SegmentTimer`，
在 `applyPayOrder` 的 finally 里**一条日志打完所有段**（一次请求一行，避免日志 IO 本身变成瓶颈）：

```
[BIZ] stage=PROFILE phase=applyPayOrder bizKey=<交易订单号> totalMs=1075 seg=trade.queryOrderById#1:4 pay.queryByBizOrderNo:557 pay.idWorker.getId:0 pay.save:512
```

- 段口径：`begin()` / `record(name, begin)` 成对包裹被测调用；`finally` 里落日志，**失败路径同样有样本**；
- 另一处：`tryPayOrderByBalance` 里扣款前的那次 `tradeClient.queryOrderById`（第二处 Feign 回查）。
- 计时器不写库、不发消息、不抛异常、不改返回值；对业务结果的影响为零（分段日志开启前后账实核对同样精确成立，见第四节）。

**日志级别是 DEBUG，非常开 INFO**。定位时按包名临时开级，不必改代码：

```powershell
# 例：只对 pay-service 打开分段计时（其余日志级别不动）
JAVA_OPTS="... -Dlogging.level.com.llmall.pay.service.impl.PayOrderServiceImpl=DEBUG"
```

关闭时不会拼字符串（先判 `isDebugEnabled()`），主链路只剩几次 `nanoTime()` 的开销。
理由：分段计时是定位工具而不是生产语义日志 —— 常开 INFO 会给每个支付请求多写一行，
压测时日志 IO 还会反过来影响被测链路（这也正是"一条日志打完所有段"的原因）。

## 三、几处容易误判的地方（如实写）

1. **Feign 不是瓶颈**：`trade.queryOrderById#1` 的 P99 只有 22 ms（均值 4.4 ms）。
   台账此前猜测"瓶颈在交易订单远程校验 + 落库"，**前半句不成立**，后半句成立。
2. **单号生成不是瓶颈**：`IdWorker.getId()` 全程 0 ms（本地序列，不访问网络）。
3. **不是 MySQL 慢、也不是行锁**：全程 `Threads_running ≤ 7`、行锁当前等待峰值 0。
4. **不是某个 HTTP 线程卡住**：`pending` 峰值 45~46 与 50 并发同量级，说明请求都停在"等连接"这一步，
   而不是停在网关或 Feign。
5. **本轮为腾内存停掉了 shop / cart / content / search / promotion 五个服务**（宿主内存压测前 97 %，
   守卫脚本按红线拒绝了第一次启动）。因此**绝对延迟不与上一轮严格可比**，
   但**段间占比**这个结论不受影响 —— 五个被停服务都不在申请支付单链路上。
6. **未覆盖的段**：`claimDeductAttempt`（条件更新）、`markPayOrderSuccess`、扣款 Feign、
   事务收尾钩子。它们在 `POST /pay-orders/{id}` 里，已有 `BizTrace.cost` 的总耗时（728 ms），
   本轮没有再细分 —— 不属于 P-01（申请支付单）的范围。

## 五、优化方向（**只是选项，等拍板**）

按"改动小 → 大"排序，每一条都标了口径与风险：

| # | 方向 | 预期收益 | 风险与注意 |
|---|---|---|---|
| **A** | **抬 pay-service 的连接池上限**（5 → 15~20） | 直接按 Little 定律：吞吐 ≈ 池 ÷ 单次占用，池 ×3 则吞吐 ×3（排队时间降为 1/3） | ① 全局连接数要重新算账：11 服务 × 5 = 55，MySQL `max-connections=100` 只是勉强够；只抬 pay 到 20 → 70，仍留 30 余量，但**必须同时核对其它服务的峰值**；② 池不是越大越好，而 5 明显是把资源省到了错误的地方 |
| **B** | **把申请支付单的两次取连接合并为一次**（给 `applyPayOrder` 加只读事务，或把"先查后插"改成一条 upsert） | 每请求 DB 操作数 2 → 1，**同池上限下吞吐翻倍** | ① `applyPayOrder` 目前**故意没有事务**，唯一性靠 `pay_order.biz_order_no` 唯一索引兜底；加事务本身不改正确性，但会延长持锁时间，需要压测复核；② 改 upsert 会改"查到旧单即复用/重置"的分支逻辑，**属于支付链路结构调整，必须小步 + 每步过闸门** |
| **C** | **降低单次连接占用（65 ms）** | 直接抬高天花板 | 本轮 60 秒里 13,702 次 INSERT 产生 16,082 次 fsync —— 单次占用里很可能有一部分是提交时的落盘等待。任何涉及 `innodb_flush_log_at_trx_commit` 的调整**是持久性取舍，属资损红线**，不建议在本轮动 |
| **D** | **余额支付链路不要在事务里调远程** | `POST /pay-orders/{id}` 的 743 ms 里，连接被整段占着（含 `userClient.deductMoney` 的 Feign 往返） | 这是**资金链路的事务结构调整**，风险最高，且不属于 P-01（申请支付单）范围。建议先只记录，不动 |
| — | ~~去掉/异步化 `tradeClient.queryOrderById`~~ | **不建议**：它只占 0.4 % | 而且它是资损防线（订单已关闭却继续扣款的唯一拦截点），**不能动** |

### 我建议的最小第一步

**只做 A**（抬池上限），因为它是配置层、不碰代码分支、可一步回滚，且能直接验证"排队是不是真因"：
若抬池后 Avg 从 1075 ms 掉到 ~300 ms 级、且 `pending` 归零，则根因确认，B/C/D 才有必要谈。

## 五·补、抬池验证结果（2026-10-17 第二轮，pool 5 → 20）

> **这一节的结论与上面的预期不完全一致，如实记录：抬池把延迟砍了一半，但排队没有归零。**

### 1. 先说一个必须先解决的前置障碍：**池上限在这个项目里改不动**

按任务要求先在服务自己的 `application.yaml` 里写 `maximum-pool-size: 20`，重启后以
`/actuator/prometheus` 的 `hikaricp_connections_max` 为准逐一验证，**五轮全部仍为 5.0**：

| # | 覆盖方式 | 结果 | 原因 |
|---|---|---|---|
| ① | 写进 `llmall-pay-service` / `llmall-item-service` 的 `application.yaml` | 5.0 | Nacos 共享配置 `shared-jdbc.yaml` 优先级更高 |
| ② | `-Dspring.datasource.hikari.maximum-pool-size=20`（JVM 系统属性） | 5.0 | Spring Cloud 默认 `override-system-properties=true` |
| ③ | `--spring.datasource.hikari.maximum-pool-size=20`（命令行参数） | 5.0 | SCA 把远程配置源插到最前，连命令行参数都被压住 |
| ④ | ③ + `--spring.cloud.config.override-none=true` | 5.0 | 未被采纳 |
| ⑤ | ③ + `-Dspring.cloud.config.override-system-properties=false` | 5.0 | 未被采纳 |

**旁证（同一轮同一份启动参数）**：`--logging.level.com.llmall.pay.service.impl.PayOrderServiceImpl=DEBUG`
**生效了** —— 差别在于那个键 Nacos 里没有。所以规律是：**凡 Nacos 下发的键，外部参数一律盖不过去**。
两个服务的 `application.yaml` 里本来就写着这句警告（"看起来配了、其实被 Nacos 覆盖"），这次把它验成了事实。

**最终做法（不改 `shared-jdbc.yaml`、不改 Nacos 现网）**：在**压测期临时**把这两个服务的
`bootstrap.yaml` 里的 `shared-jdbc.yaml` 那条共享配置摘掉，改为在它们各自的 `application.yaml` 里内联
等价的 `spring.datasource`（url/driver/账号/hikari，池上限 20）；压完立刻还原，
服务回到"池上限 5（Nacos 下发）"。这段临时配置**没有进提交**。

### 2. 抬池前后延迟对照（50 并发 × 60 秒，多账号，同一份 JMX）

| 采样器 | pool 5（抬池前）Avg / P95 / P99 | pool 20（抬池后）Avg / P95 / P99 | 变化 |
|---|---|---|---|
| `POST /orders` | 57.1 / 77 / 94 ms | 61 / 81 / 149 ms | 基本持平（本链路不走 pay 的连接池） |
| **`POST /pay-orders`** | **1083 / 1398 / 2374 ms** | **573 / 828 / 950 ms** | **Avg −47 %，P99 −60 %** |
| `POST /pay-orders/{id}` | 728 / 944 / 1849 ms | 953 / 1219 / 1326 ms | Avg 上升，P99 下降（见下注） |
| 整链路吞吐 | 74.8 req/s | **85.6 req/s（+14 %）** | — |

> `POST /pay-orders/{id}` 的 Avg 上升、P99 下降：它是 **`@Transactional` 且事务内还发一次 Feign 扣款**，
> 连接被整段占着；池变大后更多这样的长事务能同时进来，于是平均变慢、但尾部不再排长队。
> 这条本身就是一个信号：**余额支付链路把远程调用放进了事务里**（方向 D）。

### 3. 分段计时对照（applyPayOrder，n=1719）

| 段 | pool 5 | pool 20 | 变化 |
|---|---|---|---|
| `trade.queryOrderById#1`（Feign） | 4.4 ms | 5.9 ms | 不变（仍只占 1 %） |
| `pay.queryByBizOrderNo` | 557.2 ms | **326.5 ms** | −41 % |
| `pay.save` | 512.4 ms | **232.6 ms** | −55 % |
| `pay.idWorker.getId` | 0 ms | 0 ms | — |
| **`applyPayOrder` 总耗时** | **1075.2 ms** | **566.5 ms** | **−47 %** |

### 4. 连接池读数：**排队变浅了，但没有消失**

| 指标 | pool 5 | pool 20 |
|---|---|---|
| 池上限 | 5 | 20 |
| 在用连接峰值 | 5（全程顶满） | 20（全程顶满） |
| **排队线程峰值** | **43~46** | **30** |
| 平均等连接 | 517 ms | 278 ms |
| 平均用连接 | 65 ms | 221 ms |
| MySQL 连接数峰值 | — | 36（≤ `max-connections=100`） |
| 行锁等待增量（60 秒） | 351 | 637 |

**怎么读这张表**：
- 排队确实变浅（46 → 30、等连接 517 → 278 ms），**"排队是主因"这一点被证伪了一半、证实了一半**：
  它确实是最大的一块（抬池直接砍掉一半延迟），但**不是唯一的一块**；
- 池一放开，**每次真正占用连接的时间从 65 ms 涨到 221 ms** —— 因为同时打到 MySQL 的连接从 5 变 20，
  MySQL 侧的抓锁与竞争上来了（行锁等待 351 → 637）。所以下一步的天花板已经不是应用侧的池，而是
  **"DB 侧单位时间能吞吐多少"**；
- 每请求仍要取 **2 次连接**（申请支付单没有事务，SELECT 与 INSERT 各借还一次）—— 这是方向 B 的价值所在：
  不抬池也能把每请求的连接占用次数砍一半。

### 5. 结论（供决策）

1. **抬池方向对，但不是终点**：5 → 20 让 `POST /pay-orders` 从 1083 ms 降到 573 ms（−47 %），
   但**没到 300 ms 级**，`pending` 仍有 30。
2. **想继续往下压，优先级应当是 B（每请求 2 次连接 → 1 次）而不是继续加大池**：
   池再大，MySQL 的并发也同步变高（221 ms 单次占用已经在提示 DB 侧摩擦）。
3. **本轮的池上限已还原**：服务当前 `hikaricp_connections_max = 5.0`（Nacos 下发），
   与提交态一致；要不要让 20 长期生效、以及其余 9 个服务抬不抬，是下面待决策的问题。

## 六、停点：等你拍板的问题

1. **池上限怎么落地**：本轮已证实"外部参数改不动 Nacos 下发的键"，所以 pay/item 单独 20 只有两条路 ——
   ① 改 Nacos 的 `shared-jdbc.yaml`（全局默认，红线里明令不动，需要你授权具体数值与范围）；
   ② 用 compose/启动命令把这两个服务改成"不引 shared-jdbc、本地内联 datasource"（会引入配置漂移，
   与两个 `application.yaml` 里的警告冲突）。我不建议 ②。**请定 ① 的具体数值与是否授权。**

### 8.2 代码改动（2 个源文件 + 1 个单测 + 1 份 Nacos 配置）

资金状态机（0/1/2/3 的推进条件）、核销/员工/前端。**没有 git commit。**

#### upsert 的三个关键细节（改动正确性的全部依据）

1. **重复时不改已有行**：`ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id)` 把 id 赋成它自己，
   MySQL 判定"行没有变化"，不会改写金额/状态/渠道，也不会触发 `update_time` 的 ON UPDATE。
   因此"已存在则复用/重置"的分支（终态报错、渠道不同才重置）仍然完整留在 Java 侧。
2. **主键怎么回填**：用 IdWorker **预生成** id 再插入。
   - 新插入：驱动回填的就是这个预生成 id；
   - 命中唯一键：`LAST_INSERT_ID(id)` 让驱动回填**已有行的 id**。
   两者一比就知道是新建还是复用，不需要额外一次查询。**不能用返回的 updateCount 判断** ——
   Connector/J 默认带 `CLIENT_FOUND_ROWS`，新插入与命中都返回 1（已用本项目的 Connector/J 8.0.33
   在临时表上实测：新插入 / 命中已存在行的 `updateCount` 都是 1，`getGeneratedKeys()` 分别返回
   预生成 id / 已有行 id）。
3. **防串单**：命中唯一键后仍按 `biz_order_no` 回查（而不是直接采信回填的 id），
   万一命中的是 `pay_order_no` 上另一行（单号碰撞），回查不到就报错，绝不把别人的支付单 id 返回给本次请求。

### 8.3 连接数预算（复测时实测）

| 消费者 | 池上限 | 下限（min-idle） | 依据 |
|---|---|---|---|
| `llmall-pay-service` | **25** | **10** | 服务专属 dataId（本次调整） |
| 其余 8 个有库服务（item/user/trade/shop/cart/content/search/promotion） | 5 × 8 = 40 | 1 × 8 = 8 | `shared-jdbc.yaml`，本次逐服务读 `hikaricp_connections_max` 确认仍为 5.0 |
| **小计（理论最坏）** | **65** | **18** | `65 ≤ MySQL max_connections = 100`，留 35 条余量给 root/运维/突发 |
| 实测连接峰值（`Threads_connected`） | **48**（池 25 轮次 39~48） | — | 距 100 仍有 52 条余量 |
| MySQL `max_connections` / `wait_timeout` | 100 / 28800 s | — | 实测取值 |

**为什么是 25，而不是 30/50**：

- **不是拍脑袋加的**：池 20 时 `active` 全程顶满 20、`pending` 30（= 50 并发 − 20），
  申请侧平均 389 ms 里有 321~393 ms 在等连接 —— 排队是主因，加 5 条是"把排队往下压一档"的最小步长；
- **再加就撞 DB 侧摩擦**：20 → 25 后 `pending` 只从 30 降到 25，混合"用连接"从 320 ms 涨到 395 ms，
  余额支付 Avg 从 986 ms 涨到 1090 ms。连接不是凭空产生吞吐，而是把更多长事务同时压到 MySQL；
- **预算账**：30 就是 70、50 就是 90，离 100 只剩 30/10 条余量，而实测 `Threads_connected` 已经到 48；
  真正该做的是减少"每条连接被占多久"（方向 D），不是继续加池；
- **minimum-idle 10**：50 并发下池要从 1 长到 25，建连抖动都落在预热阶段；保活 10 条低于上限、不额外占预算；
- **leak-detection 30 s**：本服务最长正常持有是余额支付事务（事务内两次 Feign，读超时 5 s、
  扣款最多 2 次尝试，最坏约 15 s）+ 取连接最多 5 s ≈ 20 s，30 s 留 1.5 倍余量，既不误报，
  又能在连接泄漏把池耗尽前打出持有栈。

运行时确认：`hikaricp_connections_max = 25.0`、`hikaricp_connections_min = 10.0`（`/actuator/prometheus`）。

### 8.4 第 2 步：Feign 查单移出连接持有期（结论：原本就在外面，本轮把它锁死）

**复核结果**：`applyPayOrder` 在本次改动前**就没有** `@Transactional`，旧代码也是先
`checkOrderPayable`（Feign）再 `checkIdempotent`（两次 DB）。所以第 2 步**没有可测的性能变化**，
它是一个"防回归"的结构改动：

- 方法体显式写成两阶段，并在注释里写死"远程校验阶段不取连接、不开事务"；
- 新增单测 `queriesTradeOrderBeforeTouchingDatabase`：Feign 执行时断言
  `TransactionSynchronizationManager.isActualTransactionActive() == false`、且 Mapper 尚未被调用，
  最后用 `InOrder` 断言"先 Feign 后 Mapper"。**任何人以后给 `applyPayOrder` 加 `@Transactional`
  或把 Feign 挪到 DB 段之后，这条测试会直接红。**

**报告中"事务内 Feign 查单占用连接"经复核属于另一个接口**（`POST /pay-orders/{id}` 余额支付），

### 8.7 残留瓶颈（按证据排序）

> 本轮复测期间累计的服务端指标（pay-service 在池 25 之后完成 5 轮有效压测 + E2E；
> user/trade 服务自进程启动起累计，因此分母比 pay 更大）：
> `/pay-orders` 9,597 次 / 3,403.0 s（**Avg 354.6 ms**，与压测一致）；
> `/pay-orders/{id}` 9,502 次 / 10,264.8 s（**Avg 1,080.3 ms**）；
> `/users/money/deduct` 22,062 次 / 14,600.1 s（**Avg 661.8 ms**）；
> `/orders/{id}` 44,372 次 / 309.3 s（**Avg 7.0 ms**）。

1. **连接排队（主因，占申请侧 355 ms 的 ~90 %）**
   `active` 恒等于池上限、`pending` 24~25、等连接 321 ms。**不是 SQL 慢**：单请求 upsert 只有 6 ms。
2. **同一个池被余额支付长事务吃掉（省下的连接去哪了）**
   `POST /pay-orders/{id}` 是 `@Transactional`，事务从第一次 `getById` 一直持有连接到最后提交，
   **事务内**还有两次 Feign：查交易订单（7 ms）和扣款（**662 ms**，含支付密码 bcrypt 校验 + 余额/流水写）。
   按单轮（池 25 的第 4 步）粗算：余额支付每次持有约 1,090 − 321 = 769 ms，1,784 次 ≈ 1,372 连接秒；
   申请每次约 355 − 321 = 34 ms，1,802 次 ≈ 61 连接秒 —— **余额支付占了约 96 % 的连接占用**
   （池 20 的第 3 步同口径约 91 %）。一轮 60 s 的连接需求 ≈ 1,433 秒 ≈ **23.9 条连接持续被占**
   （池 25 的 ~96 %），所以排队是必然结果。
3. **MySQL 侧（次要，且在抬池后变差）**
   `Threads_running` 峰值 ≤ 13、行锁等待 907~1122/min、`Innodb_data_fsyncs` ≈ 1.9 万/min。
   DB 没有成为主瓶颈，但 20 → 25 后混合"用连接"320 → 395 ms 说明 DB 摩擦在上升，继续加池收益递减。
4. **Feign 查交易订单（不是瓶颈）**：服务端平均 **7.0 ms**（44,372 次），与 10-17 的 4.4~5.9 ms 一致。
5. **JVM GC（不是瓶颈）**：37~43 次/分钟、合计 153~308 ms/分钟 ≈ 0.3 %，池 25 后没有恶化。
6. **空载 vs 负载的差值**：单请求 upsert 6 ms / 余额支付事务 145 ms；到 50 并发分别变成
   申请侧 ~35 ms 工作 + 321 ms 排队、余额支付 ~760 ms 工作 + 321 ms 排队 —— **差值全部来自
   等连接与"下游在负载下变慢"，不是某一条 SQL 突然变慢**。

**目标为什么没达到**：在不碰 `POST /pay-orders/{id}` 的前提下，申请侧每请求只剩 1 次取连接，
但这一次取连接要和占约 96 % 连接占用的余额支付长事务抢同一个池；只要池被长事务占满，
申请侧的排队就还在 300 ms 量级。**Avg ≤ 200 ms 需要先降低"连接被占多久"（方向 D），
或者在连接层做隔离（独立池/bulkhead），而不是继续加池。**
