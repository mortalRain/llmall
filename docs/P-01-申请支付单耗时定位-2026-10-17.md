# P-01 定位报告：申请支付单的 1072 ms 到底花在哪

> **状态：停点 —— 只定位、不改业务逻辑，等拍板优化方向。**
> 本报告不含任何优化改动；支付链路（`PayOrderServiceImpl`）本轮只增加了只读的分段计时。

---

## 一、结论先说

| 段 | 内容 | Avg | P50 | P95 | P99 | 占整条链路耗时 |
|---|---|---|---|---|---|---|
| `trade.queryOrderById#1` | 同步 Feign 查交易订单（`checkOrderPayable`） | **4.4 ms** | 2 ms | 5 ms | 22 ms | **0.4 %** |
| `pay.queryByBizOrderNo` | 按交易订单号查支付单（`checkIdempotent` 第一步） | **557.2 ms** | 562 ms | 779 ms | 1137 ms | **51.8 %** |
| `pay.idWorker.getId` | 生成支付单号（本地计算） | **0 ms** | 0 | 0 | 0 | 0.0 % |
| `pay.save` | 插入支付单（`checkIdempotent` 落库） | **512.4 ms** | 519 ms | 748 ms | 1729 ms | **47.7 %** |
| **`applyPayOrder` 整条链路** | 入口 → finally（含上面各段与间隙） | **1075.2 ms** | 1122 ms | 1373 ms | 2329 ms | 100 % |

（n = 1487 条 `POST /pay-orders` 请求；App=应用侧耗时，单位为毫秒）

**一句话**：**不是 Feign 慢，也不是单号生成慢 —— 是 pay-service 自己访问 MySQL 的第一步和第二部各花了半秒，
而这两半秒里约 87% 是"排队等数据库连接"，不是 SQL 本身慢。**

### 根因：`hikari.maximum-pool-size: 5` 把 pay-service 的 DB 并发钉死在 5

同一轮压测里从 pay-service 自己的 Prometheus 指标取的增量证据：

| 指标 | 值 | 含义 |
|---|---|---|
| `hikaricp_connections_max` | **5** | 池上限 5（来自 `nacos-config/shared-jdbc.yaml`） |
| `hikaricp_connections_active`（全程采样） | **恒为 5** | 5 条连接 100 % 占用，没有空闲 |
| `hikaricp_connections_pending`（全程采样） | **43 ~ 46** | 同一时刻有 45 个左右线程在排队等连接 |
| `hikaricp_connections_idle`（全程采样） | **0** | 无空闲连接可借 |
| 每次获取连接的平均耗时（acquire） | **517 ms** | 这是排队时间 |
| 每次真正使用连接的平均耗时（usage） | **65 ms** | 这含 SQL 执行 + 驱动 + 网络 |
| MySQL `Threads_running` 峰值 | **7** | 数据库自己并不忙 |
| MySQL 行锁等待（当前等待峰值 / 增量） | **0 / 351** | 不是行锁把请求卡住 |
| 连接获取次数（本轮增量） | **4575 次** | 与"apply 每请求 2 次 + 支付每请求 1 次"完全对得上（1530×2 + 1509×1 = 4569） |

两项一比就是全部答案：**一次 DB 操作 = 517 ms 排队 + 65 ms 执行**。排队占了 89 %。

### 吞吐天花板（用同一组数算得出来，且与实测吻合）

- 池上限 5 ÷ 单次占用 0.065 s = **≈77 次 DB 操作/秒**；
- 实测本轮 4575 次获取 ÷ 60 秒 = **76.3 次/秒** —— 已经贴着这个天花板，几乎没有余量；
- 申请支付单**没有事务**，SELECT 与 INSERT 各取一次连接、各还一次（这是 2 次/请求的来源）；
  余额支付**有** `@Transactional`，整段只占 1 次连接（1 次/请求）。
  这解释了一个此前没有量化的现象：同一套并发下，`POST /pay-orders`（1083 ms）比
  `POST /pay-orders/{id}`（728 ms）慢 —— 前者比后者多一次"取连接"。

## 二、怎么测的（可复现）

### 1. 埋点（只读，不改业务逻辑）

`llmall-pay-service/.../PayOrderServiceImpl.java` 里增加了一个私有静态内部类 `SegmentTimer`，
在 `applyPayOrder` 的 finally 里**一条日志打完所有段**（一次请求一行，避免日志 IO 本身变成瓶颈）：

```
[BIZ] stage=PROFILE phase=applyPayOrder bizKey=<交易订单号> totalMs=1075 seg=trade.queryOrderById#1:4 pay.queryByBizOrderNo:557 pay.idWorker.getId:0 pay.save:512
```

- 段口径：`begin()` / `record(name, begin)` 成对包裹被测调用；`finally` 里落日志，**失败路径同样有样本**；
- 另一处：`tryPayOrderByBalance` 里扣款前的那次 `tradeClient.queryOrderById`（第二处 Feign 回查）。
- 计时器不写库、不发消息、不抛异常、不改返回值；对业务结果的影响为零（分段日志开启前后账实核对同样精确成立，见第四节）。

**日志级别是 DEBUG，非常开 INFO**。定位时按包名临时开级，不必改代码：

```powershell
# 例：只对 pay-service 打开分段计时（其余日志级别不动）
JAVA_OPTS="... -Dlogging.level.com.llmall.pay.service.impl.PayOrderServiceImpl=DEBUG"
```

关闭时不会拼字符串（先判 `isDebugEnabled()`），主链路只剩几次 `nanoTime()` 的开销。
理由：分段计时是定位工具而不是生产语义日志 —— 常开 INFO 会给每个支付请求多写一行，
压测时日志 IO 还会反过来影响被测链路（这也正是"一条日志打完所有段"的原因）。

## 三、几处容易误判的地方（如实写）

1. **Feign 不是瓶颈**：`trade.queryOrderById#1` 的 P99 只有 22 ms（均值 4.4 ms）。
   台账此前猜测"瓶颈在交易订单远程校验 + 落库"，**前半句不成立**，后半句成立。
2. **单号生成不是瓶颈**：`IdWorker.getId()` 全程 0 ms（本地序列，不访问网络）。
3. **不是 MySQL 慢、也不是行锁**：全程 `Threads_running ≤ 7`、行锁当前等待峰值 0。
4. **不是某个 HTTP 线程卡住**：`pending` 峰值 45~46 与 50 并发同量级，说明请求都停在"等连接"这一步，
   而不是停在网关或 Feign。
5. **本轮为腾内存停掉了 shop / cart / content / search / promotion 五个服务**（宿主内存压测前 97 %，
   守卫脚本按红线拒绝了第一次启动）。因此**绝对延迟不与上一轮严格可比**，
   但**段间占比**这个结论不受影响 —— 五个被停服务都不在申请支付单链路上。
6. **未覆盖的段**：`claimDeductAttempt`（条件更新）、`markPayOrderSuccess`、扣款 Feign、
   事务收尾钩子。它们在 `POST /pay-orders/{id}` 里，已有 `BizTrace.cost` 的总耗时（728 ms），
   本轮没有再细分 —— 不属于 P-01（申请支付单）的范围。

## 四、账实核对（红线：必须精确成立）

本轮所有改动后复跑，判据与上一轮压测一致：

| 核对项 | 值 | 判据 |
|---|---|---|
| 50 个压测账号初始余额合计 | 1,000,000,000 分 | — |
| 压后余额合计 | 924,147,200 分 | 差额 **75,852,800 分** |
| 余额差额 ÷ 25,600 | **2963.0** | 与"支付成功次数"精确相等 |
| `balance_flow`（`PAY:` 流水，压测账号） | **2963 条**，`SUM(change_amount) = -75,852,800` | 与扣款次数一一对应，金额全为 25,600 |
| `pay_order` 状态 3（压测账号） | **2963 条** | 与流水、与订单状态 2 三者相等 |
| `pay_order` 中 `COUNT(DISTINCT biz_order_no)` | **3018 = 总条数 3018** | 一单一张支付单，无重复 |
| 订单状态 2（已付款，压测账号） | **2963** | — |
| 并发双击（同一支付单 20 线程） | **1×200 + 19×400**，余额差额 **25,600** | 只扣一次 |
| **最终复核（含双击那一次）** | 差额 **75,878,400 = 2964 × 25,600**（`ROUND(差额/25600,3) = 2964.000`）；流水 2964 条、支付成功 2964 条、订单已付款 2964 条，三者相等 | 精确成立 |

> 双击实验：`logs/task1/double-click.ps1`（bench50 造新单 → 20 线程同时支付 → 校验余额差额）。
> 最终复核 SQL：`logs/task1/accounting-final.sql`。

**结论：加了分段计时之后，账实核对依然精确成立，且双击只扣一次。**

## 五、优化方向（**只是选项，等拍板**）

按"改动小 → 大"排序，每一条都标了口径与风险：

| # | 方向 | 预期收益 | 风险与注意 |
|---|---|---|---|
| **A** | **抬 pay-service 的连接池上限**（5 → 15~20） | 直接按 Little 定律：吞吐 ≈ 池 ÷ 单次占用，池 ×3 则吞吐 ×3（排队时间降为 1/3） | ① 全局连接数要重新算账：11 服务 × 5 = 55，MySQL `max-connections=100` 只是勉强够；只抬 pay 到 20 → 70，仍留 30 余量，但**必须同时核对其它服务的峰值**；② 池不是越大越好，而 5 明显是把资源省到了错误的地方 |
| **B** | **把申请支付单的两次取连接合并为一次**（给 `applyPayOrder` 加只读事务，或把"先查后插"改成一条 upsert） | 每请求 DB 操作数 2 → 1，**同池上限下吞吐翻倍** | ① `applyPayOrder` 目前**故意没有事务**，唯一性靠 `pay_order.biz_order_no` 唯一索引兜底；加事务本身不改正确性，但会延长持锁时间，需要压测复核；② 改 upsert 会改"查到旧单即复用/重置"的分支逻辑，**属于支付链路结构调整，必须小步 + 每步过闸门** |
| **C** | **降低单次连接占用（65 ms）** | 直接抬高天花板 | 本轮 60 秒里 13,702 次 INSERT 产生 16,082 次 fsync —— 单次占用里很可能有一部分是提交时的落盘等待。任何涉及 `innodb_flush_log_at_trx_commit` 的调整**是持久性取舍，属资损红线**，不建议在本轮动 |
| **D** | **余额支付链路不要在事务里调远程** | `POST /pay-orders/{id}` 的 743 ms 里，连接被整段占着（含 `userClient.deductMoney` 的 Feign 往返） | 这是**资金链路的事务结构调整**，风险最高，且不属于 P-01（申请支付单）范围。建议先只记录，不动 |
| — | ~~去掉/异步化 `tradeClient.queryOrderById`~~ | **不建议**：它只占 0.4 % | 而且它是资损防线（订单已关闭却继续扣款的唯一拦截点），**不能动** |

### 我建议的最小第一步

**只做 A**（抬池上限），因为它是配置层、不碰代码分支、可一步回滚，且能直接验证"排队是不是真因"：
若抬池后 Avg 从 1075 ms 掉到 ~300 ms 级、且 `pending` 归零，则根因确认，B/C/D 才有必要谈。

## 六、停点：等你拍板的问题

1. **优化方向**：先做 A（抬池上限）？还是 A+B 一起？还是先只做 A 并复跑压测？
2. **池上限的目标值**：pay-service 5 → 10 / 15 / 20？（要同时定 MySQL `max-connections` 与其它服务的池上限口径，
   我建议先给 pay 单独 20，并复核 MySQL 连接总数 70/100）
3. **是否允许动 `applyPayOrder` 的事务边界**（方向 B）？这条会碰"先查后插 + 唯一键兜底"的结构，
   按红线需要小步走 + 每步过闸门 + 复跑压测 + 精确账实核对 —— 需要你明确授权范围。
4. **C（fsync 相关）与 D（事务里调远程）是否纳入后续**？我倾向：**本轮都不动**，只登记。
5. **分段计时日志的去留**：当前是常开 `log.info`（每请求一行）。定位结束后是否要我把它改成
   `log.debug` 或加开关（例如 `llmall.pay.profile.enabled`），避免长期占用日志量？

> 在收到答复前：**支付链路不再有任何改动**，压测数据保持现状，账实核对结论保持为"精确成立"。
