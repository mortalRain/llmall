# 普通券购买升级与恢复操作说明

适用范围是普通券领取。秒杀继续使用原协议，不可据此切换资金键。本文只交付操作材料，不代表已在业务库执行迁移或部署。

## 升级前与执行顺序

1. 备份 promotion 的券/持券数据、user 的余额/完整资金流水和 64 引入的账本，保存同一维护窗口的对账快照。先在隔离的 MySQL 8 副本预演，检查表结构、唯一键、字符集和守卫行为。
2. 停止旧普通购券入口，暂停旧恢复/补偿任务；停止并排空所有旧 promotion/user 写入实例、在途 HTTP/RPC 与队列消费者。64 还要求停止旧 pay/trade 写入。仅网关停流不够，旧实例不能与新实例混跑。
3. 按 `sql/merged/README.md` 的唯一顺序执行必要增量。已有基础表后先 `64-payment-recovery.sql`，再 `65-voucher-purchase.sql`；65 显式引用 64 的 `balance_payment`、`voucher_order_cancel`、`payment_attempt`，缺一即失败。初始化演示角色时另有 `32 → 60 → 33` 依赖，33 的 Rose INSERT 引用了支付密码列。
4. 使用遇错即停的 MySQL 客户端执行，**禁止 `mysql --force`**，也不能用忽略退出码的外层脚本继续发布。65 的临时表已插入主键 1，发现风险时再次插入 1，故意报重复键；这就是阻断升级的守卫，不是可忽略的幂等报错。失败后保持停流，关闭该连接（清除临时表），核对后用新连接重试。
5. 65 仅新增 `voucher_purchase`，不修改余额、旧流水、持有券或历史购买记录。守卫通过后同批发布支持 `VOUCHER_PURCHASE_V1:<雪花ID>` 的新 user、promotion 与前端，核对实例版本一致后开放入口。不得拿旧清理脚本、删账本或自动扣退款让守卫“通过”。

## 旧数据守卫如何判断

只检查精确前缀 `VOUCHER_BUY_` 的 DEDUCT 与 `VOUCHER_REFUND_` 的 REFUND；秒杀命名空间不参与。买入和退款前缀长度不同，分别从各自完整前缀之后取首段 voucher ID；按流水 `user_id` 与该 voucher ID 聚合所有历史尝试的 `change_amount`，金额单位分。

净额为负表示尚有支出，净额为正表示净退款。没有匹配 `user_voucher(user_id,voucher_id)` 且净额不为零，或者无论有没有券净额为正，都会阻断。使用过、过期的券仍算已发券事实，不能只查“未使用”状态。已有券且净支出非正或无券但净额为零可通过；这不是历史每笔付款都正确的证明，人工对账仍须保留。

失败时导出该前缀下完整流水，并用 SQL 中相同的 `legacy_net` 子查询改为只读 SELECT（显示 `user_id,voucher_id,net_amount,uv.id`），核查原始键、关联券、资金账本和调用记录。不得根据总余额猜测退款、不得重扣旧未决款，也不得用新键重放旧请求。任何业务修复需单独审批、保留证据与可审计修复方案，65 不执行这些修复。守卫通过也不能解除“停旧版本后再上线”的要求。

## 新协议上线后的观察与恢复

`voucher_purchase` 的 id 由应用雪花算法生成，不自增；`request_id` 是区分大小写的 ASCII、最长 64 字符，唯一性为 `(user_id,request_id)`。金额、门店和过期时间是领取时快照，不能按当前模板价格重算。恢复任务使用 `(next_check_time,state)` 索引；按用户券查看尝试使用 `(user_id,voucher_id,state)`。

| 状态 | 已提交事实与操作 |
|---|---|
| ACTIVE | 已持久化请求，尚无最终结果；重试查询，不拿原支付密码重复扣款。超过两分钟的尝试由恢复任务转撤销。 |
| ISSUED | 券与成功状态在同一本地事务提交；返回原 userVoucherId。后续模板变价、下架不能改变成功事实，绝不能撤销它。 |
| CANCELING | 撤销意图已提交；用户域原子 cancel 完成退款或写取消墓碑，失败可重试，确认前不能标记完成。 |
| CANCELED | 已确认取消；前端结束旧请求，下一次需要用户显式确认并使用新 requestId。 |

恢复任务每 30 秒扫描最多 100 条，先延后本批检查时间，避免一条永久失败挡住后续记录；多实例重复依赖数据库锁与资金域幂等。观察 ACTIVE/CANCELING 的数量、最老等待时间、下一检查时间与失败日志/指标，持续积压需查依赖故障、锁等待和执行器状态。任务不依赖登录上下文，不保证故障下有限时间内清空积压。

发生 RPC 超时、进程中断或数据库提交回执丢失时，先按当前用户 requestId 查询持久状态。ISSUED 必须返回原券，不能误退；ACTIVE/CANCELING 显示处理中并保留请求键。NOT_FOUND 可复用原键发起请求；网络不确定不能生成新键。前端按用户和券在 localStorage 保存 requestId，写入失败应阻止付费请求；不要保存密码。状态查询不能用于查看他人的购买。

排障先做只读检查，例如按 `user_id,request_id` 查购买记录，以 `VOUCHER_PURCHASE_V1:<id>` 查 `balance_payment` 和对应流水，再核对 `user_voucher_id` 的持券事实。不要手改状态、删唯一键、删流水或调用旧退款接口。恢复依赖暂不可用时修复依赖并继续同键幂等恢复。

## 回退与验证边界

新版本写入发生前，可在保持停流的前提下整体回退同批应用；新增表保留，不需要删表。新版本已产生购买记录、资金账本或取消墓碑后，不得直接回旧普通购券协议，旧代码不理解新事实且会使用不同资金键。先停流保留全部记录，在副本对账并制定整体恢复方案；绝不为回滚清空 `voucher_purchase` 或 `balance_payment`。

`VoucherPurchaseMigrationGuardTest` 读取实际 65 文件并执行守卫查询，覆盖不同前缀解析、同用户同券聚合、无券未结款、超额退款、用户/券隔离、持券历史支出与秒杀排除。测试使用 H2 MySQL 模式，仅对临时表语法作兼容替换；不构成 MySQL 实机 DDL、ASCII 排序规则、生产数据完整性或跨进程崩溃演练证明。本次未执行真实业务 SQL 或部署。

## 浏览器与演示脚本边界

付费购买需要支持Web Locks的浏览器，并通过HTTPS或localhost访问；跨标签页购买和恢复使用同一用户/券锁。不满足条件时明确阻止付费提交，不作无锁降级。前端密码只存在当前确认请求内，刷新后只查状态，不重放密码。

当前demo.ps1旧水位清理仍未完整适配各域资金和购买账本；如在隔离演示环境使用，必须传-NoCleanup保留事实和流水，勿用于有价值数据。旧cleanup-e2e-data.sql/cleanup-bench-data.sql不得用于本协议数据。默认演示清理的整体重写另立任务，此次未宣称已修复H18。
