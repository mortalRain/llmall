# sql/ 目录说明

## 结构

| 路径 | 内容 | 性质 |
|---|---|---|
| `merged/` | 库表结构演进脚本（`00`–`62` 按序执行，含幂等守卫），全新库可重放 | 随代码演进，必须入库 |
| `llmall-{item,cart,pay,trade,user}.sql` | 各业务域**完整数据导出**（结构 + 演示数据），供 demo 与检索演示直接装载 | 演示数据集 |

## 为什么 `llmall-item.sql`（34.7MB）整份入库

这是权衡后的决定，不是疏忽：

1. **演示需要数据规模感** —— 门店热度榜、搜索加权、评价 → 榜单联动，都依赖一批真实感的商品数据（京东公开示例商品）。手工造几百行，造不出「榜单随评价实时变化」的演示效果。
2. **克隆即跑** —— `docker compose up` 后装载本文件即有完整数据，不需要再去任何地方下载。
3. **替代方案被否的原因**：
   - *瘦身种子版*：收益只是省 30MB 工作树体积，代价是要同步核对演示口径与 E2E 断言；
   - *Git LFS / Release 附件*：增加「clone 后再下载」一步，破坏一键体验；且 34.7MB 的历史对象仍在 `.git` 里，clone 体积并不会因此变小。
4. **体积账**：34.7MB 在 GitHub 50MB 警告线以下，对 clone 时长影响约数秒。

若未来本仓库转为多人协作的长期项目，正路是：仓库内改放 `llmall-item-seed.sql`（结构相同、精选数据），完整版挂 GitHub Release —— 那是产品化动作，演示阶段不必。

## 注意

- 本文件由 HeidiSQL 从早期环境导出：文件头注释中的主机 IP 是**导出环境**，与当前部署环境无关。
- 本文件超过 1MB，被 `gates/gate.ps1` 的脚本指纹扫描排除（闸门只指纹「代码文本」，见其头部注释）；
  但任何结构性变更仍应先走 `sql/merged/` 流程，保持「库表脚本可重放」口径。
